## 1. RAM / Performance

*Codex verdict: partially confirmed with corrections — see [`CodexReviews/01-performance-ram.codexreview.md`](CodexReviews/01-performance-ram.codexreview.md).*

**Root architectural cause:** the entire save database — every character, every chat, every message, every module — lives in one monolithic Svelte 5 `$state` tree (`DBState.db`, `src/ts/stores.svelte.ts:105-107`). Svelte 5's deep-proxy reactivity means any edit anywhere can be read by broad effects that subscribe to large swaths of that tree.

**The reported Module-editor keystroke stutter is confirmed, and it's worse than "saves to disk every keystroke":**
- The Module editor has no draft copy — `ModuleSettings.svelte:110` binds the edit UI directly to the live `DBState.db.modules[i]` proxy.
- Every keystroke therefore mutates global state directly, which fires **two independent, un-debounced full `$state.snapshot()` deep-clones of the entire `modules` array** (`stores.svelte.ts:195-204` and `globalApi.svelte.ts:356-360`). Confirmed by cross-validation as-is.
- Only the actual disk write is debounced (500ms). The stutter is a synchronous main-thread clone cost that happens *before* that debounce ever fires.
- **Corrected:** the general autosave watcher (`globalApi.svelte.ts:376-403`) does deep-clone the active character's entire chat history on relevant edits, but it explicitly excludes `modules`/`botPresets`/`loadouts`/`plugins`/`pluginCustomStorage` — so a Module editor keystroke does **not** trigger this particular clone. It remains the mechanism behind stutter when editing character fields or chatting, just not for module edits specifically; the two are independent hot paths, not one combined one.
- **New finding from cross-validation:** the Module "Create" flow has a real duplicate-insertion bug, distinct from the perf issue — `ModuleSettings.svelte:157` and `:182` both push the same new-module object onto `DBState.db.modules`, so every newly-created module gets inserted twice.

**No virtual scrolling anywhere.** Chat message rendering grows monotonically within one open chat (`DefaultChatScreen.svelte`, loads 30 messages then +15 per scroll upward) — old messages are never unmounted as the user scrolls back, so a long single conversation accumulates an ever-growing live DOM tree. (Corrected: this window does reset when switching chats, so it isn't unbounded *across* the whole session — only within one long chat, which is where the actual RAM risk lives.)

**Cold storage helps more than originally stated, but still not the hot data.** It offloads idle *characters* (10+ days untouched) **and** — corrected — independently sweeps old, stale *chats* within any character, including the currently-active one. It provides zero relief only for the active/recent chat itself and for `modules`/`botPresets`/`loadouts`/`plugins`, which remain the data actually implicated in the bugs above.

**Android relevance:** the monolithic state, the confirmed per-keystroke deep-clones, the unbounded within-chat DOM growth, and full-character `JSON.stringify` per save are RAM/CPU-transient-heavy patterns that compound directly into OOM risk on low-RAM Android WebViews — this is the concrete basis for gating Android platform work (see §4).

**Round 2 (deep-dive):** *Codex verdict: partially confirmed with corrections — see [`CodexReviews/01-performance-ram-deepdive.codexreview.md`](CodexReviews/01-performance-ram-deepdive.codexreview.md).*
- **The most broadly-reproducible new bug in the whole investigation**: `fileCache` (`globalApi.svelte.ts:99-104`, `199-219`) is an unbounded, never-evicted in-memory cache holding the full raw bytes of every asset resolved on the non-Tauri/non-service-worker path, redundantly re-encoded to base64 on every hit. Unlike the Module-editor bug (one screen) or the chat-list bug (long chats only), this fires from ordinary browsing.
- A second unbounded in-memory cache: the translation cache (`translator.ts:22-25`) grows one entry per unique translated string for the session's lifetime with linear-scan lookups.
- **Corrected**: plugin iframe cleanup was originally "checked, no issue" — it's actually a confirmed bug. A synchronous throw in an unload callback skips `host.terminate()` entirely (termination only runs after the callback, not in a `finally`), so a removed plugin's iframe/host registry entry can leak.
- **Corrected**: "no other unbounded list found" overstated the evidence — several other uncapped `{#each}` renderers exist (LoreBook, scripts, triggers, characters, personas, modules); there's no basis to call them safe at scale, only that chat is *probably* highest-risk.
- The Module editor's live-state-aliasing pattern (binding an editor directly to a live `DBState` array element) also exists in the **LoreBook entry editor** and **Regex/Script editor** — though direct binding to live state turned out to be widespread (Persona/CharConfig do it too); what's actually distinctive about the Module editor is the *cost* of what gets cloned on each keystroke, not the binding pattern itself.

## 2. Persistence / Save Reliability (web)

*Codex verdict: partially confirmed with corrections — see [`CodexReviews/02-persistence-reliability.codexreview.md`](CodexReviews/02-persistence-reliability.codexreview.md).*

**Most important finding — a save that fails has no automatic retry path, and can be lost.** In the autosave loop (`globalApi.svelte.ts:409-485`), the pending-change tracker is cleared *before* the write is attempted, and the `catch` block never re-arms it. **Corrected:** there is no formal retry-then-give-up mechanism as originally described — there simply is no automatic retry at all. Failures 1-4 are just logged; a user-facing alert only fires from the 5th *accumulated* failure across whatever save attempts happen to occur next, and the edit only gets a fresh save attempt if some unrelated mutation happens to re-fire a tracking effect before the tab/app closes. Also corrected: the tracker isn't uniformly wiped — character/chat entries keep their newest value; only `botPreset`/`modules` are cleared. Net effect stands regardless: this is a plausible root cause for "I edited something and it wasn't saved" reports. (The claim that web write paths fail "far more often" than Tauri's is a reasonable hypothesis, not something established by the code — flagged as such in the report.)

**OPFS — the storage backend with a stronger atomicity story than plain IndexedDB — is dead code.** It's gated behind a `localStorage['opfs_flag!'] === "able"` flag that nothing in the codebase ever sets (`autoStorage.ts:177-179`). The real web default for the main database falls through to LocalForage (normally IndexedDB in supported browsers, though that's LocalForage's own driver choice, not a hard guarantee). Cold storage does use OPFS directly, though — corrected — only in its ordinary-browser-profile branch (not account-sync or Node-server), not unconditionally across every web configuration. Separately, `OpfsStorage.setItem` doesn't `await stream.close()` (`opfsStorage.ts:12-14`) — confirmed as a real bug (an async close rejection is silently dropped) — currently unreachable, but a live landmine if the flag is ever flipped. (The stronger claim that this "breaks the atomic swap guarantee" and would race into `NoModificationAllowedError` is a plausible consequence, not something demonstrated by the code or a reproduction here.)

**No storage-quota handling anywhere** — no `navigator.storage.estimate()`, no `QuotaExceededError` handling — confirmed via repo-wide grep. Quota failures flow straight into the no-automatic-retry gap above.

**The block/chunk save model itself is reasonably sound** — saves are incremental (only changed blocks re-encoded) and the whole buffer is assembled in memory before one `setItem` call, so JS-level torn writes are unlikely. The risk is concentrated in the storage-backend layer, not the save format. **Corrected:** Tauri bypasses `AutoStorage` entirely, including for remote character blocks (contrary to the original report's phrasing) — `AutoStorage`'s remote-block path is only actually exercised by the Node-server backend.

**Existing test coverage is narrower than it looks:** `remoteSaveCleanup.test.ts` only tests remote-block cleanup logic that's inactive on the pure web/IndexedDB build. The one area with dedicated tests is, structurally, the area least relevant to "mainly web version" bug reports — and, per cross-validation, this cleanup mechanism also never runs for the Node-server backend (it's gated to Tauri specifically), so Node-server remote-block orphans go unswept too.

**Round 2 (deep-dive):** *Codex verdict: partially confirmed with corrections — see [`CodexReviews/02-persistence-reliability-deepdive.codexreview.md`](CodexReviews/02-persistence-reliability-deepdive.codexreview.md).*
- **`saveDbKei()`'s KEI auto-backup can fail silently forever**: an un-awaited, uncaught `fetch()` (`kei/backup.ts:83-104`), with the rate-limit timestamp set before success is even known — a KEI-enabled user can have every auto-backup fail for an entire session with zero signal.
- **A real data-loss path**: local backup restore (`backuplocal.ts`'s `LoadLocalBackup()`) can overwrite the live database with corrupted/undecrypted data — a decrypt failure only logs/toasts rather than aborting, and the result flows through `setDatabaseLite()`, which does essentially no validation, unlike the normal boot path's `setDatabase()`. **Corrected**: the decode step isn't guaranteed to "always produce something" (it can still throw), and a cold-storage confirmation dialog does appear before the overwrite — it's just unrelated to data integrity, so it doesn't actually protect against this.
- **The self-hosted Node server itself** (code round 1 never reached) does a plain in-place `fs.writeFile` with no atomic write and no locking. Its batch-delete endpoint is also broken — **corrected mechanism**: the client hex-encodes the *entire* `$$`-joined key blob as one unit, and the server splits on `$$` *before* hex-decoding, so a batch delete of N keys deletes **zero** of them (not "the first one succeeds, the rest are silently unconfirmed" as originally described) — a worse bug than first reported, just via a different mechanism.
- Two more localforage instances (inlay attachments, plugin storage) lack error handling; inlay attachments have no automatic GC at all — only a manual debug UI action removes them. **Corrected**: a third instance, `risuSaveCacheForage`, was originally lumped in with these two but is actually covered by the existing save-retry path — not the same gap.
- No checksum in the save format — a bit-flip inside a JSON value parses fine into silently-wrong data, a different failure class than "fails to parse."
- Confirmed `changeTracker.loadouts`/`.plugins`/`.pluginCustomStorage` are set but never reset, silently defeating incremental save for those three blocks for the rest of the session.

## 3. Asset "Corruption"

*Codex verdict: partially confirmed with corrections — see [`CodexReviews/03-asset-corruption.codexreview.md`](CodexReviews/03-asset-corruption.codexreview.md).*

**Confirms the community plugin's reverse-engineered model was highly accurate** — nearly every file:line claim in `Agents/Evidences of Investigations/Asset Cache/Community Mitigation_Webrowser Plugin/main-world.js` checked out against current source, independently re-verified rather than trusted, and confirmed a second time by an independent Codex pass. The bug is real and has **at least three independent root causes**, not one — though impact severity was overstated in a few places, corrected below:

1. **[Most serious, but opt-in] Unbounded fuzzy image-name collapse in `ChatBody.svelte`'s `checkImg()`.** When `newImageHandlingBeta` is on, this function re-scans already-resolved `/sw/img/<hex>` image sources, fails to recognize them as already-resolved (its exclusion filter checks URL schemes but not this shape), and falls into a Levenshtein nearest-neighbor search **with no distance cap** — collapsing many different images onto whichever asset has the smallest edit distance to the hex string. This is a genuine, currently-live logic bug, independently re-derived twice now (once by the original pass, once by Codex). Corrected: it reruns tied to markdown re-parse events, not literally "every re-render," and the resulting mismatch is deterministic (asset-order tie-breaking), not arbitrary.
2. **Incomplete boot-time GC allowlist.** `getUncleanablesSync` (`globalApi.svelte.ts:933-1028`) never references `gptSoVitsConfig.ref_audio_data.assetId`, `NAIImgConfig.*`, or `wavespeedImage.reference_image` — confirmed exact. **Corrected — impact differs by field:** GPT-SoVITS reference audio is the genuinely severe case, since TTS reads it back via `loadAsset(assetId)` with no fallback, so its deletion is real functional data loss. NAI and Wavespeed reference/character images are less severe than originally claimed: both retain a separate base64 copy used directly by generation, so deleting the local `assets/*` copy mainly breaks the cached *preview*, not the feature. `reference_image_multiple` should not have been listed as an omitted field at all — no current code path populates it via `saveAsset`.
3. **Zero-byte cache poisoning.** A local-storage read miss can result in a `/sw/register/` POST with a null body; the service worker happily caches that as a 0-byte entry, and the app's own "is this cached" check (`/sw/check/`) reports success — so the image never gets a chance to re-register. **Corrected:** "renders blank forever"/"permanent" overstates this — the underlying cache entry can still be evicted or manually cleared, so it's accurately "persists until removed," not a literal permanent state, though nothing in the app's own logic will ever self-correct it.

A structural precondition underlies all three: the service worker's `CacheStorage` layer is a pure lookup cache that is **never revalidated** against the actual source-of-truth storage after its first write — nothing keeps it honest.

**None of the six files' pre-existing "corrupt" string hits in `src/ts` are actually about image assets** — they're about save-blob corruption, backup-file corruption, lorebook corruption, cold-stored-chat corruption, or memory-subsystem JSON corruption (six files, more than six individual hits — a minor counting imprecision in the original report, corrected). This is itself informative: **RisuAI currently has no first-party concept of "asset corruption" at all** — every diagnostic vocabulary (cache mismatch, zero-byte entry, name collapse) that exists today was invented by the third-party community plugin, not the app.

**Round 2 (deep-dive):** *Codex verdict: partially confirmed with corrections — see [`CodexReviews/03-asset-corruption-deepdive.codexreview.md`](CodexReviews/03-asset-corruption-deepdive.codexreview.md).* This pass looked beyond images specifically, since the underlying `{{...}}` tag syntax also covers video/audio/bgm and the round-1 investigation was anchored to a third party's image-specific findings. Two "checked, sound" verdicts from the deep-dive were **reversed** on cross-validation — flagged explicitly below since that's a more serious correction than the usual overstatement:
- **Reversed — group-chat GC exclusion is not actually safe.** The deep-dive concluded `groupChat` has no `additionalAssets`/`vits`/`ccAssets` fields at all, so excluding group chats from the GC allowlist was sound. It stopped reading the type definition too early: `groupChat` **does** declare `vits` and `additionalAssets` (only `ccAssets` is genuinely absent). Whether those fields are ever actually populated for a real group chat is unresolved — the original code has a "lazy hack for typechecking" comment suggesting they might be typing artifacts only — but the "no bug here" verdict is not supported as stated, and this is flagged as an open follow-up.
- **Reversed — the `.charx` import "no collision risk" conclusion relied on a false assumption.** ZIP archives can contain duplicate member names; the importer keys assets by filename alone, so a collision path does exist (content-hash storage still prevents it from overwriting unrelated assets already on disk, limiting the damage to import-time confusion).
- **Confirmed, new**: video/audio/bgm assets share the exact same resolution pipeline as images (so they're equally exposed to the still-open GC-allowlist gap, though not to the now-fixed `checkImg()` bug, which is `<img>`-only). The bgm player only ever creates one `Audio` element and never swaps tracks — switching chats/characters can silently leave the wrong background music playing.
- **Confirmed, new**: character-asset and module-asset name pools get merged into one bucket — a module asset sharing a name+extension with a character's own asset can silently blend in and get selected instead (deterministically per chat, not randomly, per correction).
- **Confirmed, new**: inlay (chat attachment) storage has no boot-time GC at all — the inverse risk from the main cache (nothing wrongly deleted, but orphans accumulate forever).
- **Confirmed, new, scope-corrected**: emotion-image resolution caches the resolved path by value, not by name — editing/removing an emotion doesn't invalidate the cache. Scoped to the current session only (the cache isn't persisted, so it can't survive a restart, contrary to the deep-dive's original framing).
- **Confirmed, new, unrelated to media**: a `.charx` import size-check has an operator-precedence bug making the size gate dead code for files with a known positive size — oversized files get fully decompressed into memory before being rejected.

## 4. Tauri Platform Expansion (ARM Linux, Windows ARM, Android)

*Codex verdict: partially confirmed with corrections — see [`CodexReviews/04-tauri-platform-expansion.codexreview.md`](CodexReviews/04-tauri-platform-expansion.codexreview.md).*

**Current state:** shipped targets are Windows x64, macOS (Intel + Apple Silicon — ARM isn't unprecedented here), and Linux x64. No `aarch64-unknown-linux-gnu`, no `aarch64-pc-windows-msvc`, no Android in CI or `tauri.conf.json`. `src-tauri/gen/` has no `android/`/`apple/` subfolder — `tauri android init` has never been run.

**ARM Linux and Windows ARM are low-to-medium effort at the Rust/Tauri layer** — no architecture-gated dependencies found, and the org already has working ARM64 CI experience (the server's Docker image already builds for `linux/arm64` via buildx/QEMU) that can serve as a template.

**The single biggest cross-platform blocker, for all three new targets, is `src-python`** — RisuAI's local/offline GGUF inference backend. It isn't PyO3-embedded; the app downloads a bare CPython interpreter at runtime and shells out to it. That installer (`install_python`, `main.rs:230-246`) is **hardcoded to a Windows-amd64-only URL**. **Corrected — two important fixes here:** (1) Windows-on-ARM does *not* hit a dead `else` branch as originally claimed — `std::env::consts::OS` reports `"windows"` regardless of CPU architecture, so ARM64 Windows actually downloads the amd64 interpreter (whether it then works under x64 emulation is unverified either way); (2) on Linux/macOS, the installer returning `false` isn't a clean silent no-op — the frontend (`local.ts:22-54`) ignores that failure and proceeds into steps with Windows-specific assumptions and `unwrap`/`expect` calls, so the actual observed behavior is closer to an error or a panic than quiet inaction. `llama-cpp-python` itself has no official Android wheels at all, and would need an NDK from-source cross-compile — realistically this feature needs to be explicitly disabled on Android rather than ported.

**The "Android icon in the wrong place" claim is confirmed but more nuanced than a single misplaced folder.** Two unrelated sets exist:
- Orphaned leftovers (`resources/icon-*.png`, `splash*.png`, `capacitor.config.ts`) from a **2024 Capacitor-based Android prototype** that was later fully deleted — these files are dead weight, referenced by nothing, and sit nowhere Tauri looks.
- A Tauri-convention set already staged at `src-tauri/icons/android/mipmap-*/` (**corrected: 15 files, not 20**) — this one is *not* misplaced, and is expected (per Tauri's own documented tooling behavior, though not independently verifiable from this repo since `gen/android` doesn't exist yet) to be picked up automatically once `tauri android init` runs.

The actionable cleanup is deleting/relocating the orphaned Capacitor set, not "fixing" the Tauri-staged one.

**Sequencing constraint (explicit, non-negotiable per project owner):** Android must not be scoped as a standalone "just add the target" task. It is gated behind the RAM/performance rework in §1 — the current architecture (monolithic in-memory DB, no virtual scrolling) will OOM low-RAM Android devices if cross-compiled as-is. This report — and the roadmap below — treat all Android-specific groundwork (icon staging, the `mainx.txt`/`Cargo.toml` mobile-template scaffold from the Tauri V2 migration commit, mobile UI components) as useful context for a later phase, not a current punch list. **Corrected:** the original report's narrative that `mainx.txt` reflects "a prior, incomplete attempt to prepare this project for Tauri mobile" that was "renamed from `main.rs`" is inference beyond what the repository establishes — what's actually confirmed is that it was introduced together with the matching commented-out `Cargo.toml` `[lib]` block in the single Tauri V2 migration commit, in the shape Tauri's mobile template expects, and remains inert today. Its further backstory is unknown.

**Round 2 (deep-dive):** *Codex verdict: partially confirmed with corrections — see [`CodexReviews/04-tauri-platform-expansion-deepdive.codexreview.md`](CodexReviews/04-tauri-platform-expansion-deepdive.codexreview.md).*
- **An actual Android compile failure, confirmed, independent of everything else already found**: `main.rs:582` and `:585` unconditionally register `tauri_plugin_deep_link` and `tauri_plugin_updater` in the builder chain, even though both crates are already excluded for Android/iOS in `Cargo.toml`. Only `single_instance` got the matching `#[cfg(desktop)]` guard — the other two were missed. This is a two-line fix but is a genuine blocker as the code stands today.
- **Four spots conflate `isTauri` with "desktop"** in the app's actual startup path (`bootstrap.ts`): window maximize, fullscreen toggling, the update-checker, and MCP's stdio transport (arbitrary local-process spawning gated only by `isTauri`, fundamentally incompatible with Android's sandbox). **Corrected severity**: only the (awaited) fullscreen call can actually abort `loadData()`'s startup sequence — the update-checker wraps its own failure in a local try/catch and resolves normally (an unnecessary failing call on Android, not a startup-blocker), and the maximize call isn't awaited so its rejection can't be caught by the surrounding try either (an unhandled rejection, not a caught exception). The underlying "these need a desktop-only gate, not a bare `isTauri` one" finding stands regardless of exactly how each one currently fails.
- A concrete mobile-distribution cost: `public/` is 95MB, 77MB of which is tokenizer files (up to 18MB each) fully embedded in the packaged frontend.
- Full sweep of all 11 `#[tauri::command]`s in `main.rs`, including a new one: `post_py_install` hardcodes the `.pth` filename, so it'd silently break if the Python installer's OS/version gating is ever fixed without updating this too.
- Confirmed the Phase 0 `local.ts` fix is in place and is the only caller path to the Rust-side Python-installer commands.

## 5. Multi-Instance / Multi-Writer Conflicts

*Codex verdict: needs-attention → corrected — see [`CodexReviews/topic05/05-multi-instance-conflict.codexreview.md`](CodexReviews/topic05/05-multi-instance-conflict.codexreview.md).* This topic was raised after Phase 0.5 shipped, prompted by the observation that having RisuAI open in multiple tabs/devices/browsers could cause data loss. It is a genuinely new investigation topic, distinct from the single-instance save races fixed in Phase 0/0.5 — this is about **multiple simultaneous writers**, not races within one save loop.

**Confirmed: every writer path this repository's code controls is last-write-wins with no version/lock check.** The self-hosted Node server's `/api/write` (`server/node/server.cjs:1278-1305`) is a bare `fs.writeFile`, no locking, no version check, no atomic rename. Plain-browser IndexedDB (LocalForage) has no coordination beyond the same-browser `BroadcastChannel` guard described below. **Unverified/hub-dependent:** the account-sync cloud backend sends a `x-risu-session`/`x-risu-save-date` header pair and can be told to `reloadSession`, suggesting *some* server-side enforcement — but that logic lives on Risu's remote hub service, outside this repo, so whether it actually prevents cross-device data loss could not be established either way. This is flagged as the single biggest open question blocking any fix design for account-sync specifically.

**Confirmed, and arguably the most important single finding across the whole investigation to date: a one-shot bug, not even requiring a second writer, that silently blanks a user's real remote database.** `src/ts/bootstrap.ts:157-163` — when account-sync's read returns a `303`/`match:false` "your cache is stale" signal, `AccountStorage.getItem` returns `null` (`accountStorage.ts:126-135`), and bootstrap treats any `null` as "no remote database exists yet," immediately writing an *empty* database back over the real one. No retry-with-fresh-body, no distinction between "new account" and "stale local cache." This can fire on an ordinary load, not just a conflict scenario.

**The one existing same-tab protection mechanism is itself a data-loss bug.** The `BroadcastChannel('risu-db')` guard in `saveDb()` (`globalApi.svelte.ts:379-626`) doesn't wait for an actual conflicting write — it force-reloads any other open tab the moment *any* tab completes its very first save cycle, discarding that tab's unsaved in-memory edits with no "save first?" prompt. Opening two tabs "just to compare something," with no overlapping edits at all, is enough to trigger it. It's also silently absent whenever `window.BroadcastChannel` is unsupported, and has a real (if narrow) race window between "tab A posts intent" and "tab B reacts."

**Corrected: the per-character remote-storage mechanism that would reduce blast radius on Tauri/Node-server is opt-in and off by default.** `db.enableRemoteSaving` has no initializer anywhere in the codebase; `disableRemoteSaving()` (`risuSave.ts:24-30`) returns `true` (disabled) whenever it's unset. So out of the box, Tauri and Node-server saves are just as monolithic as account-sync's — every save writes the *entire* database as one blob, meaning any concurrent edit anywhere, even to an unrelated character, risks the whole database being overwritten. Account-sync in particular — the backend most likely used across multiple real devices (phone + laptop) — has no way to opt into finer granularity at all.

**Recovery paths are weak or absent for the backends where a real cross-device conflict can occur.** Tauri's local numbered backups only protect against *that device's own* bad save, since Tauri never sees another device's write. Account-sync web users get **no local backup rotation at all** (`getDbBackups()` explicitly returns `[]` for that case) — the only recovery is the opt-in, off-by-default Risu-Kei 5-minute-interval cloud snapshot, which can itself capture the *already-clobbered* state if its timer fires after an overwrite.

See the full report for four concrete failure scenarios, four sketched (not implemented) design options for a fix — optimistic concurrency via revision/ETag, granular per-chat sync, CRDT-style operation-log merge, and a hard single-writer lock with takeover UI — and a list of remaining open questions (chiefly: what the Risu hub actually enforces server-side for account-sync, which this repository cannot answer).

## Cross-Cutting Observations

- **Plugin ecosystem context** (project owner, not independently investigated here): plugins are widely used, but the developer strongly discourages V2.* plugin installation for security reasons. None of the four investigations found plugin loading itself to be a primary driver of the RAM/persistence/corruption bugs — the bugs are in RisuAI's own core save/render/GC paths — but cold storage's opt-in default is disabled for any user with plugins installed (`database.svelte.ts:713`), meaning plugin users get *less* of the (partial) RAM mitigation that exists today, compounding §1.
- **`AGENTS.md` drift confirmed in two places**: its testing section (fixed elsewhere, not urgent) and its storage-backend description (OPFS listed as active; it's actually dead code per §2 — worth correcting once the roadmap's persistence-reliability phase lands, so the doc describes the *post-fix* state rather than needing a second edit).
- **All five investigations independently converged on the same theme**: RisuAI's core data model treats the entire save file as one always-resident, always-live, rarely-validated blob — this single design decision is the common ancestor of the RAM problem (§1), the silent-save-loss bug (§2), half of the asset-corruption mechanisms (§3, via the boot-time sweep operating on that same always-resident model), and the multi-writer conflict problem's worst-case blast radius (§5, where the same one-blob-per-save model means *any* concurrent edit anywhere can clobber the whole database). Platform expansion (§4) is gated on fixing it. A roadmap that treats these as unrelated bug lists would miss that the highest-leverage work — decomposing the monolithic save blob into independently-addressable pieces — pays off across RAM, persistence, and conflict-safety simultaneously.
