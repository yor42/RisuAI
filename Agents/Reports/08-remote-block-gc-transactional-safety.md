# Remote-Block GC Transactional Safety — Design Feasibility

**STATUS:** reference

Scope note: this report does not re-litigate whether content-addressed remote-block naming (Report 07's recommendation) is the right fix for the original Stage 2-4 corruption bug — that conclusion stands, and its "publish leaf blocks, then commit the already-revision-checked root" ordering claim is re-confirmed by this pass's own reading of `saveDb()`. This report's job is narrower and more mechanical: **size exactly one thing** — the concurrency protocol needed for garbage-collecting superseded, content-addressed remote blocks without racing a concurrent publish — precisely enough that a future implementation attempt (and its Codex adversarial-review cycle) starts from the actual shape of the problem instead of discovering it mid-implementation, which is what happened in the session that produced this report's starting point. **No application code was changed by this investigation; the uncommitted GC implementation that motivated it (`src/ts/bootstrap.ts`, `src/ts/storage/risuSave.ts`, `src/ts/storage/remoteSaveCleanup.ts`) was read as-is and left untouched.** Account-sync is out of scope entirely, per the task's own framing and the permanent hub-access blocker already established in `Agents/Summary.md` §5 and `Agents/Roadmap.md`'s Phase 1.5 Tier B item 6.

## Summary

**The uncommitted Stage 3a GC implementation is unsafe, and the Codex review that says so (`Agents/CodexReviews/tierb-stage3a/tierb-stage3a-round1.codexreview.md`) is correct on direct re-verification of the actual code** — both findings are confirmed below by tracing the exact interleaving against the real, current file contents, not assumed from the review's own summary. The root cause on both backends is the same structural gap Report 07 predicted in its round-3 correction but did not resolve: **liveness is decided from a snapshot (the root pointer as of some earlier read), but the delete is authorized from a check against a different, later-observed fact (the candidate key's own current revision, or a lock that is only held around the leaf write, not the root commit) — and nothing ties the root-commit boundary to the delete boundary.** A revision-conditioned delete answers "has this exact key changed since I looked at it," which is a necessary check but not a sufficient one: it says nothing about whether a *different* key (the root) is about to start referencing this one for the first time.

**Recommendation: do not build automatic GC as a first increment. Ship naming-only (content-addressed blocks, no automatic reclamation) and treat superseded-block cleanup as a separate, deferred, and possibly product-level decision** — either a manual/admin-triggered sweep with a much longer, human-supervised grace window, or accepting unbounded storage growth as a known, quantified tradeoff for now. Of the mechanisms this report sized (Option A: extend `/api/write` to an atomic multi-key write-with-preconditions; Option B: a lease/reservation marker; Option C: a two-version-pointer or dirty-tracking-deferral scheme), **Option A is the mechanism this report recommends pursuing if GC is ever built, but — [Corrected — Codex round 1, see `Agents/CodexReviews/topic08/08-remote-block-gc-transactional-safety.codexreview.md`] — the version below overstated how close to "verifiably complete" its own sketch was.** Two further gaps were found on review, both requiring MORE server/protocol work than originally scoped, not less: (1) Option A's own safety argument assumed GC could hold a server-side lock across multiple separate client-orchestrated requests (`/api/read`, a local decode, then `/api/remove`) — that isn't how any lock in this codebase works; a lock lives inside one handler's single request/response cycle, so Option A as file-by-file-scoped below does not actually supply the atomic capability its own safety proof depends on, and needs a genuinely new single-endpoint primitive instead (detailed in Option A's own corrected section). (2) The Tauri analysis originally claimed a widened writer-side lock alone was sufficient, reasoning that same-process execution prevents a decision from going stale — that reasoning is wrong; GC's decision is still made asynchronously, before any lock is touched, and a writer's entire publish-through-commit sequence can complete between that decision and GC's later lock acquisition, same bug, same shape, just re-derived independently by this report instead of copied from the original bug (see the Tauri section's own correction). Both gaps, once fixed, make Option A **larger** than this report's own round-1 estimate, not smaller — reinforcing, not undermining, the "do not build automatic GC as a first increment" recommendation, which does not change.

**[Corrected — Codex round 2, see `Agents/CodexReviews/topic08/08-remote-block-gc-transactional-safety-round2.codexreview.md`.]** Round 2 found a THIRD ordering the round-1-corrected Node-server design (a cross-key revision precondition on `/api/remove`) still does not close, and — this is the important, structural part — **cannot be made to close by refining that same kind of precondition further, no matter how it's captured.** A writer's publish of a remote block and its later commit of the root referencing it are two genuinely separate operations; once the publish has fully completed, nothing observable anywhere in the system indicates that a commit is imminent, so no revision-snapshot-based check (taken at any time, by any method) can distinguish that state from a truly orphaned, safe-to-delete block. Closing this with certainty requires merging publish and commit into one atomic multi-key write on the Node-server side — a materially larger change than the cross-key-precondition design, which now has to be understood as *risk reduction layered on top of the existing grace period's practical time margin*, not as a mechanism that makes the grace period's role in correctness unnecessary. **The Tauri fix is not affected by this limitation and closes its analogous race completely** — its lock is a single global mutex (not per-key), so a writer holding it across its entire publish-through-commit sequence genuinely cannot release it partway through, which is exactly the atomicity property the Node-server side is missing and cannot cheaply obtain (see the Tauri section's own note on why this asymmetry exists and is unavoidable, not an oversight). None of this changes the report's bottom-line recommendation — if anything, discovering that even the corrected "real fix" for Node-server has an inherent, only-partially-closeable limit is a stronger reason to not build automatic GC as a first increment than round 1's finding alone was.

**[Corrected — Codex round 3, see `Agents/CodexReviews/topic08/08-remote-block-gc-transactional-safety-round3.codexreview.md`.]** Round 2's own "the grace period bounds the residual risk in practice" claim was itself wrong as stated. It implicitly assumed the risk window is bounded by how long a SINGLE save's publish-to-commit gap can realistically stay open (genuinely short, absent a crash) — but the actual risk window for a **republish of previously-orphaned content** is bounded by how stale that block's `.meta` file already happens to be, which has nothing to do with the current save's timing at all: verified against the actual current code, `encodeRemoteBlock()` never refreshes a candidate's `.meta` timestamp on publish, only GC's own sweep ever writes one. So a block that was orphaned and aged past the grace threshold in some earlier, unrelated episode is immediately vulnerable the moment it's legitimately republished — no crash, no suspended tab, no unusual delay needed at all, just an ordinary GC sweep running moments after an ordinary revert-to-previous-content save. Restoring the grace period's intended protection requires one more piece this report failed to carry forward from Report 07's own round-2 correction: publishing (including republishing) must also refresh/create the candidate's `.meta` timestamp, so a republish always needs a genuinely full grace period to elapse (after that specific republish) before becoming delete-eligible again. **This is now understood to be a required part of Option A for Node-server, not an independent nice-to-have** — see the corrected reasoning in the "Option A" section below. Tauri's correctness, by contrast, does not depend on grace-period timing at all (its fix comes from the lock's atomicity, not from timestamp freshness) — see the Tauri section's own note on this further asymmetry. Recommendation unchanged; if anything, this is a third consecutive round finding the "real fix" needs more machinery than the round before it estimated, which is itself useful evidence for how large and easy-to-underestimate this undertaking actually is.

**[Corrected — Codex rounds 4 and 5, see `Agents/CodexReviews/topic08/08-remote-block-gc-transactional-safety-round4.codexreview.md` and `-round5.codexreview.md`.]** Two more consecutive rounds, each closing the previous round's gap and each finding a new one underneath it. Round 4: meta-refresh-on-publish (round 3) does nothing unless GC's delete request actually re-checks `.meta`'s own revision at delete time, not just K's and root's — otherwise a republish that refreshes `.meta` but (via `skipRemoteSaving`) never touches K's own bytes leaves GC's stale eligibility decision undetected. Fixed by adding `.meta`'s revision as a third check-only precondition, alongside K and root, all captured from one shared decision-time snapshot. Round 5: even the three-way precondition set doesn't help if K's own write and `.meta`'s refresh are two separate operations with a gap between them — a GC sweep that lands entirely inside that gap sees a fully self-consistent (if stale) picture from every angle it checks, because the writer's later steps (meta-refresh, root-commit) genuinely haven't happened yet at either the decision or the delete moment. Fixed not with a fourth precondition key but by reordering the writer's own steps: `.meta` must be refreshed *first*, awaited, before K's own write/reassertion and before root commit — this closes the gap by construction (any GC sweep landing after a writer has started at all now sees a fresh `.meta` and correctly declines to even attempt a delete), the same structural principle as the Tauri fix, rather than by chasing an ever-longer precondition list. **Five correction rounds on a report whose job is to size, not implement, a fix is itself a data point**: this is a harder problem to get right on paper than it looks, which is exactly the kind of thing this report exists to surface before a real implementation attempt, not after. Recommendation unchanged throughout — do not build automatic GC as a first increment.

## Verified background

### The Node-server GC path, traced against the actual current code

- `src/ts/bootstrap.ts:667-759` (non-Tauri branch of `cleanChunks()`): for each `remotes/*` key, liveness is computed via `isRemoteSaveFileLive()` (`src/ts/storage/remoteSaveCleanup.ts:54-72`) against `remotePointers` — a `Map` populated by `decodeRemotePointers()` (`src/ts/storage/risuSave.ts:970-991`), which itself is a **fresh, independent read+decode of `database/database.bin` taken once, at the very top of this `cleanChunks()` invocation** (`bootstrap.ts:579-589`). This is the "earlier database.bin snapshot" the Codex review refers to.
  - If `isLive` is false, `bootstrap.ts:694-713` checks a `.meta` companion file's `lastUsed` timestamp against a 7-day grace window (`remoteSaveCleanupGraceMs`, `remoteSaveCleanup.ts:2`) and sets `okayToDelete = true` only if that grace period has elapsed.
  - If `okayToDelete`, `bootstrap.ts:736-738` does exactly this, verified verbatim:
    ```ts
    await forageStorage.getItem(asset)
    await forageStorage.removeItem(asset)
    ```
    `forageStorage.getItem()` (`src/ts/storage/nodeStorage.ts:133-159`) issues `GET /api/read`, which — under the server's own per-key `withFileWriteLock` (`server.cjs:1347-1353`) — returns the *candidate key's own current revision* in the `x-risu-revision` header and caches it into `NodeStorage.knownRevisions` (`nodeStorage.ts:146-152`). `forageStorage.removeItem()` (`nodeStorage.ts:177-243`) then issues `GET /api/remove` presenting that just-observed revision as `if-match-revision` (`nodeStorage.ts:194-197, 202`).
  - **This is the exact gap.** The `isLive` decision was made from the root snapshot read at the top of the sweep. The revision presented to `/api/remove` is re-observed *after* that decision, specifically about the candidate key, immediately before delete. If a writer publishes (or idempotently republishes — same content, same content-addressed key, a routine and expected occurrence per Report 07 §"Atomic root-referencing") that exact key in the window between the sweep's root snapshot and this `getItem()`/`removeItem()` pair, `getItem()` observes the writer's own fresh revision as "current," and `/api/remove`'s server-side check (`server.cjs:1452-1469`) — which only compares the *presented* revision against the *candidate key's own* current revision, nothing about the root — passes. The delete proceeds, exactly as the writer's not-yet-committed root is about to start referencing that same key. The candidate-key revision-CAS mechanism has no way to know or care that a *different* key (the root) is mid-flight toward referencing this one; it only proves "nobody touched this key since I, GC, last looked at it *right now*," which is trivially true immediately after a republish. This confirms the Codex review's `bootstrap.ts:714-738` finding is accurate against the code as it stands (line numbers shifted slightly in the current tree from the review's `714-738` citation to `736-738` for the actual `getItem`/`removeItem` pair, but the mechanism and the bug are identical).

- **`/api/write` is single-key only — verified directly.** `server.cjs:1582-1712` (`app.post('/api/write', ...)`) reads exactly one `req.headers['file-path']` (`server.cjs:1586`), acquires exactly one `withFileWriteLock(filePath, ...)` (`server.cjs:1613`), and validates exactly one `if-match-revision` header value against exactly one key's current revision (`server.cjs:1636-1647`). There is no batch/array form anywhere in this handler — confirmed by reading the handler in full, not inferred from its shape. This is a real, structural asymmetry with `/api/remove`, which — confirmed by reading `server.cjs:1366-1563` in full — already accepts a `$$`-joined multi-key `file-path` header, a correspondingly `$$`-joined `if-match-revision` header (one segment per key, empty segment meaning "no precondition for this key," `server.cjs:1374-1431`), and commits the whole batch atomically via `withFileWriteLocks()` (sorted-key nested locking, `server.cjs:147-156`) wrapping a single `withRevisionTransaction()` call that validates every key's precondition before mutating any of them (`server.cjs:1441-1531`). **The multi-key locking and multi-key precondition-checking machinery already exists and is already battle-tested (this is the same code Tier B Stage 1 round 4 hardened into true all-or-nothing batch semantics, per `Agents/Roadmap.md`'s Stage 1 entry) — it exists on the delete path, not the write path.** This matters directly for Option A below: extending it to writes is reusing an established, already-reviewed pattern, not inventing a new one, but it is still new *code*, in a handler (`/api/write`) that has never had to reason about more than one key.

- **`withFileWriteLock`/`withFileWriteLocks`/`withRevisionTransaction`, what they can and cannot already do** (`server.cjs:63-156`, read in full):
  - `withFileWriteLock(key, fn)` is a per-key, in-process `Promise`-chained critical section (a `Map<string, Promise>`, `server.cjs:112`) — it serializes any two operations that both name the same key, in submission order, but does **not** by itself provide any cross-key coordination; two operations on different keys run fully concurrently under it.
  - `withFileWriteLocks(keys, fn)` (`server.cjs:147-156`) acquires a **set** of per-key locks by recursively nesting `withFileWriteLock` calls in sorted-key order (`server.cjs:148`), which is what makes it deadlock-free against another batch request that shares some but not all of the same keys in a different order — `fn` only runs once every key's lock in the set is held, and none release until `fn` returns. This is exactly the primitive that would need to be reused, not reinvented, for a multi-key write-with-preconditions (Option A).
  - `withRevisionTransaction(fn)` (`server.cjs:98-102`) is a **separate, coarser, fully global** queue (not per-key) that only the actual revision-map read→validate→mutate→persist sequence runs inside — not the file I/O itself. Its purpose (per its own comment, `server.cjs:86-96`) is narrower than `withFileWriteLock`: it exists so that one request's in-memory revision bump can never be durably persisted to `__revisions.json` by a *different*, concurrently-queued request's own `saveRevisions()` call before the first request's own rollback-on-failure logic has had a chance to run. It does not provide cross-key liveness guarantees either — it protects the integrity of the revision *store itself* under concurrent global writes, which is an orthogonal concern to "does key A's existence get atomically verified alongside key B's write."
  - **Conclusion verified directly from the code, not assumed**: nothing in this file today can express "commit this write to key A, but only if keys B and C currently exist, and hold all three keys' locks for the duration so nothing about B or C can change in between." `withFileWriteLocks` gets 90% of the mechanical shape needed (multi-key locking, all-or-nothing), but it is wired today exclusively into the batch-*delete* path (`/api/remove`), not into any write-with-side-precondition shape. Building that shape for `/api/write` is new route logic reusing an existing locking primitive, not a novel concurrency-control mechanism from scratch — which is the main reason Option A below is smaller than it might first appear, while still being real, non-trivial, adversarially-reviewable work.

### The Tauri GC path, traced against the actual current code

- `src/ts/storage/risuSave.ts:69-74` (`withRemoteBlockGcLock`): a plain in-process `Promise`-chained mutex, identical in shape to `server.cjs`'s `withFileWriteLock` but scoped to a single Tauri process (no cross-process or cross-device concern — Report 05/07 both already established Tauri isn't a multi-writer backend the way Node-server/account-sync are).
- **The writer's lock scope** — `risuSave.ts:538-556` (`encodeRemoteBlock()`): the lock is acquired only around `mkdir` + `writeFile` for the one remote-block file (`risuSave.ts:546-551`). It is released as soon as that single leaf write returns.
- **The root commit happens later, under a different lock entirely.** `saveDb()`'s actual sequence (`src/ts/globalApi.svelte.ts:748-780`, re-confirmed by direct read matching Report 07's own trace): `encoder.set(db, toSave)` (line 748) — which is what triggers `encodeRemoteBlock()` and therefore acquires-and-releases `withRemoteBlockGcLock` — returns fully *before* `saveDb()` reaches its own root-commit write. The root write itself (`writeFile('database/database.bin', ...)`, line 776 under Tauri) is instead guarded by `dbWriteLock` (`globalApi.svelte.ts:417`, acquired at line 773), an entirely separate `AsyncMutex` whose actual purpose — confirmed by its own doc comment and by Phase 1 item 4's roadmap entry — is same-process mutual exclusion against this tab's own `loadDrive()` restore path, unrelated to GC.
- **GC's delete step** — `bootstrap.ts:646-658`: acquires `withRemoteBlockGcLock` around the delete only, same lock the writer briefly held around its own leaf write.
- **This confirms the Codex review's `risuSave.ts:538-551` finding exactly.** The interleaving the review describes is directly reproducible from this trace: encoder writes key K under the lock and releases it (`risuSave.ts:546-551` returns) → GC, having already decided (from its own earlier root read, same structural pattern as the Node-server case) that K is superseded, acquires the now-free lock and deletes K → `saveDb()` only *then* reaches its root commit (line 776) and writes a root that references the now-deleted K. Widening `withRemoteBlockGcLock`'s acquisition window on the writer's side to also cover the eventual root commit is the natural fix shape, but as implemented today the lock simply does not span that far — it is scoped to the single leaf write, exactly as the review says, not to "directory creation/listing" as the code's own comment implies is the closed gap (the comment describes the wrong boundary; the actual boundary that matters is leaf-write-through-root-commit, not leaf-write-through-mkdir).

### What Report 07 already established that still holds

- `saveDb()`'s write ordering — publish leaf/remote blocks first via `encoder.set()`, then commit the one revision-checked root write — is unchanged and still correct as an ordering fact; re-verified directly above (`globalApi.svelte.ts:748-780`). The bug is not in this ordering; it's that nothing observes the *gap* between the two steps as a unit.
- Report 07's round-3 correction already predicted, in the abstract, that a "decide from one read, execute later with no re-validation" structure is unsafe and that closing it needs Stage-1-grade interleaving analysis and stress testing. This report's job was to verify that prediction was not just correct in the abstract but is *exactly* the bug in the actual uncommitted code (it is, per the two traces above), and then to size the fix concretely rather than restate the prediction again.

## Candidate mechanisms

### Option A: cross-key revision precondition on `/api/remove` **[Corrected — Codex round 1: originally titled "extend `/api/write` to an atomic multi-key write-with-preconditions" — that shape didn't work, see below]**

**Concept (corrected):** GC's *delete* of a superseded remote-block key is made conditional not only on that key's own revision (as today's unsafe implementation already checks) but ALSO on the root key's (`database/database.bin`) revision matching what GC observed when it decided the candidate was dead. Both preconditions are validated atomically, under both keys' locks together, inside `/api/remove` — which already has exactly this multi-key locking/precondition shape for the keys it deletes (`withFileWriteLocks`, sorted, all-or-nothing); this just adds one more key to the precondition-checking loop that is checked but never deleted. Nothing about `/api/write` needs to change at all under this design — the original draft's plan to make the root's *write* itself a multi-key operation with existence-preconditions was the part that didn't hold up (see the file-by-file section below for why, and what replaces it).

**File-by-file:**

- **`server/node/server.cjs`**: `/api/remove` needs a small, optional extension — two new `$$`-joined headers (e.g. `check-only-path`, `check-only-revision`, positionally aligned, mirroring the existing `file-path`/`if-match-revision` convention exactly) naming extra keys to fold into the SAME `withFileWriteLocks` lock set and the SAME precondition-validation loop as the keys actually being deleted, but excluded from the final `fs.rm()` loop. No new status code needed — a mismatch on a check-only key's revision is the same kind of failure as a mismatch on a to-be-deleted key's revision, so it can reuse the EXISTING 409 "Revision conflict" response shape (`server.cjs:1552-1559`) unchanged, just reporting which key (possibly a check-only one) failed. Back-compat: omitting the new headers preserves every current caller's behavior exactly. `/api/write` is untouched by this design.
- **`src/ts/storage/nodeStorage.ts`**: `removeItem()` needs an optional parameter (e.g. `checkOnly: {key: string, revision: number}[]`) threaded through to the two new headers. No new error TYPE is needed — a check-only-key mismatch surfaces through the exact same `NodeStorageConflictError` path `removeItem()` already throws on any 409 (`nodeStorage.ts:229-232`), since from the caller's perspective both cases mean the same thing: "the precondition I presented no longer holds, don't proceed, re-evaluate."
- **`src/ts/bootstrap.ts`, GC side — [Corrected — Codex round 1: the original text here claimed GC could "hold a lock" across multiple separate client-orchestrated requests (an earlier `/api/read`, a local decode, then a later `/api/remove`). Codex's review correctly pointed out that isn't how any lock in this codebase works — a lock exists only inside one handler's single request/response cycle, never held open across separate HTTP round trips. No cross-request lock-holding is needed under the corrected design above. Corrected further — Codex round 4: the checkOnly precondition set needs a THIRD entry, not just the root — see below]**: `cleanChunks()`'s non-Tauri branch needs to remember, as ONE shared decision-time snapshot — not observed piecemeal, not refreshed for any single one of them later — the root's revision, the candidate key's (K's) own revision, AND its `.meta` file's revision, all captured together at the moment GC reads `.meta` and decides K is eligible for deletion. All three are then presented on the later, single `removeItem()` call: K as the key actually being deleted (`if-match-revision`), root and `.meta` as `checkOnly` preconditions. This is ordinary client-side state (three remembered numbers), presented later on a single, separate, atomic request, the same way `NodeStorage.knownRevisions` already works for every other revision check in this codebase — the round-4 correction below explains why `.meta`'s revision specifically must be included, not just root's.

**Does this actually close the race — traced against Codex's counterexamples, not asserted:**
  - *Codex's Tauri-analog counterexample, applied here ("writer's full publish-then-commit sequence completes entirely, THEN GC's stale decision executes")*: GC observed root at revision R0, decided K dead. Writer publishes K, then commits a new root (R0→R1, now referencing K) — an ordinary, already-existing `/api/write` call, unaffected by anything in this design. GC's delete-of-K request arrives after: presents `check-only-revision` = R0 for the root. Server's precondition check: is root's CURRENT revision (R1) still R0? No → reject the whole request, K is never deleted. **Closes this interleaving.**
  - *"GC arrives at the lock set first"*: GC's delete-of-K request acquires [K, root] locks before the writer's own publish-of-K request reaches K's lock. Root is still R0 (writer hasn't committed yet) → GC's precondition passes → K is deleted, both locks release. The writer's publish-of-K request (blocked on K's lock this whole time) now proceeds and recreates K, then commits its root referencing the just-recreated K — succeeds normally. **Closes this interleaving.**

**[Corrected — Codex round 2: a third ordering survives both fixes above, and no revision-precondition design — however the values are captured — can close it. This is a genuine limit of this whole mechanism class, not a fixable oversight, and materially changes what "Option A closes the race" can honestly mean.]** Codex's round-2 review found: (1) writer publishes K via its own, separate `/api/write` call and that call **fully completes and releases K's lock** — K now has a fresh revision, entirely independent of the root; (2) *before* the writer's separate root-commit request is even sent, GC's delete-of-K request acquires [K, root]; (3) the root precondition passes (root genuinely hasn't moved — the writer hasn't reached that step yet); (4) if GC's presented K-revision is freshly re-observed (this report's original round-1-corrected design), it also matches (nothing else has touched K since the writer's publish completed) — both preconditions pass, K is deleted; (5) the writer's *separate*, later root-commit request now proceeds and succeeds, referencing a K that no longer exists. **The writer does not republish K in this ordering — its publish already fully succeeded before GC ever acted — so K's own per-key lock (which is what closed the previous ordering) never forces a "recreate K" step here at all.**

The natural next fix — present K's revision *as captured atomically alongside the root snapshot*, never re-observed fresher than that, so a completed-but-not-yet-committed-against publish would show up as a K-revision mismatch too — does not close this either, and it's important to be precise about why: even a perfectly atomic, perfectly consistent {root, K} snapshot, taken at literally the same instant, can only ever describe the OBSERVABLE state that exists at that instant. A writer that has already finished publishing K (an ordinary, fully-committed write to K, no different in kind from any other write to K) by the time that snapshot is taken leaves **no observable trace anywhere in the system** that says "a root-commit referencing this key is imminent" — that fact exists only in the writer's own in-flight, not-yet-executed next step, which is invisible to any observer until the writer actually sends that request. No amount of tightening *when* GC reads K's revision relative to the root's can manufacture information that doesn't exist yet. This is a structural property of "publish" and "commit" being two genuinely separate operations from any outside observer's point of view, not an implementation gap in how the precondition is captured.

**What would actually close this with certainty**: merging "publish K" and "commit the root referencing K" into a single atomic multi-key write — the *writer's own* two steps, not just GC's read, would need to become one indivisible operation (extending `/api/write`, not `/api/remove`, to a genuine multi-key atomic write mode — the shape this report's original, now-abandoned round-1 draft was reaching for, for a different, insufficient reason). This removes the intermediate "published but not yet committed" state from ever being externally observable at all, which is the only way to make the absence of that state something GC can reliably infer. This is a substantially larger change than the cross-key-precondition design above — it means `saveDb()`'s fundamental "publish leaf blocks, then separately commit the revision-checked root" sequencing (re-confirmed correct as an *ordering* fact by this report and Report 07 both) would need to become one single locked operation spanning both steps, for every save that touches a remote-eligible character.
  - **New persisted state**: none beyond the existing revision store, for the cross-key-precondition design above. The atomic-multi-key-write alternative also needs none beyond what already exists, but is real, new route logic on `/api/write` (unlike the precondition design, which only touches `/api/remove`).
  - **Does it change the wire contract?** The cross-key-precondition design: yes, additively (`/api/remove` gains two new optional headers; `/api/write` unchanged). The atomic-multi-key-write alternative: yes, additively too, but on `/api/write` instead, and is a materially larger change to that handler's shape.
  - **Does either actually close the race, in full?** The cross-key-precondition design **closes two of the three orderings that matter, but not the third** (a writer's publish that has already fully committed before GC acts, with that writer's own root-commit still pending) — this is a real, permanent limitation of that design, not a bug to patch further. Only the atomic-multi-key-write alternative closes all three, and does so by construction (no intermediate state to observe) rather than by a precondition check.

**[Corrected — Codex round 3]** If the project owner accepts the third ordering as a practical (grace-period-bounded), not mathematically-proven, risk — the cheaper of the two paths — **one more piece is required for that acceptance to actually be true, and this report initially missed it**: `encodeRemoteBlock()` must refresh (or create) a candidate's `.meta` liveness timestamp as part of publishing, including republishing an already-existing hash. Verified directly against the current uncommitted code: it does not do this today — `.meta` files are written only by GC's own sweep, never by a publish. Without this, a block that was orphaned and aged past the grace threshold in some earlier, unrelated episode is immediately vulnerable to the third ordering the moment it's legitimately republished — no crash or unusual delay needed, just an ordinary GC sweep running shortly after an ordinary revert-to-previous-content save, which is a realistic occurrence, not a rare edge case. With meta-refresh-on-publish in place, every candidate — new or republished — needs a genuine, full grace period elapsed *since its own most recent publish* before GC would even attempt to delete it, which is what actually makes "requires an extraordinary failure" a true statement rather than an unverified assumption. This is now considered a required part of the cross-key-precondition design for Node-server, not an independent, skippable hardening step.

**One further implementation-level nuance worth flagging for whoever builds this, found by this report's own author while sizing the fix, not by a review round**: `encodeRemoteBlock()`'s existing `skipRemoteSaving`/`checkedRemoteExistence` optimization (used during the boot-time `init()` full re-encode pass, defaulting to `true`) can skip the actual byte-write entirely when the target hash-named file already exists — a legitimate, harmless optimization, since the content would be identical either way. If meta-refresh is implemented naively, gated behind the same "did an actual write happen" condition, this optimization would ALSO silently skip the meta-refresh for a hash that's being re-asserted as this character's current pointer but whose underlying file happened to already exist — reopening the exact gap this correction exists to close, specifically for the `init()`/full-reload path. **Meta-refresh must run whenever `encodeRemoteBlock()` is invoked for a given hash (i.e., whenever the caller is asserting "this hash is this character's current pointer"), independent of whether the underlying byte-write itself was skipped as an optimization.**

**[Corrected — Codex round 4: meta-refresh-on-publish alone is still not sufficient, for a precise, narrow reason — the delete-time precondition check never actually validates meta's freshness, only K's and root's revisions.]** Codex traced: GC reads `.meta` at decision time, sees it expired, decides K is eligible. A writer then republishes K — which, per the fix above, refreshes `.meta`'s revision — but if `skipRemoteSaving` also applies (the underlying bytes are unchanged, so the byte-write itself is skipped), **K's own revision never moves at all**, only meta's does. GC's delete-with-precondition request — as designed through round 3 — only conditions on K's revision and root's revision, neither of which changed. The precondition passes; K is deleted using an eligibility decision that was already invalidated by the time the delete executed, and the writer's subsequent root-commit references a now-missing K. Refreshing `.meta` accomplishes nothing if the thing that's supposed to consult it at the moment of truth never actually re-checks it.

**The fix: `.meta` must become a third check-only precondition key, alongside K and root, using the exact same multi-key mechanism already proposed** — `.meta` is an ordinary file, already tracked in the server's `revisions` map like any other key (writing it via `/api/write` already bumps its revision automatically, no new server capability needed), so this is purely a matter of GC presenting one more `check-only-path`/`check-only-revision` pair on the same `/api/remove` request, not a new kind of primitive. **Critically, and this is the part that actually closes the gap**: all three revisions GC presents (K's, root's, and now `.meta`'s) must come from the SAME decision-time snapshot — captured together, when GC reads `.meta` and decides eligibility — and never re-observed fresher for any one of them individually before the delete request is sent. (This retroactively confirms and generalizes what round 2 already established about K's own revision needing to be decision-time-captured, not freshly re-observed — round 3's meta-refresh fix reintroduced a version of the same mistake by only protecting meta's *content*, not wiring its *revision* into the precondition set GC's delete actually checks.) With this in place: any writer activity that touches K at all — whether or not it rewrites K's own bytes, thanks to the mandatory unconditional meta-refresh — bumps at least one of the three preconditioned revisions, and GC's stale decision is correctly rejected regardless of which of the three actually moved.

**[Corrected — Codex round 5: the three-way precondition set correctly closes round 4's ordering, but a FOURTH ordering survives it, and closing that one needs a change to the WRITER's own step ordering, not another precondition key.]** K's write (or its `skipRemoteSaving`-gated no-op determination) and `.meta`'s refresh are two separate operations — nothing in the round-4 design specifies which happens first, or requires the first to be durably complete before the second begins. Codex traced: if the writer performs step "touch K" before step "refresh `.meta`" (the natural order to write, given meta-refresh reads as a follow-up to publishing), there is a real gap between them. If GC's ENTIRE decide-and-delete operation — both its decision-time snapshot reads AND its actual delete-with-precondition request, server-side lock acquisition and all — completes inside that gap (after "touch K," before "refresh `.meta`"), then every value GC observes is, from GC's own point of view, entirely self-consistent and unchanged from decision time to delete time: `.meta` genuinely still shows its old, expired state (the refresh hasn't happened yet), and K/root are whatever they were. The three-way precondition set correctly validates "nothing changed between my decision and my delete" — but everything relevant to the writer's true intent (refreshed `.meta`, about-to-be-committed root) simply hadn't happened yet at either point GC looked. GC deletes K; the writer's `.meta` refresh then runs (pointless — K is already gone) and the writer commits a root referencing the now-missing K.

**The fix: order the writer's own steps so that touching `.meta` happens FIRST, and is durably complete, before K's own write/reassertion, which itself happens before the root commit** — not merely "run meta-refresh unconditionally whenever `encodeRemoteBlock()` is invoked" (round 3's fix, correct in that it must always happen, but silent on *when* relative to K's own write). With this reordering: the *only* way GC can observe an expired `.meta` for a candidate is if no writer has begun touching it at all yet — the moment any writer starts this sequence, `.meta` is the very first thing that changes, before anything else about that candidate becomes observably different. GC's decision itself (not just its later precondition check) is gated on reading `.meta` first, so a GC sweep that lands at any point once a writer has started is guaranteed to see a fresh `.meta` and correctly decide "not eligible," never even reaching the delete-attempt code path — closing the gap by construction, the same way the Tauri fix closes its analogous gap by construction rather than by an ever-growing precondition list. A crash after the meta-refresh but before K's write/root-commit only ever makes reclamation more conservative (a `.meta`-refreshed-but-not-actually-live candidate looks falsely "recently used" and survives an extra grace period before GC reconsiders it) — never less safe.

**Assessment (revised) — [Corrected — Codex round 3: the "the grace period bounds the residual risk" claim immediately below was itself wrong as originally stated. See the correction that follows it.]** neither sized mechanism gets to a place where "GC never deletes something a legitimate writer is about to reference" is true with certainty, without also either (a) accepting the atomic-multi-key-write redesign's much larger scope, or (b) leaning on the grace period — but (b) only actually works if one more piece is added, and this report's round-2 draft claimed it worked without checking that piece was present.

**[Corrected — Codex round 3]** The round-2 draft argued the residual ordering is "safe in practice" because a writer's publish-to-commit gap would need to span the entire multi-day grace window, which would require an extraordinary failure (a crashed/never-resumed client). **This reasoning is wrong for a specific, realistic, and far more common case: a republish of content that hashes to an ALREADY-existing key, whose `.meta` file is already aged past the grace threshold from a PRIOR, unrelated orphaning episode.** Verified directly against the actual current (uncommitted) code: `encodeRemoteBlock()` (`risuSave.ts:538-554`) never touches a candidate's `.meta` file at all — publishing (or republishing) a block only ever writes the block's own content and bumps its own revision; the `.meta` timestamp is written ONLY by GC's own sweep (`bootstrap.ts:696-711`), and only when GC first discovers an unreferenced candidate with no existing meta, or reads an existing one to check its age. So: if K was previously orphaned and its `.meta` already aged past seven days (from whenever GC first noticed it, unrelated to anything happening now), and a writer later republishes identical content that happens to hash to that same K (a realistic revert-to-previous-content scenario, not a rare edge case), GC can classify K as delete-eligible using that ALREADY-STALE metadata **immediately** — no waiting required, no crash required, just an ordinary GC sweep running moments after an ordinary republish. The relevant "age" the grace period checks is the meta file's age, not "how long has this specific save's publish-to-commit gap been open" — and those are only the same thing for a genuinely brand-new hash that has never existed before (which DOES need a real GC "discovery" pass — a `create-meta` action, not a delete — before it can even become a delete candidate, correctly bounding that case to a real multi-day window). A republished, previously-orphaned hash has no such protection.

**What actually restores the grace period's role as real practical protection**: publishing (including republishing/reusing an existing hash) must ALSO refresh or create the candidate's `.meta` `lastUsed` timestamp as part of the publish step itself — this is not a new idea; it is Report 07's own round-2 correction, which this report's author had already implemented an understanding of during the original (reverted) Stage 3a attempt, and which this report's round-2 draft incorrectly treated as superseded by the revision-based precondition mechanism rather than complementary to it. With meta-refresh-on-publish restored: every candidate, whether brand-new or a republish, needs a full, continuous grace period of being unreferenced *since its own most recent publish* before GC would even attempt a delete — which genuinely does require an extraordinary gap (a save that starts, publishes, and then doesn't commit its root for multiple days) to be exploitable, restoring the "practically safe, not crash-required" framing the round-2 draft asserted without this piece in place. **The cross-key-precondition design and meta-refresh-on-publish are both required together** — the precondition check closes the narrower, shorter-window concurrent-observation races (a concurrent GC sweep, a writer that raced GC and lost the lock); meta-refresh-on-publish is what makes the grace period's own timing assumption actually hold for a republish, which the precondition check alone does nothing to ensure. Neither substitutes for the other, and this report's round-2 draft only accounted for the first.

This report's original framing ("Option A is the only mechanism that actually, verifiably closes the race") was corrected once (round 2) to "closes 2 of 3 orderings, relies on the grace period for the third" and must be corrected again here: it relies on the grace period **plus meta-refresh-on-publish**, a concrete additional piece of required machinery this report failed to carry over from Report 07 into its own risk calibration until this round. Whoever scopes a future implementation must treat meta-refresh-on-publish as a non-optional part of Option A, not an independent nice-to-have.

### Option B: lease/reservation mechanism

**Concept:** a remote block, once published, gets a short-lived server-side "protected" marker independent of the `.meta`/grace-period heuristic, which GC must honor even if root-liveness looks stale.

**Sizing against the failure modes the task calls out:**

- **How long must the lease last?** It must cover "publish finished" to "root committed" — but that interval has no fixed upper bound. `saveDb()`'s retry loop can re-attempt a root write multiple times (on a `409` from a genuine conflict, or on a generic I/O failure) before succeeding, and a slow network, a backgrounded tab, or a suspended process could stretch this arbitrarily. A lease with a fixed short TTL (seconds) risks expiring mid-retry-loop and reopening the exact race it exists to close, just with lower probability instead of zero.
- **What if the client crashes mid-save, after publish but before commit?** The lease is never explicitly released. It needs its own expiry to avoid permanently protecting an orphaned block forever (which would defeat GC's whole purpose) — but an expired-but-never-committed lease is functionally identical to today's `.meta`/grace-period timestamp: a heuristic staleness signal, not a correctness guarantee. **This reproduces the exact unresolved problem Report 07's round-3 correction already identified for the timestamp/grace-period design** — a lease is a renamed grace-period timestamp with a shorter default window, not a structurally different mechanism. It narrows the race's probability (shorter window between "safe" and "unsafe" classification) but does not close it, because the underlying gap (decide-then-execute with no re-validation against what changed in between) is unchanged; a GC sweep that reads an expired lease and a stale root snapshot in the same sweep can still delete a block whose root commit is in flight but hasn't landed yet, for exactly the same reason as today's code.
- **Verdict: does not actually close the race**, for the same structural reason Option A's "must move the decision inside the lock" requirement exists — a lease is a data point GC reads at decision time, not a thing that prevents the decision from being made from stale data in the first place, unless the lease acquisition and the delete are themselves serialized against the writer's own commit under a shared lock — at which point it has converged into a differently-named version of Option A's locking requirement, without Option A's actual precondition-verification step. Not recommended as a standalone mechanism; if it's built at all, it should be built as Option A's lock-acquisition step, not as an independent timestamp-with-TTL scheme.

### Option C: other mechanisms

**C1 — two-phase directory entry naming both the previous and the new remote-block version, until a follow-up confirms durable commit.** Concretely: the root's `REMOTE` pointer for a character would, for one save cycle, carry both `hash` (the new version) and `prevHash` (the version it's replacing) — GC treats a block as live if it's referenced as *either* `hash` or `prevHash` by the current root, and a block only becomes eligible for the grace-period check once neither field of the current root's pointer for that character names it. This changes what "the root currently references" means (a small pointer-payload format bump, similar in shape to the `v:2` bump Report 07 already made) rather than adding a new lock. It genuinely narrows the race's exposure — a block that GC would have wrongly deleted mid-commit is instead recognized as "still the fallback the *previous* commit's readers depend on," so it survives at least one more full grace-period cycle — but it does **not** close the specific race Codex found, which is about a block that has never yet been the root's `hash` OR `prevHash` at all (the writer publishes a brand-new hash, and GC's stale root snapshot predates that write entirely, so neither field names it yet). This mechanism protects *already-referenced* versions from being reclaimed too eagerly; it does nothing for a version that hasn't been referenced by any committed root yet, which is precisely the case in Codex's finding. **Assessment: relocates the safety margin (protects one extra generation of history) without closing the actual gap — could be a reasonable defense-in-depth addition on top of a real fix, not a substitute for one.**

**C2 — GC deferring entirely to `saveDb()`'s own dirty-tracking, i.e. "don't run a sweep while there are in-flight publishes."** `saveDb()` does track dirty state (`toSaveType`/`changeTracker`, per Report 06/07's own tracing), but this is per-client, in-memory state — it has no visibility into *other* clients'/devices'/tabs' in-flight saves on the Node-server backend, which is exactly the case that matters (the whole point of GC running against a shared Node-server backend is guarding against concurrent *other* writers, not this same process's own save loop). This could plausibly help the Tauri case (a genuinely single-process backend, where "is there an in-flight publish right now" is fully knowable in-process) as a cheap defense-in-depth check layered on top of a real fix, but it is not itself a fix and cannot be extended to Node-server at all without effectively rebuilding a cross-client signal — which is what the lock-based options already are. **Assessment: not viable as a standalone mechanism on Node-server; a minor, optional hardening layer for Tauri at most.**

**Conclusion on Option C:** neither sub-option evaluated here is simpler than Option A, and neither actually closes the specific interleaving Codex traced — they narrow or relocate the exposure window, the same failure mode Report 07 round-2/round-3 already found in the grace-period-refresh approach and in the "re-observe the candidate's own revision" approach that's actually in the uncommitted code today.

## Tauri-side equivalent

Tauri has no server, no revision store, and (per Report 05/07) is not a genuine multi-writer backend — the only concurrent actors are this same process's own save loop and this same process's own boot-time GC sweep. This makes the fix structurally simpler than Node-server's, but this report's original draft got the shape of the fix wrong.

**[Corrected — Codex round 1]** The original draft claimed widening the WRITER's hold on `withRemoteBlockGcLock` to span publish-through-root-commit was sufficient BY ITSELF, reasoning that "a single process's own decision can't have gone stale between two steps of its own sequential code." That reasoning is false, and Codex's review gave the exact counterexample: GC's *decision* (made by reading the root and deciding K is dead) happens BEFORE GC ever touches the lock at all — it's a plain async read+decode at the top of the sweep, not a lock-protected operation. A widened writer-side lock only prevents GC's *delete* from running CONCURRENTLY with a writer's publish-through-commit sequence — it does nothing to stop GC from later acquiring that same (by-then-free) lock and executing a decision it made BEFORE the writer's sequence even started. Concretely: GC reads the root, decides K is dead (no lock held yet) → a writer acquires the widened lock, publishes K, commits a new root referencing K, releases the lock → GC then acquires the now-free lock and deletes K, using its already-stale decision. The lock was never actually in the writer's way at decision time, only at delete time — exactly the same shape of bug as the Node-server case, independently re-derived here instead of being caught by copying the fix that already existed for it.

**The corrected fix, matching what the corrected Node-server design (above) does in spirit — move GC's *decision*, not just its delete, inside the lock:**

- **Today**: the writer (`encodeRemoteBlock()`, `risuSave.ts:546-551`) holds the lock only around its own leaf write; the root commit (`globalApi.svelte.ts:776`, under `dbWriteLock`, a *different* mutex) happens later, unguarded by `withRemoteBlockGcLock` at all. GC's own delete step (`bootstrap.ts:655`) acquires the SAME lock, but only around the delete — its liveness decision was already made earlier, outside any lock, from the sweep's fresh-but-since-possibly-stale root read.
- **What actually closes the Tauri race**: two changes, not one. (1) The writer's hold on `withRemoteBlockGcLock` still needs widening to span from the start of leaf-block publishing (`encoder.set()`, `globalApi.svelte.ts:748`) through the root commit (`globalApi.svelte.ts:776`) — this part of the original draft was correct, just not sufficient alone. (2) GC's *decision* step must move inside its own lock acquisition too: instead of deciding liveness once at the top of the sweep and then, much later, acquiring the lock only to delete, GC must acquire `withRemoteBlockGcLock` FIRST, and only THEN (while holding it) re-read the current `database.bin` fresh, re-decode it, and re-decide whether the candidate is still dead — all inside one held-lock critical section, immediately followed by the delete if the re-decision still says "dead." Since the writer's full publish-through-commit sequence is now also fully contained within one hold of the same lock (per (1)), whichever of "GC's full re-decide-and-delete" or "the writer's full publish-and-commit" acquires the lock first now runs to complete BEFORE the other can even begin — and because GC's decision is now made FRESH, under the lock, it correctly observes any writer's sequence that already finished before GC got there. This is the Tauri analog of the Node-server fix's core idea (validate against the freshest possible state, not a decision cached from before any synchronization began) — just achieved by re-deciding under a single process-local lock instead of a cross-key server-side revision precondition, since Tauri has no revision store to make a precondition out of.
- This is a larger change to `cleanChunks()`'s Tauri branch than the original draft implied — not just widening a lock's scope, but restructuring GC's control flow so the decode-and-decide step (currently done once, up front, for every candidate in the sweep) happens per-candidate, inside that candidate's own lock hold, immediately before its delete. `withRemoteBlockGcLock`'s current callers and comment both describe its scope as "the remote-block write," and need updating to describe the new, wider, decision-inclusive scope. It should not be conflated with `dbWriteLock`, which serves an unrelated purpose (this tab's own `loadDrive()` restore vs. autosave exclusion, per Phase 1 item 4) — the two mutexes protect different invariants and merging them would be a scope-creep risk of its own, not a simplification.
- **Verification need**: same in kind as Node-server, still smaller in scope (no live server needed — this is a same-process test) — but now needs to cover BOTH orderings explicitly, the same two-ordering trace the corrected Node-server section above walks through: "writer's full sequence completes, then GC's stale-if-not-corrected decision runs" (must now be safe because GC re-decides fresh under the lock) and "GC's full re-decide-and-delete completes first, then the writer's publish-and-commit proceeds" (must be safe because the writer's own publish step, serialized by the same lock, always recreates the block before that writer's own later root-commit step, exactly the same reasoning as the corrected Node-server trace).
- **Important asymmetry with the Node-server design, worth stating explicitly: the Tauri fix closes the race completely, including the third ordering the Node-server design cannot (see the round-2 correction in Option A above).** The reason is structural, not an oversight in one design or the other: `withRemoteBlockGcLock` is a single **global** mutex (one lock for the whole app, not one per remote-block key), so a writer holding it for its entire publish-through-commit sequence genuinely cannot release it partway through — there is no way for "publish completed, commit still pending" to ever become externally observable, because nothing else can run AT ALL while that writer holds the lock. This is only affordable because Tauri is single-process and single-writer (Report 05/07's own finding) — a global lock spanning an entire save operation would be unacceptable on Node-server, which must let unrelated concurrent writers (different keys, different characters, different users' tabs) proceed without blocking on each other; that's exactly why Node-server's fix has to stay fine-grained (per-key locking) and therefore cannot achieve the same all-or-nothing atomicity across two separate requests. Tauri gets a stronger correctness guarantee than Node-server for the same class of race, for free, purely because it doesn't need to scale.
- **[Corrected — Codex round 3] This also means Tauri's correctness does not depend on `.meta`/grace-period timing at all — unlike Node-server (see the round-3 correction in Option A above, where a stale `.meta` from a PRIOR, unrelated orphaning episode makes a republish immediately vulnerable).** For Tauri, GC's liveness *decision* is re-made fresh, under the same global lock the writer's whole sequence also uses, immediately before any delete — so a candidate that's actually live (referenced by whatever root exists at the moment GC's lock acquisition succeeds) is correctly recognized as live regardless of how stale its `.meta` file happens to be; the grace-period check is only ever reached for a candidate GC's fresh re-decode has already confirmed is NOT currently referenced, and by that point the lock (not the timestamp) is what's preventing data loss. Meta-refresh-on-publish is still worth doing for Tauri (it avoids pointless delete-then-immediately-recreate churn on a republish that races GC unfavorably), but it is a performance nicety there, not — as it is for Node-server — a load-bearing part of the safety argument.

## Is automatic GC the right feature to build at all?

**Report 07 already established that GC is a storage-growth mitigation, not a correctness requirement** — content-addressed naming is safe with zero reclamation; superseded blocks are just inert, unreferenced bytes sitting in storage, not a source of corruption. This report's own findings sharpen that tradeoff rather than changing its shape:

- **Cost of building Option A properly** — **[Corrected — Codex rounds 2 through 5]** understood now as risk-reduction layered on the grace period *plus mandatory meta-refresh, sequenced strictly before K's own write/reassertion and before root commit, plus a required three-way precondition set on the delete* (Node-server; see the round-3, round-4, and round-5 corrections above — meta-refresh alone doesn't help unless both (a) the delete's precondition actually checks meta's revision too, and (b) meta-refresh happens *first*, ahead of K's own write, not merely "unconditionally, whenever" — a `skipRemoteSaving`-skipped byte-write, or a writer whose own steps run in the natural "publish then refresh" order, can each independently reopen the gap otherwise), not a mechanism that fully closes the race there (it does, fully, on Tauri, without needing any of this extra machinery for correctness — see that section's asymmetry notes): a server-side extension to `/api/remove` (two new headers supporting one or more check-only keys — now known to need at least two, root AND `.meta`, alongside K itself — folded into its existing multi-key lock/precondition loop, still smaller than this report's first-draft estimate, which wrongly required a new `/api/write` mode and a new status code, per the round-1 correction), a client-side change so publishing a remote block also unconditionally refreshes/creates its `.meta` liveness timestamp *as the first step of the publish sequence, awaited before anything else* (per the round-3 and round-5 corrections), a GC-side control-flow rework on BOTH backends so the *decision*, not just the delete, is made under the relevant lock/precondition, and captures ALL THREE relevant revisions (K, root, `.meta`) together as one snapshot, never refreshed piecemeal before the delete request (per the round-4 correction) — and, per the Codex review's own explicit recommendation, a live-server concurrency/integration test for the Node-server path (covering all orderings traced above, including both the `skipRemoteSaving`-causes-no-K-revision-bump case and the meta-refresh-ordering case specifically) plus a standalone interleaving test for Tauri (which, unlike Node-server, can be verified to close its race completely). This is realistically comparable in adversarial-review cost to Tier B Stage 1's nine rounds: both are "a decision made from one read, executed later, where a concurrent actor can invalidate the read in between" bug classes, and Stage 1 needed nine rounds specifically because that class of bug kept resurfacing in slightly different shapes even after each "obvious" fix. This report's own five correction rounds are a small-scale instance of the exact same pattern — each round found the previous round's fix was necessary but not sufficient, and this pattern (a genuinely new sub-ordering surfacing each time a fix closes the previous one) is itself informative: it demonstrates concretely, not just by analogy to Stage 1, how easy this specific bug class is to underestimate even when actively trying to design around it carefully. There is no reason to expect a real implementation converges faster — if anything, it's structurally harder than Stage 1, since the Node-server side has a genuine, only-partially-closeable residual limit that Stage 1's single-key case never had to contend with.
  - **Cost of the fully-closing alternative (merging publish+commit into one atomic multi-key `/api/write`)**, if the residual Node-server gap above is judged unacceptable rather than adequately covered by the grace period: larger still — this restructures `saveDb()`'s fundamental two-step write sequence for every remote-eligible save, not just GC's read path, and was not sized in file-by-file detail by this report (flagged here as the next thing to size if the project owner decides the residual gap needs closing rather than accepting the grace-period-backed risk reduction).
- **Cost of not building it**: unbounded accumulation of superseded remote-block versions per character, per save, for any user on Tauri or Node-server who has `enableRemoteSaving` on (still opt-in-only today, per Report 07's confirmed finding that no code path sets a default). This is a real but bounded-severity cost — it is disk space, not data loss, and it scales with save frequency and character count, not with anything catastrophic. It is also, per Report 07's own "Migration" section, exactly the same category of cost that already exists today for legacy `v:1` un-versioned blocks sitting around (those, too, currently rely on the same not-fully-safe GC path this report is scoping a fix for) — so shipping naming-only does not introduce a new class of problem, it just means an existing, already-latent growth-without-reclaim situation continues a while longer under a safer naming scheme.
- **This report's honest read**: given that (a) GC is confirmed non-load-bearing for correctness, (b) the actually-safe fix is a large, multi-round undertaking on the order of the hardest thing this whole investigation-and-remediation effort has done, and (c) the current uncommitted implementation is confirmed unsafe and must not ship as-is — the effort/risk tradeoff clearly favors **not building automatic GC as part of landing content-addressed naming**. Ship the naming fix (Report 07's Option A, minus GC), leave superseded blocks unreclaimed, and revisit reclamation later as its own explicitly-scoped, explicitly-resourced project — ideally only if real usage data later shows storage growth is an actual problem in practice, not a theoretical one.

## Incremental adoption path

1. **Immediate: revert or do not ship the current uncommitted GC implementation as-is** — it is confirmed unsafe by both this report's own re-trace and Codex's round-1 review, on both backends.
2. **Small, safe, shippable now: content-addressed naming alone (Report 07 Option A), with no automatic reclamation.** This is already effectively done in the uncommitted `risuSave.ts` changes (the `v:2` pointer shape, `hashRemoteBlockContent()`, content-addressed filenames) — what needs to be stripped out or gated off before shipping is specifically the delete path in `cleanChunks()` (`bootstrap.ts`'s "create-meta"/"delete" branches for `remotes/*` entries) and the `withRemoteBlockGcLock` machinery that only exists to serialize against that delete path. The naming/pointer-format change and the "create-meta" (liveness-tracking-only, no delete) half of the GC loop are safe to keep as-is — only the actual `remove()`/`removeItem()` calls are the unsafe part.
3. **Deferred, large, needs-its-own-multi-round-review: Option A's cross-key revision-precondition mechanism (Node-server) and the widened-lock mechanism (Tauri)**, sized above, if and when the project owner decides storage growth from unreclaimed superseded blocks has become a real problem worth the effort. Should be scoped and resourced as its own dedicated Roadmap phase item, explicitly budgeted for review-cycle cost comparable to Tier B Stage 1's nine rounds, not folded into "finish Stage 3a" as if it were the remaining small piece — and, per this report's own two correction rounds, not assumed correct on a first (or even second) design pass: Tauri's fix does close its race completely, but Node-server's analogous fix has a genuine, structural, only-partially-closeable residual gap (see the round-2 correction above) that a future implementer needs to either explicitly accept (backed by the grace period) or address with the larger atomic-multi-key-write alternative — not discover mid-implementation as unsafe, the way this session's own first attempt did.
4. **Not recommended at all: Option B (lease/reservation) as a standalone mechanism** — sized above specifically to show it collapses into a weaker version of Option A rather than being a genuinely smaller alternative.

## Where this is a product decision, not a technical one

- **Build the real mechanism (Option A) now vs. ship naming-only with no automatic reclaim vs. defer the whole feature**: this is squarely the project owner's call, and this report's own honest recommendation is the middle option — ship naming-only now (it's already most of the way done in the uncommitted tree, minus the unsafe delete path), defer reclamation as a separate, explicitly-scoped future project. The case for building Option A immediately would need to rest on a demonstrated storage-growth problem, not a hypothetical one — nothing in this investigation established real-world save frequency or character-count numbers that would quantify how fast unreclaimed blocks actually accumulate for a typical user, which would be useful input to that future decision but is out of scope here.
- **Whether unbounded superseded-block growth is an acceptable long-term status quo, or needs even a manual/admin-triggered cleanup tool as a lower-effort middle ground** (a human explicitly clicking "clean up old remote block versions," accepting a coarser, more conservative safety margin than an automatic sweep since a human is present to notice something looks wrong) is a genuine, not-yet-explored option this report did not size in detail — flagged here as a possible cheaper alternative to full Option A worth considering before committing to the large adversarial-review undertaking Option A represents.
- **Whether the Tauri-side fix (widening `withRemoteBlockGcLock`'s scope) should ship independently of the Node-server fix**, since it's genuinely smaller and doesn't need a live-server test: this is a reasonable sequencing question for the project owner, not a technical blocker — but shipping only the Tauri half would leave the more commonly-deployed shared-backend case (Node-server, and eventually the blocked-but-someday account-sync case) still without safe automatic reclaim, so it would only be a partial win.
