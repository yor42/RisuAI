# Tier B Conflict-Resolution Design Feasibility

Scope note: this report does not re-investigate whether the last-write-wins problem exists (confirmed in `Agents/Reports/05-multi-instance-conflict.md`, Tier A already fixed in `cafd2315`). It assesses which of Report 05's four sketched design options is most technically feasible and least invasive to actually build in this codebase, based on reading the real save/encode/decode pipeline and both server backends. No code was changed by this investigation.

**[Corrected after Codex adversarial-review — see `Agents/CodexReviews/topic06/06-conflict-resolution-design-feasibility.codexreview.md`.]** The review found four issues, all now corrected inline below: (1) the initial draft's proposed Stage-1 revision check was described as if a simple read-compare-write in the Express handler would be sufficient, without accounting for two concurrent requests both passing the comparison before either writes (a TOCTOU race in the mitigation itself) — corrected in the Option 1 file-by-file section and the increment sketch. (2) The initial draft claimed a conflict branch in `saveDb()` could tell the user their edits were "safely queued" by reusing the existing `mergeUnsavedChanges` helper; that helper only restores dirty *identifiers* into the in-memory `changeTracker`, not the edited content itself, and does not survive a reload — corrected. (3) The initial draft described Stage 2 (account-sync 409/412 handling) as safe to add regardless of hub behavior; in fact `AccountStorage.setItem` (`accountStorage.ts:71-75`) writes the new blob into `cachedForage` immediately after the fetch resolves, *before* checking whether the response indicates success (`accountStorage.ts:94-107`), so a rejected write's content would already be cached as if accepted — corrected. (4) The initial draft characterized `server/node/server.cjs`'s `/api/write` as a bare, non-atomic `fs.writeFile`, based on a read of the file at investigation start; by the time Codex's review ran, the working tree already contained an uncommitted temp-file-write-then-rename change to that same handler (apparently in-progress, unrelated work happening concurrently in this repo, matching `Agents/Roadmap.md` Phase 1 item 9) — the atomicity characterization is now corrected to reflect that, while the core conclusion (no revision/lock/conflict-detection of any kind exists) is unaffected and remains true under either version of the handler.

## Summary

**Recommendation: Option 1 (revision/ETag optimistic concurrency), scoped first to the self-hosted Node server only, with detection-not-merge UX (reject + prompt, not silent overwrite).** Of the four options, it is the only one that can be fully implemented, tested, and shipped end-to-end using only code this repo controls: `server/node/server.cjs` gets a real conflict check (currently `/api/write` is a bare `fs.writeFile` with no revision, lock, or ETag anywhere in the file — confirmed by direct read), and the client-side plumbing (a revision field threaded through `AutoStorage`/`NodeStorage`/`saveDb()`) is a handful of surgical additions, not a rewrite. It does not require changing the on-wire `RisuSave` block format (the revision travels as a header/sidecar, not inside the encoded blob), so it needs no migration for existing users' saved data. Option 2 (per-block granularity) is a valuable force-multiplier *on top of* Option 1 later, but is not itself a conflict-detection mechanism — the existing `remote: 'prefer'` machinery already reduces blast radius for Tauri/Node-server when enabled, but reduces *how much* gets clobbered, not *whether* clobbering is detected, so it's a poor first move on its own. Option 3 (CRDT/op-log) is the only option that could ever get true concurrent-edit merging instead of detect-and-refuse, but it requires rewriting the save format, the encoder/decoder, and the chat data model — by far the largest lift, and disproportionate unless genuinely simultaneous same-chat multi-device editing is a confirmed real use case (not established by anything in Report 05 or this report). Option 4 (hard lock + takeover UI) is achievable for the Node server but is a larger product commitment (new persistent lease state, renewal logic, a takeover UI) for a benefit Option 1 already delivers more cheaply as a side effect (a revision check plus a clear conflict error is most of what a lock buys, without needing lease renewal/expiry design). For account-sync, all four options are constrained by the same hard limit: the hub's `/api/account/write` and `/api/account/read` handlers are not in this repository, so any option that needs the *hub* to reject stale writes, hold a revision counter, or arbitrate a lock cannot be verified or guaranteed — only client-side mitigations (revision-aware client logic that at best reduces the race window, at worst is inert if the hub ignores the extra header) are achievable without hub cooperation.

## Option 1: Revision/ETag-based optimistic concurrency

**Concept recap:** client reads current revision, includes it on write; storage rejects the write if the revision has moved since the read.

### File-by-file, what would actually change

- **`server/node/server.cjs`** (fully controlled): `/api/write` (`server.cjs:1278-1305` at the start of this investigation) had zero version awareness — confirmed by direct read at the time, no `etag`/`version`/`lock` string appeared anywhere in the file (grepped). **[Corrected — Codex round 1]** By the time this report's Codex review ran, the working tree already contained an uncommitted change to this same handler (unrelated, concurrent work matching `Agents/Roadmap.md` Phase 1 item 9): it now writes to a unique temp file and atomically `rename()`s it over the real path, closing the *torn-write* risk that Report 05 flagged as an open question. This is orthogonal to conflict *detection* — an atomic rename still means the second of two racing writes fully replaces the first with no error to either caller, so the last-write-wins conclusion is unaffected. To add real optimistic concurrency on top of whichever write-path variant is current:
  - Maintain a revision per stored file. Cheapest implementation: a single JSON map `revisions.json` keyed by hex filePath, itself written via the same atomic temp-then-rename pattern the write handler already uses (so the revision store doesn't introduce a new non-atomic-write risk of its own) — a new small piece of persisted state, scoped to the server's own save directory, not the client format.
  - **[Corrected — Codex round 1]** A read-compare-write in the request handler is not by itself sufficient: two concurrent `POST /api/write` requests for the same key can each read the same current revision, each pass the comparison (both still see it as unmoved), and both proceed to write — the comparison and the write are not one atomic operation just because they're expressed as sequential `await`s in the same async function. Node's single-threaded event loop does *not* protect against this, because the `fs.writeFile`/`fs.rename` calls yield control between the revision check and the revision-store update, giving another request's handler a window to run its own check in between. Closing this requires an explicit per-key critical section: e.g. an in-process `Map<string, Promise>` that serializes all revision-check-and-write sequences for a given key within one Node process (queue each new request's critical section behind the previous one's completion for that key), not just a plain `if (storedRevision !== requestRevision)` check. This serialization only holds within a single Node process — if the self-hosted server is ever run as a multi-process cluster (not confirmed either way for this codebase, not investigated further here), a stronger mechanism (a real file lock or a transactional store) would be needed instead. This is more implementation care than the original sketch implied, but is still fully containable inside the write-handling logic already scoped to this one file — it does not change the shape of what needs to move (still: a revision store, a conditional check, no new endpoints).
  - `/api/write` needs to accept an optional `if-match-revision` header (or similar), compare it against the currently stored revision for that path inside the per-key critical section described above, and respond `409 Conflict` (with the current revision and, ideally, current content or a hash) instead of writing, if they don't match. When no header is sent (back-compat with pre-upgrade clients), fall back to today's unconditional write — this is what makes it deployable incrementally without breaking old clients.
  - `/api/read` (`server.cjs:1183-1213`) needs to additionally return the current revision (a response header is simplest, avoids touching the response body format that `nodeStorage.ts`'s `getItem` already expects as a raw buffer).
  - This is a self-contained change scoped to one file: a new small persisted revision store, a per-key serialization mechanism, and conditional logic added to two existing route handlers. No new endpoints, no new auth model, no new heavy dependency — but it is not as trivial as "add an if-check," per the correction above.

- **`src/ts/storage/nodeStorage.ts`**: `setItem` (lines 72-90) needs to send the last-known revision as a header, and handle a `409` response distinctly from the current blanket `if(da.status < 200 || da.status >= 300){ throw "setItem Error" }` (line 83-85) — needs to throw/return a typed "conflict" signal instead of a generic string, so callers can react differently (retry-with-merge vs. generic-error-toast). `getItem` (lines 91-109) needs to capture and return/cache the revision it read, so the *next* `setItem` call can present it.

- **`src/ts/storage/autoStorage.ts`**: `AutoStorage.setItem`/`getItem` (lines 17-29) are thin pass-throughs to `this.realStorage`; they don't need structural changes, but the revision needs a place to live between a `getItem` and a later `setItem` for the same key. Since `AutoStorage` doesn't currently track any state around individual keys, a small revision cache (a `Map<string, string>` keyed by storage key, populated on `getItem`/`setItem` responses) is the natural addition — this is new in-memory state, not new persisted state.

- **`src/ts/globalApi.svelte.ts`**, `saveDb()` (lines 379-626): today it always encodes and writes unconditionally in a tight loop with a 5-strikes generic-error/retry policy (lines 598-621, `savetrys`). It needs a new branch: on a conflict response, instead of the existing retry-and-eventually-`alertError` path, it should re-fetch and prompt the user (re-using the existing `alertNormalWait` pattern already present for the BroadcastChannel case). **[Corrected — Codex round 1]** The initial draft claimed this branch could tell the user their edits are "safely queued" by reusing `mergeUnsavedChanges` (lines 497-513) the same way the BroadcastChannel `gotChannel` branch already does (lines 556-561). That overstates what the helper does: `mergeUnsavedChanges` only re-adds dirty *identifiers* (character IDs, `[chaId, chatId]` pairs, and boolean flags) back into the live in-memory `changeTracker` so the *next* save loop iteration knows to re-encode them from the live `DBState` — it does not persist the edited content anywhere, and a `location.reload()` (which the existing BroadcastChannel branch triggers, and which a conflict-recovery UX would plausibly also want to offer) would discard the in-memory database state those identifiers point at, losing the actual edits, not just deferring them. `mergeUnsavedChanges`'s existing use is safe today only because the BroadcastChannel path's losing tab is expected to keep running (not reload) while parked, waiting for the *other* tab's reload message to arrive for *it* — it was never a durable "safely queued across a reload" mechanism. Additionally, `RisuSaveEncoder.set()` mutates its `toSave` argument in place via `.splice()` while walking `toSave.character` (`risuSave.ts:216-227`) as part of encoding — so by the time a write attempt fails with a conflict, the `toSave` snapshot `saveDb()` took before calling `encoder.set()` may already have had entries removed from it, meaning a subsequent `mergeUnsavedChanges(toSave)` call cannot fully restore everything that was dirty going into that attempt. A real conflict-recovery UX therefore needs either (a) a genuinely durable pending-edit store (e.g., persisting the pre-conflict `toSave`/edited state to browser storage before prompting, so a reload can recover it) or (b) a product decision to avoid reload entirely on conflict (keep the tab running, re-fetch-and-compare in place) — "reload after parking via `mergeUnsavedChanges`" is not sufficient as sketched. This is additive logic alongside the existing retry loop, not a rewrite of it, but is a real, not merely cosmetic, design gap that needs to be closed before this increment ships.

- **`src/ts/storage/risuSave.ts`**: **no changes needed** for the base version of this option. The revision is metadata *about* the blob, not *inside* it — it can travel as a request/response header or a small separate sidecar key (e.g. `database/database.bin.rev`), so the `RisuSaveEncoder`/`RisuSaveDecoder` block format is untouched, and existing saved data needs no migration.

- **Account-sync (`src/ts/storage/accountStorage.ts`)**: The existing `x-risu-save-date`/`x-risu-session` headers (lines 49, 67-68) and the unhandled-in-client `409`/`412` gap (confirmed: `setItem`'s status handling only special-cases `403` and `304`, lines 47, 94-104, everything else including any `4xx` conflict status the hub might already send today falls into the generic `throw await getDaText()` at line 105-107) suggest the hub *may* already have some server-side session/date enforcement, but its actual semantics are unverifiable from this repo. The safe, honest client-side move: add explicit handling for a `409`/`412` status in `setItem` (today silently swallowed into a generic error) so that *if* the hub already sends one, the client at least reacts sanely (park-and-prompt, same as the Node-server case) instead of blind-retrying the same stale write up to 4 times. This is a pure client-side improvement — it cannot add revision *enforcement* the hub doesn't already do, but it stops the client from being actively hostile to enforcement the hub might already have. **[Corrected — Codex round 1]** The initial draft described this as safe to add "regardless of what the hub actually does." That's not quite right as scoped: `setItem` (`accountStorage.ts:71-75`) writes the new blob and save-date into `cachedForage` — the client's local cache used by `getItem`'s `303`/`match:true` fast path (lines 138-147) — immediately after the `fetch` call resolves, *before* the status-code check that happens later in the function (lines 94-107). So a hypothetical `409`/`412` rejection would, under the code as it exists today, still have already overwritten the local cache with the rejected (stale) content and date, ahead of any new conflict-branch logic that only runs after that point. Adding a `409`/`412` branch therefore isn't a pure addition — it also needs the `cachedForage.setItem` call moved to only run after a confirmed 2xx/304 response (or the conflict branch needs to explicitly restore the prior cached value/date it clobbers), or a later `getItem` could serve stale, rejected content out of cache as if it had been accepted. This is still a small, self-contained, client-only change, but it is two coordinated edits (reorder the cache write, add the conflict branch) rather than one additive branch.

### Server-side changes needed?

- **Self-hosted Node server: yes, and fully achievable** — this repo owns `server/node/server.cjs` outright; the revision store and conditional-write logic can be implemented, tested, and shipped completely.
- **Account-sync hub: not controllable.** The hub's `/api/account/write`/`/api/account/read` are a remote service with no source in this repo (confirmed absent from `server/node/server.cjs`, which only implements `/api/*`, not `/api/account/*`). Client-side changes can, at best, (a) stop actively mishandling a conflict signal the hub might already send, and (b) send a revision/date header the hub might already be using unbeknownst to us (it already receives `x-risu-save-date`). This cannot be verified to close the race on account-sync without either hub cooperation or a live test against the actual hub, which this investigation does not have access to.

### New persisted state?

Yes, but small and scoped: a per-file revision counter on the Node server (new, small, server-local file(s)); no new persisted state needed on the client beyond an in-memory revision cache. No account-sync-side persisted state, since we can't add anything there.

### New UI?

Minimal: one new alert/prompt state (conflict detected → "reload to get the latest version, your edits are safely queued"), which can reuse the existing `alertNormalWait` pattern already wired up for the BroadcastChannel same-browser case — not a new UI paradigm, just a new trigger for an existing one.

## Option 2: Per-chat/per-character granular sync with independent revisions

**Concept recap:** extend the existing `remote: 'prefer'` per-character file mechanism to shrink blast radius, pairing naturally with per-block revisions.

### File-by-file

- **`src/ts/storage/risuSave.ts`**: the mechanism already exists (`encodeRemoteBlock`, lines 378-422; gated by `option.remote === 'prefer' && (isTauri || isNodeServer) && !disableRemoteSaving()` in `encodeBlock`, lines 328-343) — each character's JSON is written to its own storage key `remotes/<chaId>.local.bin`, separate from the shared `database.bin`. Confirmed (per Report 05, corrected finding) that `db.enableRemoteSaving` has no initializer anywhere and `disableRemoteSaving()` returns `true` (disabled) when unset — so this is **off by default today**. Making this the default, or extending it to account-sync (currently excluded: `remote: 'prefer'` requires `isTauri || isNodeServer`, which a plain-browser account-sync context never satisfies), is the actual scope of work here — not building the mechanism from scratch, but turning it on more broadly and extending its backend-eligibility check.
  - Extending true per-*chat* (not just per-*character*) granularity is a larger change: `RisuSaveType.CHARACTER_WITH_CHAT` currently embeds the character's entire chat history as one JSON blob (confirmed — there is no separate per-chat block type actually wired to storage; `RisuSaveType.CHAT = 3` exists as an enum value but is not used by any `encodeBlock` call site in `init()`/`set()`). Actually splitting per-chat would mean: changing `RisuSaveEncoder.set()`'s dirty-tracking (`toSaveType.chat`, already tracked per-`[chaId, chatId]` pair at `globalApi.svelte.ts:483-487` but currently only used to decide *whether* to re-encode the whole character, not to address an independent storage key) to actually write one storage key per chat; and changing `RisuSaveDecoder.decode()`'s reassembly logic (currently reconstructs one character object per `CHARACTER_WITH_CHAT`/`CHARACTER_WITHOUT_CHAT` block, lines 523-529) to stitch chats back onto their character from separate blocks. This is a real, non-trivial change to the encode/decode pipeline and the on-wire format (new block type actually used, new key-naming scheme), unlike Option 1.
- **Server-side**: no server-side logic change needed for the *existing* per-character mechanism — it's just more independent `setItem`/`writeFile` calls to more keys, which the Node server already handles identically to any other key. True per-chat granularity is the same story — more keys, same handler.
- **Revision pairing**: if layered under Option 1, each block's key gets its own revision instead of one revision for `database.bin` — this multiplies the amount of revision-tracking state (one entry per character or per chat instead of one for the whole DB) but doesn't change the *kind* of server-side logic needed.

### Assessment

This option **reduces blast radius but is not itself a conflict-detection mechanism** — two devices racing to write the *same* character's block still silently last-write-wins each other under today's write path, just without also destroying unrelated characters' data. It's a strict complement to Option 1, not a substitute for it. Turning on the existing per-character mechanism by default (small change: flip the default, or expose an opt-out instead of opt-in) is cheap and immediately shrinks blast radius for Tauri/Node-server without any encode/decode format change. True per-chat splitting is a real format change (new block type wired up, new key scheme) with a compatibility/migration story: old single-blob character saves need a one-time split-out path, and the decoder needs to handle both shapes during a transition window. This is meaningfully more invasive than Option 1 and buys detection improvements no better than what Option 1 already buys per-block if paired together.

## Option 3: CRDT-ish / operation-log merge for chat content

**Concept recap:** append-only ops (new message, edit, delete) instead of full snapshots, merged across devices.

### File-by-file

This is the only option that requires touching essentially every layer:

- **`src/ts/storage/risuSave.ts`**: the entire block model (`RisuSaveEncoder`/`RisuSaveDecoder`) assumes each save produces a full current-state snapshot per block (character, preset, modules, etc.) written to a fixed key. An op-log model needs a fundamentally different storage shape: an append-only sequence of operations per chat (or per character), each with an origin device/session id, a logical/physical timestamp, and idempotent replay semantics — none of which exists today. `RisuSaveType` would need new entry types for "operation" records, and `RisuSaveDecoder.decode()`'s single-pass reconstruction (lines 432-619) would need to become "load full snapshot, then replay any newer un-folded operations on top" — a materially different decode algorithm, not an incremental addition.
- **`src/ts/globalApi.svelte.ts`**, `saveDb()`: the dirty-tracking (`changeTracker`/`toSaveType`) already tracks *which* character/chat changed but not *what specifically* changed (it's presence/absence tracking for "does this block need re-encoding," not a diff/operation record) — capturing actual operations (message appended, message X edited, message Y deleted) would need new instrumentation at the point of mutation throughout the chat-editing UI (`src/lib/ChatScreens/*`, wherever messages are appended/edited/deleted), which is a much larger, more diffuse surface area than anything in Option 1 or 2.
- **Server-side**: both the Node server and (hypothetically, if the hub cooperated) account-sync would need genuinely new logic — appending to a log rather than overwriting a file, garbage-collecting/compacting old operations, and serving "operations since revision N" reads. This is materially new server-side infrastructure, not a conditional check bolted onto existing handlers.
- **Merge logic**: ordering/idempotency across devices with clock skew, out-of-order delivery, and duplicate-delivery handling is a real algorithm design problem (not sketched further here — out of scope for a feasibility assessment, but flagged as nontrivial engineering even before touching this codebase).

### Assessment

By far the largest lift of the four — new save format, new encode/decode algorithm, new server-side infrastructure (on the one server we control; impossible to guarantee on the hub we don't), and new instrumentation scattered across the chat-editing UI. It is also the *only* option that could deliver true concurrent-edit preservation (both devices' new messages survive, interleaved) rather than detect-and-refuse. Given that Report 05 found no evidence either way about how common genuine simultaneous same-chat editing actually is for this app's users, recommending this first is not justified by what's known today — it should be considered only if product data later shows detect-and-refuse (Option 1) is insufficient in practice.

## Option 4: Hard single-writer lock with explicit takeover UI

**Concept recap:** formalize the existing same-browser BroadcastChannel mechanism into a real cross-device lease, with an explicit "take over" UI instead of silent reload.

### File-by-file

- **`server/node/server.cjs`**: needs new persisted lease state — e.g. a `lock.json` (or per-key lock) recording `{ holder: deviceId, acquiredAt, expiresAt }`, new endpoints (`/api/lock/acquire`, `/api/lock/renew`, `/api/lock/release`, or folded into existing write auth), and a check in `/api/write` (`server.cjs:1278-1305`) that rejects/warns when the caller doesn't hold the current lease. This is more new server-side surface than Option 1 (new endpoints, not just a conditional on existing ones), but still fully within this repo's control and testable.
- **`src/ts/storage/nodeStorage.ts`** / **`autoStorage.ts`**: need new methods to acquire/renew/release a lease, and `saveDb()`'s loop (`globalApi.svelte.ts:379-626`) needs a lease-renewal heartbeat woven into its existing `while(true)` cadence (there's already a natural place — the loop already sleeps 500ms-1s between iterations, lines 520, 600, 621) — not a huge structural change, but a new recurring background call that didn't exist before.
- **UI**: a genuinely new UI surface is needed — "Your other device is currently editing — [Take over] / [View read-only]" (per Report 05's sketch). This doesn't exist in any form today (the closest analog, the BroadcastChannel reload prompt, is a blunt forced-reload with no choice presented) — this is real new UI work, more than Option 1's reuse of the existing alert pattern.
- **Account-sync**: same hard limit as every option — a cross-device lease needs a server that both/all devices talk to and trust to arbitrate; the hub is out of this repo's control, so a real lease can only be built for the self-hosted Node server. For account-sync, the existing `x-risu-session`/`reloadSession` machinery (`accountStorage.ts:51-58, 85-91`) is suggestively lock-like already, but unverifiable, and this repo cannot add a *new* lock concept to the hub — it could at best try to interpret the hub's existing (unknown) session semantics more intelligently.
- **Local-only backend (plain browser, no server at all)**: no server exists to hold a lease, so this option literally cannot be implemented there — the BroadcastChannel mechanism remains the only option for that specific case, same conclusion Report 05 already reached.

### Assessment

Achievable for the Node server, not extendable to account-sync without hub cooperation, and structurally impossible for the pure-local-browser backend (nothing to hold the lease). It also fundamentally forecloses true concurrent editing (which may be an acceptable product tradeoff, but is a stronger constraint than Option 1, which still permits concurrent editing and only intervenes at save time). Its main advantage over Option 1 is UX clarity (explicit ownership/takeover instead of a save-time conflict prompt) — but it requires strictly more new infrastructure (lease store, renewal heartbeat, new endpoints, new dedicated UI) for a benefit Option 1 mostly already delivers (a conflict is still caught, just at write time rather than pre-emptively at edit time).

## Constraints from the account-sync hub being out of our control

This is the single most consequential fact shaping every option above, so it's worth stating plainly and once:

- `server/node/server.cjs` is the entirety of what this repo implements server-side. It implements `/api/*` (self-hosted Node server) only. `/api/account/*` (used by `AccountStorage` in `src/ts/storage/accountStorage.ts`) is a remote hub service with no source present anywhere in this repository — confirmed by the absence of any `/api/account/` route registration in `server.cjs`.
- Every option's account-sync story is therefore **at best "client-side mitigation," never "solved."** Concretely:
  - **Option 1** on account-sync: can add proper handling of a `409`/`412`-style conflict response *if the hub already sends one* (today such a response would fall into the generic unhandled-error path per `accountStorage.ts:105-107`), and can keep sending the revision/date data the hub might use. It cannot *make* the hub start rejecting stale writes if it doesn't already.
  - **Option 2** on account-sync: per-character/per-chat granular storage keys could be created and pushed to the hub via the same `/api/account/write` mechanism (it just takes a `key` header today, `accountStorage.ts:65`) — so *shrinking blast radius* for account-sync is client-achievable without hub cooperation, unlike detection. This is the one meaningful piece of account-sync protection achievable unilaterally.
  - **Option 3** on account-sync: fundamentally requires the hub to store and serve an operation log rather than a blob; not achievable client-side at all.
  - **Option 4** on account-sync: fundamentally requires the hub to hold and arbitrate a lease; not achievable client-side at all (the existing `reloadSession` signal might already be doing something like this, but this repo cannot add or extend that logic, only try to interpret it more carefully).
- **Bottom line, stated honestly per the task's instructions:** the only Tier-B protection that can be *fully and verifiably* delivered by changes in this repo alone is on the self-hosted Node server. For account-sync, the best achievable outcome without hub cooperation or hub source access is: (a) stop the client from actively defeating whatever protection the hub might already have (the unhandled-conflict-status gap), and (b) reduce blast radius via wider per-character/per-chat key granularity (Option 2's client-only piece). Closing the account-sync race outright requires either obtaining the hub's source/cooperation, or running a live multi-session test against the actual hub to empirically characterize `reloadSession`/session-number behavior — neither was available to this investigation, same open question Report 05 already flagged as unresolved.

## Incremental adoption path

Yes — Option 1 in particular supports a genuinely staged rollout, which is a point in its favor over Option 3/4:

1. **Stage 1 (self-hosted Node server only, fully within our control):** add revision tracking + `409` rejection to `server/node/server.cjs`'s `/api/write`/`/api/read`; update `nodeStorage.ts` to send/receive it; update `saveDb()` to handle a conflict response with a park-and-prompt UX. Ship and validate entirely against a server we control and can test concurrency against directly (addressing Report 05's own open question about `fs.writeFile` torn-write behavior as a side effect of adding this).
2. **Stage 2 (client-side account-sync hardening, no hub changes needed):** add explicit `409`/`412` handling in `accountStorage.ts`'s `setItem` so that if the hub already enforces something, the client behaves sanely instead of blind-retrying. **[Corrected — Codex round 1]** This must be paired with reordering (or guarding) the `cachedForage.setItem` call at `accountStorage.ts:71-75` so it only commits on a confirmed successful response — otherwise a conflict branch would be reacting correctly to the `409`/`412` while the local cache has already silently absorbed the rejected write, which a subsequent `getItem`'s `303`/`match:true` fast path (lines 138-147) could then serve back as if it were accepted. With that reordering included, this remains a small, self-contained, client-only change.
3. **Stage 3 (blast-radius reduction, backend-agnostic):** flip `db.enableRemoteSaving`'s default (or expose it as a clearer opt-out) for Tauri/Node-server, and evaluate extending the per-character key mechanism's eligibility check to account-sync too (Option 2's cheap piece) — shrinks the blast radius of any *undetected* conflict everywhere, independent of whether Stage 1/2's detection lands first.
4. **Stage 4 (conditional on hub information):** if/when the hub's actual behavior is confirmed (by obtaining source access or running controlled multi-session tests against it), revisit whether account-sync can get real server-enforced revision checking, or whether the existing session/`reloadSession` machinery already provides it and just needs the client to interpret it correctly.
5. **Not scheduled without a product decision:** Option 3 (op-log/CRDT) and Option 4 (hard lock + takeover UI) — both are viable *later* additions layered on top of Stage 1's revision infrastructure (a lease is, roughly, "a revision the server refuses to let move except by the lease holder"; an op-log is a fundamentally different data model that could reuse Stage 1's per-block revisions as the "which blocks changed since last sync" signal), but neither should be started before a product owner decides whether detect-and-refuse is an acceptable long-term UX or whether true concurrent multi-device editing needs to be preserved.

This path never requires an all-or-nothing rollout: Stage 1 alone is independently shippable and immediately closes the Node-server gap (Report 05's confirmed-worst case, since Node server had *zero* mitigation of any kind, weaker even than account-sync's unverified-but-present session machinery).

## Risk / invasiveness comparison

| Option | Changes on-wire/on-disk format? | Needs new server infra? | Touches all write paths or scoped? | Smallest useful (80/20) version |
|---|---|---|---|---|
| 1. Revision/ETag | No — revision travels as header/sidecar, not inside `RisuSave` blocks | Small addition to existing `/api/write`/`/api/read` handlers (Node server only) | Scoped — can ship Node-server-only first, account-sync opportunistically later | Node-server-only `409` check + client park-and-prompt (Stage 1 above) |
| 2. Per-block granularity | Yes, for true per-*chat* splitting (new block type actually wired up, key-naming scheme, migration path for old single-blob saves); No, for just defaulting-on the existing per-*character* mechanism | None beyond what already exists (more keys to the same handlers) | Scoped, additive — doesn't require touching Tauri's already-separate-file writes | Flip `enableRemoteSaving`'s default for Tauri/Node-server; extend eligibility to account-sync |
| 3. CRDT/op-log | Yes, fundamentally — new block types, new decode algorithm, replay semantics | Yes, substantial — append/compact/serve-since-revision logic, on both Node server (buildable) and hub (not buildable by us) | Touches everything: save format, encoder/decoder, chat-mutation call sites throughout the UI | No good 80/20 — the value proposition (true concurrent merge) only exists once the whole mechanism works |
| 4. Hard lock + takeover UI | No | Yes — new lease store, new endpoints, renewal heartbeat (Node server only; impossible for pure-local-browser, unbuildable for hub) | Scoped to server-backed writers; local-only browser storage still relies on BroadcastChannel alone | A lease with no takeover UI yet (just refuse writes from a non-holder with a clear error) — but this converges to roughly Option 1's Stage 1 anyway, with more infrastructure for similar effect |

Option 1 is the clear minimum-invasiveness choice: no format migration, smallest server-side change, and a real incremental/scoped rollout path that the other three options either can't match (3, 4 both need either format changes or new persistent server concepts) or only partially match (2's cheap "default-on" piece is genuinely low-risk, but its *detection* value is nil on its own — it only reduces how much a conflict destroys, not whether one is caught).

## Recommendation

**Implement Option 1 (revision/ETag optimistic concurrency) first, scoped to the self-hosted Node server as its initial shippable increment**, per the incremental path above. Reasons, given the actual codebase constraints found in this pass:

- It is the only option fully deliverable end-to-end (server + client) using code this repo actually controls, without waiting on or assuming anything about the account-sync hub.
- It requires no `RisuSave` on-wire format change and thus no migration story for existing users' saved data — the revision is header/sidecar metadata, not a new block type.
- It is genuinely incremental: the Node server can add the check behind an optional header so older clients (pre-upgrade, or any that never send it) keep working exactly as today (unconditional write) — a real backward-compatible rollout, not a flag-day format cutover.
- It directly closes the single most acute mitigation gap Report 05 found: the self-hosted Node server currently has *zero* mitigation of any kind (weaker than account-sync's unverified-but-plausibly-present session machinery, and weaker than the same-browser BroadcastChannel nag) — this is the backend where "no protection at all" is fully confirmed, not merely suspected, so it is also the backend where a fix is most clearly overdue.
- It composes cleanly with later work: Option 2's blast-radius reduction (per-block revisions) and even a future Option 4-style lease (a lease is close to "a revision only one holder may move") can both build on the revision infrastructure Stage 1 introduces, rather than being thrown away by it.

### Sketch of the first concrete increment (not implemented — sizing only, comparable to other Roadmap phase entries)

Proposed as a new Phase-1.5-Tier-B sub-item, similar in granularity to existing Roadmap phase entries:

1. **`server/node/server.cjs`**: add a small per-file revision store (e.g. a single `revisions.json` map, hex-path → monotonic counter, updated via the same atomic-rename pattern the write handler itself already uses). Add an in-process per-key critical section (e.g. a `Map<string, Promise>` queue keyed by hex `filePath`) so that for any given key, one request's full read-revision → compare → write → increment-revision sequence always completes before the next queued request for that same key begins its own — this is what actually closes the race (see the correction in the Option 1 section above; a plain sequential `if` check inside the handler is not sufficient on its own). `/api/read` returns the current revision in a response header. `/api/write` accepts an optional `if-match-revision` header; if present and it doesn't match the stored revision, respond `409` with the current revision (and optionally current content) instead of writing; if absent, behave exactly as today (back-compat). On a successful write, increment the stored revision, inside the same critical section.
2. **`src/ts/storage/nodeStorage.ts`**: `getItem` captures the revision header into a small in-memory cache keyed by storage key; `setItem` sends the last-known revision (if any) as `if-match-revision`, and throws a distinguishable `NodeStorageConflictError` (analogous to the existing `AccountSyncCacheMismatchError` pattern already established in `accountStorage.ts`) on a `409`, instead of the generic `"setItem Error"` string.
3. **`src/ts/globalApi.svelte.ts`**, `saveDb()`: catch `NodeStorageConflictError` specifically in the existing `catch` block (lines 601-622) and surface a clear "your device is out of date with the server" prompt (reusing the existing `alertNormalWait` pattern from the BroadcastChannel branch at lines 393-398). **[Corrected — Codex round 1]** This step needs more than reusing `mergeUnsavedChanges` and reloading, per the correction above: `mergeUnsavedChanges` only preserves dirty *identifiers* in memory, and reloading discards the actual in-memory edits those identifiers point at, so "safely queued" is not accurate without further work. The first shippable version of this increment should therefore either (a) avoid offering a reload at all — keep the tab running, show a non-blocking "server has a newer version, your changes could not be saved yet" toast, and let the existing retry loop keep re-attempting the write with a freshly-read revision (simplest, no new durable-storage work, but a less clear resolution path for the user), or (b) if a reload-based UX is wanted, first persist the pending `toSave`-covered edits to a durable local store (e.g. a dedicated `localforage` key) *before* prompting, and restore from it after reload. Option (a) is the smaller, more honestly-scoped version of this increment; (b) is a reasonable follow-up once (a) has shipped and the UX is validated.
4. **Verification**: this increment is testable entirely locally — run two clients against one self-hosted Node server instance, both editing, and confirm the second writer gets a `409`-driven prompt instead of a silent overwrite, and specifically confirm (via a synchronized/concurrent test, not just a serial one) that two requests racing at the comparison barrier cannot both succeed. This also complements the separately-landed (uncommitted, in-progress as of this report) atomic temp-file-rename fix to `/api/write` noted in the correction at the top of this report — that fix addresses torn writes, this increment addresses conflict *detection*, and both are needed for the Node server to be considered hardened against concurrent writers.

This increment deliberately excludes account-sync, Tauri (single-process, not multi-writer-capable in the way that matters here since it bypasses shared storage entirely per Report 05 section 4), and any UI beyond the one new prompt — sized to be its own shippable phase, not bundled with Option 2/3/4 work.

### Where this is a product decision, not a technical one

- **Detect-and-refuse (Option 1/4) vs. true concurrent merge (Option 3):** whether losing a concurrent-edit race should always require a human to notice and reload, or whether the product should invest in preserving both edits automatically, is a product call about how common genuine simultaneous multi-device editing is for this app's real users — not something this investigation can resolve from code alone. This report's recommendation (Option 1) is conditional on "detect-and-refuse is an acceptable UX for now"; if the project owner determines true concurrent editing is a hard requirement, Option 3 becomes necessary despite its much higher cost, and Option 1's revision infrastructure would still be reusable as a building block for it.
- **Silent block vs. explicit takeover (Option 1's simple prompt vs. Option 4's lease+UI):** Option 1's park-and-prompt is less polished than Option 4's proposed "Take over / View read-only" UI. Whether the extra lease/UI investment is worth it over Option 1's simpler save-time conflict prompt is a UX judgment call for the project owner, not a feasibility question — this report recommends starting with Option 1's simpler mechanism and revisiting Option 4's UI investment only if user feedback shows the save-time prompt is too disruptive.
