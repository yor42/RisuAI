# Save/Persistence Reliability — Deep-Dive (Second Pass)

Scope: everything the first pass (`Agents/Reports/02-persistence-reliability.md`) did *not* cover — secondary storage backends, the self-hosted Node server's actual file-write code, import/restore flows, `saveDbKei()`, and the encode/decode error-handling gaps. Read-only static analysis (Read/Grep only). Confirmed that the Phase 0 fix landed as described: `saveDb()` now has `mergeUnsavedChanges` (`src/ts/globalApi.svelte.ts:435-448`) and a `toSave: toSaveType | null` guard (`globalApi.svelte.ts:465`), and `catch` now sets `changed = true` and folds `toSave` back in (`globalApi.svelte.ts:533-543`) — not re-litigated below except where it interacts with a new finding.

> **Cross-validated** via an independent Codex adversarial-review pass (`Agents/CodexReviews/02-persistence-reliability-deepdive.codexreview.md`). Verdict: **partially confirmed with corrections**. `saveDbKei()`'s fire-and-forget behavior, the never-reset `changeTracker` booleans, and (with narrowing) the localforage/inlay findings are confirmed. Four corrections were applied in place below: the `/api/remove` batch-delete mechanism was misdescribed (the actual failure mode is different, though still a real bug — see Lead 2); the backup-restore finding overstated both decoder certainty and confirmation timing; the "no error handling" claim for the three secondary localforage stores was too blanket (`risuSaveCacheForage` writes are in fact covered by the existing save-retry path); and the `setDatabaseLite` call-site count was wrong (there's a third call site in `plugins.svelte.ts` not originally found, and the KEI-restore attribution was already self-corrected in the original draft's "Additional findings" section, which the executive summary and Lead 3 text hadn't been updated to match).

## Executive summary

- **`saveDbKei()` is fire-and-forget and can silently break KEI auto-backup with zero user-facing signal.** `src/ts/kei/backup.ts:83-104`: the `fetch(...)` call at line 91 is neither `await`ed nor given a `.then()/.catch()`, so any network failure becomes an **unhandled promise rejection**, not something the wrapping `try/catch` (lines 84-103) can ever see — that `catch` only guards the synchronous setup code above the `fetch` call. `saveDb()`'s main loop then does `await saveDbKei()` (`globalApi.svelte.ts:531`), but since `saveDbKei` itself isn't `async` in a way that awaits the fetch, that `await` resolves immediately regardless of whether the KEI backup actually succeeded. A user with `db.account.kei` enabled can have every KEI backup silently fail (e.g. server down, network blip) with no error, no retry, no UI indication — only a browser console "unhandled rejection" warning nobody sees.
- **The self-hosted Node server (`server/node/server.cjs`) does non-atomic, unlocked file writes.** `/api/write` (`server.cjs:1264-1291`) calls `fs.writeFile(path.join(savePath, filePath), fileContent)` directly onto the live filename — no write-to-temp-then-rename, no advisory lock, no `O_EXCL`/flock. A crash, container OOM-kill, or power loss mid-write can leave a truncated/corrupt save file on disk, and two concurrent writes to the same key (e.g. two browser tabs pointed at the same Node server) can interleave with no protection at all. This mirrors the main report's "no atomicity at the backend layer" finding but for a code path the first pass never reached.
- **`/api/remove`'s batch-delete path is broken, but [corrected] not via the multi-response mechanism originally described.** The client (`nodeStorage.ts:127-137`'s `removeItem(key: string|string[])`) hex-encodes the **entire `$$`-joined key string as one blob** (`Buffer.from(key.join('$$'), 'utf-8').toString('hex')`) before sending it as the `file-path` header. The server (`server.cjs:1219`) then does `req.headers['file-path']?.split('$$')` **on the still-hex-encoded header, before any hex-decoding** — and a hex string can never contain a literal `$` character, so this split always yields a single-element array containing the whole composite hex blob, not N separate paths. The one loop iteration that does run passes that composite (non-decoded, multi-key) string to `fs.rm(path.join(savePath, filePath))`, which fails because no file on disk is named after a hex-encoding of several `$$`-joined keys — the failure is caught and passed to `next(error)`, so a batch delete simply **fails outright for all keys**, not "silently masks partial success after the first." The `res.send()`-inside-the-loop pattern *would* be a real multi-response bug if the loop ever iterated more than once, but as currently reachable from this client, it doesn't. This is still reachable in practice and still broken: `src/ts/process/coldstorage.svelte.ts:283-291` calls `(storage as NodeStorage).removeItem(deleteKeys)` with a multi-key array for Node-server cold-storage cleanup — **and does so without `await`**, so even this (corrected) failure mode is invisible to the caller (see below).
- **`backuplocal.ts`'s `LoadLocalBackup()` can overwrite the live, in-memory database with corrupted or completely un-decrypted data — confirmed, but [corrected] with two overstated details fixed.** If account-encrypted backup decryption fails (`backuplocal.ts:533-543`), the code logs the error, shows a toast, and **proceeds anyway** with `db` still pointing at the *original, still-encrypted* byte buffer (`db` is only reassigned inside the `try`, `backuplocal.ts:536-537`; on `catch` it silently keeps the pre-decrypt value). That buffer is then fed into `decodeRisuSave(db)` (`backuplocal.ts:544`), whose fallback ladder (raw/compressed/stream/risusave headers, then three more guesses — `risuSave.ts:623-666`) is **not guaranteed to "produce something"** — its final `unpackr.decode` attempt can still throw, and destructive persistence only happens if a fallback strategy *happens* to decode the ciphertext into something that parses without error (a real risk given how permissive `JSON.parse`/`unpackr` are on dense binary/text formats, but not a certainty). If a fallback does produce a value, it's handed to `setDatabaseLite(dbData)` (`backuplocal.ts:559` → `database.svelte.ts:724-726`), which does effectively no meaningful validation (`DBState.db = data`) — contrasted with `setDatabase()` (`database.svelte.ts:30` onward), which is more accurately described as *normalizing/defaulting* dozens of fields than performing true schema validation, but still catches far more malformed shapes than `setDatabaseLite`'s bare assignment. The result is then persisted back over the real `database/database.bin` (`backuplocal.ts:562`/`569`). **Correction**: this does *not* happen "before any confirmation dialog" — `backuplocal.ts:555-557` does show a `confirmIncompleteColdStorageOperation` dialog before the assignment/persist — but that dialog is about cold-storage completeness, unrelated to whether the decoded data is actually valid, so it provides no real protection against this specific failure mode; a user could click through it without it ever flagging the underlying decrypt failure. This remains the single most concrete "import corrupts live state" finding of this pass, just with the certainty and gating details corrected.
- **`changeTracker.loadouts` / `.plugins` / `.pluginCustomStorage` are set to `true` by their `$effect`s (`globalApi.svelte.ts:388,393,398`) but are never reset to `false` anywhere** — not in the pre-write trim (`globalApi.svelte.ts:483-486`, which only resets `character`/`chat`/`botPreset`/`modules`), not in `mergeUnsavedChanges` (`globalApi.svelte.ts:435-448`, same four fields only). This isn't data loss, but it silently defeats the incremental-save optimization for these three blocks: once touched, they are re-serialized on *every* subsequent save cycle for the rest of the session.
- **[corrected]** Two of three localforage instances outside the main DB save path (`inlay`, `plugin`) write with no local error handling and no quota awareness — same class of gap as the main path, not yet fixed anywhere. The third, `risuSaveCacheForage`, is **not** in the same boat: its writes are `await`ed inside the same `encodeBlock`/`set()` call chain that `saveDb()`'s top-level retry logic already covers (see the dedicated `risuSaveCacheForage` finding below), so its failures are handled, not silently lost — the original executive-summary framing incorrectly grouped it with the other two. For the `plugin` store specifically, its `getItem`/`setItem` methods do reject on failure rather than swallowing errors locally, so whether a given failure is actually "uncaught" depends on whether each of the plugin-bridge call sites that invoke them awaits and handles that rejection — this wasn't fully traced caller-by-caller, so treat the `plugin` store's gap as "no defense at the storage layer itself," not a confirmed uncaught-failure demonstration for every caller. Chat-attachment (`inlay`) assets additionally have no automatic garbage collection at all, so deleting a message/chat that referenced an inlay image leaves the blob in IndexedDB forever.

## Lead 1 — Storage backends not yet examined

### `inlay` localforage instance (`src/ts/process/files/inlays.ts:30-33`)
**CONFIRMED BUG (reliability gap, same class as main path).**
- `postInlayAsset`, `writeInlayImage`, `saveInlayedSignature`, `setInlayAsset` (`inlays.ts:35-81`, `83-125`, `136-144`, `217-219`) all call `inlayStorage.setItem(...)` with a plain `await` and no try/catch of their own. None of the traced call sites wrap the call either: `src/ts/process/inlayScreen.ts:28`, `src/ts/process/files/multisend.ts:291`, `src/ts/process/scriptings.ts:402,427,454`, `src/ts/process/triggers.ts:1553,1891`, `src/ts/process/request/google.ts:742` are all bare `await writeInlayImage(...)`/`await postInlayAsset(...)` with no local `try/catch`. A `QuotaExceededError` (large video/audio attachments are stored as raw `Blob`s with no size cap — `inlays.ts:52-64`, `66-78`) propagates as an uncaught rejection up whatever async chain called it (chat send, script execution, trigger processing), aborting that operation with no attachment-specific error message — the user just sees "something failed," not "storage is full."
- **No automatic garbage collection.** `removeInlayAsset` (`inlays.ts:221-223`) is only ever called from `src/lib/Playground/PlaygroundInlayExplorer.svelte:56,71` — a manual admin/debug UI. Grep-confirmed: no caller in the message-deletion, chat-deletion, or character-deletion code paths. Every inlay image/audio/video/signature ever created (`postInlayAsset`/`writeInlayImage`/`saveInlayedSignature`) persists in the `inlay` IndexedDB store even after the chat message referencing it is deleted, edited away, or the character is removed — unbounded growth over the life of the profile, and a plausible contributor to the storage-quota exhaustion the first report already flagged as unhandled.
- The migration path in `getInlayAssetBlob` (`inlays.ts:190-206`) that converts legacy base64-string assets to `Blob` on read (`setInlayAsset(id, {...img, data})`, line 200) is itself an unawaited fire-and-forget write inside a function whose own return doesn't wait for it — a small, low-impact instance of the same "write not confirmed before caller proceeds" pattern.

### `plugin` localforage instance / `SafeLocalPluginStorage` (`src/ts/plugins/pluginSafeClass.ts:4-7, 51-77`)
**CONFIRMED — separate, previously-unexamined persistence surface, same gap class.**
- This is a *third* distinct persistence surface for plugin data, separate from both `db.pluginCustomStorage` (saved as part of the main block-encoded DB, see `risuSave.ts:175-180`) and the `inlay` store. It is exposed to plugin sandboxes via the `_getPluginStorage`/`_setPluginStorage` aliases (`src/ts/plugins/apiV3/v3.svelte.ts:1331-1332`).
- `getItem`/`setItem`/`removeItem`/`clear` (`pluginSafeClass.ts:53-76`) have no local error handling; a failing `pluginStorage.setItem` (e.g. quota, or a plugin storing a huge blob) rejects straight back through the plugin bridge with no plugin-storage-specific messaging added at this layer.
- **[corrected]** Whether that rejection ends up genuinely uncaught depends on each plugin-bridge caller — this pass did not trace every call site through to confirm none of them `await`/`.catch()` it, so "no error handling at the storage layer" is the confirmed claim, not "confirmed uncaught in practice for every caller." Not itself confirmed to cause data loss beyond what any uncaught-rejection failure mode already implies — flagged as the same class of storage-layer gap as the main path, not a new failure class.

### `risuSaveCacheForage` (`src/ts/storage/risuSave.ts:121-123`)
**CHECKED — unbounded growth confirmed; no correctness bug found.**
- Written on every block encode (`risuSaveCacheForage.setItem(...)`, `risuSave.ts:370-374`), read back only when the decoder needs a directory-listed block that wasn't inline in the current buffer (`risuSave.ts:499-513`, the "remote save via cache" indirection for the incremental save model).
- **No pruning/eviction logic exists anywhere** for this store — grep-confirmed no `removeItem`/`clear` call on `risuSaveCacheForage` in the codebase. Every character/preset/module/plugin/loadout block ever saved accumulates here permanently (keyed by name, so re-saves of the *same* key overwrite rather than duplicate — growth is bounded by "number of distinct blocks ever created," not "number of saves," so this is milder than the `inlay` store's growth, but still never shrinks even after characters are deleted).
- The `setItem` call is `await`ed and sits inside the same `encodeRawBlock`/`encodeBlock`/`set()` call chain that's already wrapped by `saveDb()`'s top-level `try/catch` (`globalApi.svelte.ts:466-554`), so a failure here is not silently swallowed — it triggers the same (now-fixed) retry path as any other save failure. **No new bug beyond unbounded growth.**

### `pluginCustomStorage` field / plugin-specific persistence under `src/ts/plugins/`
**CHECKED-NO-ISSUE for the DB-embedded field itself.**
- `db.pluginCustomStorage` is not a separate storage backend — it's block `pluginStorage` inside the main block-encoded save (`risuSave.ts:175-180` write, `risuSave.ts:277-284` incremental re-encode, `risuSave.ts:550-553` decode), subject to exactly the same atomicity/quota characteristics as the rest of the main DB, already covered by the first report. No additional backend-specific risk found here; the actual separate backend is `pluginSafeClass.ts`'s `plugin` localforage instance, covered above.

## Lead 2 — Self-hosted server (`server/node/server.cjs`)

**CONFIRMED BUG.**
- **No atomic write.** `/api/write` (`server.cjs:1264-1291`): `await fs.writeFile(path.join(savePath, filePath), fileContent)` writes directly to the live filename. No temp-file-then-`rename()` pattern, no `fsync`. A crash/power-loss/OOM-kill mid-write leaves a truncated or zero-length file on disk that the next `/api/read` (`server.cjs:1183-1213`) will happily serve back to the client as-is — the client's `decodeRisuSave` fallback ladder (`risuSave.ts:623-666`) will then either throw (surfacing as a generic load failure) or, per the Lead 5 finding below, potentially parse to something garbage without throwing.
- **No concurrency control.** No file lock, no `O_EXCL`, no in-process write queue/mutex keyed by `filePath`. Two concurrent `/api/write` requests for the same `file-path` header (e.g. two tabs/devices pointed at the same self-hosted server, or the primary DB write racing a remote-block write) can have their two `fs.writeFile` calls interleave at the OS buffer-cache level with no serialization guarantee from this server code; whichever `write()` syscall lands last wins, with no merge or conflict detection (contrast with `AccountStorage`'s `x-risu-save-date` staleness header, which the Node-server path doesn't have — noted in the first report as "simpler, no staleness headers," now confirmed as *the reason why* on the server side: there's nothing server-side to check against even if the client sent one).
- **`/api/remove`'s batch-delete path fails for every key, not just after the first — [corrected], see the executive summary correction above for the exact mechanism.** The handler's `res.send()`-inside-the-loop pattern (`server.cjs:1236-1242`) *would* independently be a multi-response bug (`ERR_HTTP_HEADERS_SENT` on the second+ send, silently absorbed by Express) if the loop ever ran more than once — but as actually invoked by this client, `req.headers['file-path']?.split('$$')` (`server.cjs:1219`) is applied to a header that is *still hex-encoded* at that point, and hex strings cannot contain a literal `$`, so the split always produces exactly one element: the whole composite hex blob. That single iteration's `fs.rm(path.join(savePath, filePath))` targets a nonexistent composite-named file and fails outright (caught, passed to `next(error)`). Net effect: a batch delete of N files deletes **zero** of them and returns a single error response — not "N-1 silently unconfirmed successes." The client-side visibility problem is real either way: `nodeStorage.ts`'s `removeItem` does throw on a non-2xx response (`nodeStorage.ts:136-137`), so the failure *is* signaled to whoever calls it and awaits it — which is precisely why the next bullet's missing `await` at the actual call site matters.
  - **Reachable in practice**: `src/ts/process/coldstorage.svelte.ts:283-291` calls `(storage as NodeStorage).removeItem(deleteKeys)` with a multi-element array when `isNodeServer` — this is the exact `$$`-joined batch path (`nodeStorage.ts:127-137` joins with `key.join('$$')`) that always fails per the correction above.
  - **Compounding bug at the call site**: that same call, `coldstorage.svelte.ts:287`, is **not awaited** (`(storage as NodeStorage).removeItem(deleteKeys)` with no `await`, inside a `try {}` that has nothing async to actually guard — line 284-290). Since the removal always fails (per the corrected server-side finding) and the rejection is never awaited, it becomes an unhandled promise rejection, invisible to the `catch (error) { console.error(error) }` at line 288-289 which can only catch synchronous throws. This is a second instance of the "fire-and-forget write whose failure is invisible" pattern found independently at `saveDbKei()` — and, per the correction above, it's masking a call that would *always* fail today for Node-server cold-storage cleanup, not an occasional partial-failure case.
- **Auth/`isHex` checks are present and look sound** for path traversal (`isHex(filePath)` gate before every filesystem operation, `server.cjs:1196,1228,1276`, backed by `savePath` = `path.join(process.cwd(), "save")`) — this wasn't in scope but was checked in passing since it sits right next to the write logic; **no path-traversal issue found**.
- `server/hono/` does not exist in this repo (`Glob` for `server/hono/**` returns nothing) — only `server/node/` is present, so there is no second server implementation to cross-check.

## Lead 3 — Import/export and backup-restore flows

**CONFIRMED BUG** (see Executive Summary for the core finding). Details:

- **`backuplocal.ts`'s `LoadLocalBackup()`** (`backuplocal.ts:405-585`) streams a `.bin` local-backup file in 1MB chunks, parsing a simple TLV (name-length/name/data-length/data) framing as it goes (`backuplocal.ts:447-524`). Per-chunk parsing is defensive (`offset + 4 + nameLength > remainingBuffer.length` bounds checks, `446-463`) and a genuinely truncated/mid-stream-cutoff file just means the outer chunk-read loop ends with a partial trailing entry silently dropped (no error) — reasonable behavior for a stream parser, not itself a corruption vector.
- The **real risk is post-parse, pre-persist**: once `pendingDatabase` bytes are collected, the flow is decrypt-if-needed → `decodeRisuSave` → `setDatabaseLite` → **write back to the live save slot** → reload. **[corrected]** There is a confirmation dialog in between (`confirmIncompleteColdStorageOperation`, `backuplocal.ts:555-557`, shown before the assignment/persist) — the original draft's "before any confirmation dialog" was wrong — but that dialog is about cold-storage completeness and has nothing to do with whether the decoded `Database` object is actually well-formed, so it provides no real protection against this specific failure mode.
  - Decrypt failure (wrong/rotated server-side crypto key, corrupted `encryption.risudat` metadata, network failure fetching the key) is caught and only downgrades to a **user-facing warning**, not an abort: `backuplocal.ts:539-542` logs+toasts "will attempt to load it without decryption" and falls through to decode the **still-encrypted** ciphertext as if it were a valid save.
  - `decodeRisuSave` (`risuSave.ts:623-666`) tries hard not to give up: header check → 4 progressively more desperate fallback attempts (unpackr on raw bytes → strip a hardcoded legacy `"\0\0RISU"` prefix and unpackr → `fflate.decompressSync` + `JSON.parse` → `fflate.decompressSync` + `unpackr`). **[corrected]** This is not guaranteed to "produce something" — the final fallback's `unpackr.decode` call can itself throw, and if all four strategies throw, that final throw propagates to the caller (safe, not silent). The genuinely dangerous case is narrower than "decode always succeeds": it's specifically when ciphertext, piped through `unpackr.decode()` or `JSON.parse()`, *happens* to decode into some structurally-valid-but-semantically-meaningless JS value without throwing — msgpack and JSON are both dense-enough formats that this isn't guaranteed, but it's a real enough possibility (both formats are comparatively permissive about reinterpreting arbitrary bytes) that the destructive-persist risk below is conditional on it, not certain.
  - **If** a fallback does produce a value, it's passed to `setDatabaseLite(dbData)` (`database.svelte.ts:724-726`) — a one-line `DBState.db = data` with effectively no meaningful validation. **[corrected]** Contrasting this with `setDatabase()` (`database.svelte.ts:30` onward): that function is more accurately described as normalizing/defaulting dozens of fields (`?? defaultValue`-style assignments) than performing true schema/semantic validation — it would still catch many malformed shapes by virtue of touching each field, but "validated" overstates what it actually guarantees. The inconsistency between the *normal* app-boot decode path (`setDatabase()`, at least field-touching) and this *restore* path (`setDatabaseLite()`, bare assignment) is still real and still the core of this finding. Confirmed via grep: `setDatabaseLite` has **3** non-definition call sites in `src/ts` — `backuplocal.ts:559`, and (newly found on re-check) calls in `src/ts/plugins/plugins.svelte.ts` — **not** `src/ts/kei/backup.ts:63`, which actually calls the validated `setDatabase()` (see the Additional Findings section below, which already corrected this specific point in the original draft — the executive summary and this paragraph simply hadn't been updated to match; now reconciled).
  - The corrupted/garbage `db` (when the conditional decode-succeeds-with-garbage case occurs) is then immediately written back over the *actual* `database/database.bin` (`backuplocal.ts:562` Tauri / `569` web) before the process reloads — so even backing out (killing the app, not confirming anything further) does not save the user at that point, because the overwrite already happened synchronously before `relaunch()`/`location.search = ''`.
- **`characterCards.ts` character-card imports** (`.risum`/`.risup`/`.charx`/PNG-embedded cards, `characterCards.ts:32-720` region, entry points `importCharacterCardSpec` at line 720): unlike the backup-restore flow, these go through typed parsing of a `CharacterCardV2Risu`/`CharacterCardV3` object and are appended as a *new* character rather than replacing the whole live `DBState.db`, which structurally limits blast radius — a malformed card can produce a broken *character* but can't by itself clobber the rest of the database the way `LoadLocalBackup` can. Did not trace every field-level default/validation in `importCharacterCardSpec` (very large function, low marginal value given the time budget and the much sharper finding above) — **COULDN'T FULLY DETERMINE** whether every malformed-field case is defaulted safely, but the blast-radius argument means this is a materially smaller risk class than the whole-DB-replace path in `backuplocal.ts`/`kei/backup.ts`, so it wasn't pursued further.
- **`drive.ts`'s `loadDrive()`** was already covered by the first report (race with the autosave loop) — not re-examined here except to confirm it also calls `setDatabaseLite`-style raw assignment via `setDatabase`... actually **checked**: `drive.ts` uses `setDatabase()` (validated), not `setDatabaseLite()` — so the cloud-drive restore path does *not* have this specific unvalidated-overwrite bug; it's isolated to the two local/manual restore paths (`backuplocal.ts`, `kei/backup.ts`) identified above.

## Lead 4 — `saveDbKei()`

**CONFIRMED BUG** (see Executive Summary). Full detail:

`src/ts/kei/backup.ts:82-104`:
```
let lastKeiSave = 0
export function saveDbKei() {
    try{
        let db = getDatabase()
        if(db.account.kei){
            if(Date.now() - lastKeiSave < 60000 * 5){ return }
            lastKeiSave = Date.now()
            fetch(keiServerURL() + '/autobackup/save', { ... })   // <-- not awaited, no .then/.catch
        }   
    }
    catch(e){}
}
```
- `saveDbKei` is **not even declared `async`**, so `saveDb()`'s `await saveDbKei()` (`globalApi.svelte.ts:531`) awaits a plain, already-resolved return value — it does not and cannot wait for the `fetch` to complete or fail.
- The `fetch(...)` call's returned promise is discarded. If the KEI server is unreachable, returns a non-2xx, or the request throws asynchronously, nothing in this function observes it. The outer `try/catch` only covers the synchronous body (the `db.account.kei` check, the rate-limit gate, and the *initiation* of the fetch) — by the time the fetch's promise actually rejects, the `try` block has long since exited.
- Practical effect: `lastKeiSave = Date.now()` is set **before** the fetch is known to succeed (line 90, before line 91's fetch), so even if the request fails, the 5-minute rate-limit gate (line 87) is still consumed — a failed KEI backup blocks the *next* attempt for a full 5 minutes with no indication anything went wrong, compounding the silence.
- No retry, no backoff, no user-facing error, no console log of the failure (an unhandled rejection is the *only* trace, and only if devtools happen to be open). This is a strictly worse failure mode than the (now-fixed) main autosave path, which at least logs and eventually alerts.
- `autoServerBackup()` (`kei/backup.ts:6-80`), the sibling function for interactively *restoring* from a KEI backup, is properly awaited/handled throughout (each `fetch` is awaited and checked via `res.status`) — the bug is specific to the fire-and-forget auto-save path, not the whole file.

## Lead 5 — Encryption/decompression error-handling gaps

**CORRECTED PREMISE, then CONFIRMED BUG under a different name.**
- There is **no encryption in the core save format itself.** Grepped `src/ts/storage/` for `encrypt|decrypt|AES|crypto.subtle`: the only hits are `nodeStorage.ts` (JWT signing/verification for API auth, unrelated to save-data confidentiality) and `database.svelte.ts` (incidental). `risuSave.ts` only ever does **compression** (gzip via `CompressionStream`/`fflate`), never encryption, for the block-save format (`RisuSaveEncoder`/`RisuSaveDecoder`, `risuSave.ts:1-716`). The "encryption" that does exist in the codebase is narrowly scoped to the **account-synced local-backup export/import** path: `backuplocal.ts:164-170` (`encryptBuffer`) and `:533-543` (`decryptBuffer`), using a server-fetched per-timestamp key from `sv.risuai.xyz/cryptokey`. So "encrypted-but-corrupted save silently decrypts to garbage" is not a risk for the everyday autosave path (nothing there is encrypted) — it *is* a risk for the local-backup restore path, and that exact scenario is the bug already detailed under Lead 3 (`backuplocal.ts:533-543` swallowing decrypt failure and decoding the still-encrypted bytes anyway).
- **The genuinely relevant "succeeded with bad data" risk for the everyday save path is different: no per-block checksum/integrity check.** `RisuSaveDecoder.decode` (`risuSave.ts:432-620`) validates a block's *framing* (type/name-length/data-length bytes) but never validates the *content* beyond "does `JSON.parse` throw." A single-bit flip inside an otherwise-well-framed block (e.g. bad IndexedDB read, disk bitrot on Tauri, a bug elsewhere corrupting the in-memory buffer before it's written) that happens to land inside a JSON string/number value rather than breaking JSON syntax will parse successfully into a `Database`/`character` object with **silently wrong field values** — no length checksum (CRC32 etc.) exists anywhere in the block format (`encodeRawBlock`, `risuSave.ts:345-376`) to catch this class of corruption. This is a real gap distinct from the already-documented "block fails to parse → silently vanishes" finding in the first report: this is "block parses fine → silently wrong."
- **Compression-stream failure handling**: `checkHeader`'s `compressed`/`stream` branches (`risuSave.ts:39-50`, `624-648`) and the per-block `DecompressionStream` path (`risuSave.ts:458-467`) all sit inside `try/catch` blocks that either fall through to the next fallback strategy (`decodeRisuSave`, `risuSave.ts:650-666`) or, for a single corrupt block, get caught and the block dropped (`risuSave.ts:476-478`, `605-611`) — consistent with, not worse than, the first report's finding. **CHECKED-NO-ISSUE**: decompression failure is not a silent-garbage case, because `DecompressionStream` reliably throws on malformed gzip data (unlike `JSON.parse`, which is comparatively permissive) — the corrupted-buffer risk is concentrated in the *post-decompression* `JSON.parse` step, not the decompression step itself.
- **`encodeRisuSaveCompressionStream`** (`risuSave.ts:69-81`) and `encodeRawBlock`'s compression branch (`risuSave.ts:348-356`) both call `writer.close()` **without `await`** (`risuSave.ts:75`, and implicitly via the same pattern at `353`) before reading from `cs.readable` via `new Response(cs.readable).arrayBuffer()`. This is a narrower, functionally-harmless instance of the same un-awaited-`close()` shape flagged for `OpfsStorage` in the first report — but here it does **not** carry the same risk, because `Response(readable).arrayBuffer()` already fully drains the readable side of the transform stream, which is what actually determines when this function's returned promise resolves; the un-awaited `close()` on the writable side doesn't gate anything downstream the way `OpfsStorage`'s file-swap-on-close does. **CHECKED-NO-ISSUE**, flagged only for completeness/consistency (a future refactor that assumes "un-awaited close = safe pattern here" could get bitten if this code is ever restructured to not drain synchronously).

## Additional findings outside the numbered leads

1. **`changeTracker.loadouts`/`.plugins`/`.pluginCustomStorage` are never reset, defeating incremental save for those three blocks for the rest of the session once touched once.** `globalApi.svelte.ts:388,393,398` set them `true`; the pre-write trim (`483-486`) and `mergeUnsavedChanges` (`435-448`) only handle `character`/`chat`/`botPreset`/`modules`. Not a correctness bug (data is still saved correctly), but a perf regression that compounds the first report's "extra backup file every save" quota-pressure concern — three more blocks get needlessly re-serialized and rewritten every single autosave cycle after the first touch.
2. **`unMigrationAccount()` (`src/ts/storage/accountStorage.ts:193-219`) has no error handling around its per-key copy loop** (`await MigrationStorage.setItem(key, await forageStorage.getItem(key))`, line 204) — if any single key's copy throws (quota, corrupt source value), the whole migration aborts partway with some keys copied and others not, then falls through to `location.reload()` at the end of the function only if no exception occurred; but there's no `try/catch` around the loop at all, so an exception here just becomes an uncaught error, leaving `localStorage`'s `accountst`/`dosync` flags in whatever partial state they were in before the throw (the flag mutations at lines 216-218 are *after* the loop, so a failure mid-loop is at least "safe" in the sense that the account-mode flags aren't flipped — but the user is left in a broken state with a partially-migrated store and only a console error to explain it).
3. **`autoServerBackup()`'s restore branch also uses the unvalidated `setDatabase`… correction, actually uses `setDatabase`, checked directly**: `kei/backup.ts:63` calls `setDatabase(await res.json())` — **this one is fine**, it uses the validated `setDatabase()`, not `setDatabaseLite()`. (Flagged during Lead 3 investigation; corrected here after re-reading — only the *auto-save* half of `kei/backup.ts`, i.e. `saveDbKei()`, has the fire-and-forget bug; the restore half is sound.)

## Recommendations, ranked by (impact, effort)

1. **(High impact, low effort) Fix `saveDbKei()` to actually await and handle its fetch.** `src/ts/kei/backup.ts:83-104` — make the function `async`, `await fetch(...)`, check `res.status`, and only advance `lastKeiSave` on confirmed success (move `lastKeiSave = Date.now()` after a successful response, not before the request). Currently a KEI-enabled user can have auto-backup silently dead for an entire session with no signal at all.
2. **(High impact, medium effort) Validate before `setDatabaseLite()`, or stop using it for restore paths.** `src/ts/drive/backuplocal.ts:559` and `src/ts/kei/backup.ts` restore path — either route through `setDatabase()` (which has the `checkNullish` defaulting) or add an explicit shape check (e.g. `Array.isArray(db.characters)`) before accepting decoded restore data, and **abort** (don't proceed to decode-and-overwrite) when decryption fails in `backuplocal.ts:533-543`, rather than falling through to decode the still-ciphertext buffer.
3. **(High impact, low effort) [corrected priority] Fix the batch-delete path so it actually works for more than zero keys.** Both sides need a fix: the client (`nodeStorage.ts:127-137`) should hex-encode each key separately (or send a JSON array) instead of hex-encoding one `$$`-joined blob, and the server (`server.cjs:1219`) should hex-decode the header before splitting on `$$` — as it stands today, Node-server cold-storage batch cleanup doesn't just risk masking partial failures, it fails unconditionally. While fixing this, also send a single aggregated response after the loop instead of calling `res.send()` per iteration (`server.cjs:1236-1242`), so the pre-existing multi-response bug doesn't resurface once multi-key batches actually reach the loop.
4. **(Medium impact, low effort) Await the Node-server batch-remove call.** `src/ts/process/coldstorage.svelte.ts:287` — add `await` in front of `(storage as NodeStorage).removeItem(deleteKeys)` so its existing `try/catch` (lines 284-290) can actually catch failures instead of letting them become unhandled rejections. This surfaces the always-fails bug above; it should land alongside item 3, not as a substitute for it.
5. **(Medium impact, medium effort) Add write-then-rename atomicity to `server/node/server.cjs`'s `/api/write`.** Write to a temp path in the same directory, `fsync`, then `fs.rename()` over the target — standard atomic-write pattern, closes the torn-write risk on crash/power-loss for self-hosted deployments.
6. **(Medium impact, medium effort) Wire up automatic inlay-asset garbage collection.** `src/ts/process/files/inlays.ts` — hook `removeInlayAsset` into message/chat/character deletion paths (or add a periodic sweep comparing `listInlayAssets()` against inlay IDs still referenced by any character's chats), instead of relying entirely on the manual Playground explorer UI.
7. **(Low-medium impact, low effort) Reset `changeTracker.loadouts`/`.plugins`/`.pluginCustomStorage` after a successful write**, mirroring the existing `botPreset`/`modules` handling at `globalApi.svelte.ts:483-486` and `435-448`, to restore the intended incremental-save behavior for those three blocks.
8. **(Low impact, medium effort) Add a lightweight per-block checksum to the `RisuSave` block format** (`risuSave.ts:345-376` write / `432-479` read) — even a CRC32 of the raw block payload would let the decoder distinguish "parsed fine and is correct" from "parsed fine but is corrupted," which `JSON.parse`-success alone cannot do.
9. **(Low impact, low effort) Wrap `unMigrationAccount()`'s copy loop in a try/catch** (`src/ts/storage/accountStorage.ts:199-206`) with a clear error message, so a mid-migration failure doesn't leave the user in a silently half-migrated state.
