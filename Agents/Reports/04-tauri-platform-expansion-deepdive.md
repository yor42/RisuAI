The Rust plugin cfg-gating bug (Lead 1/2), the `public/token/` footprint (Lead 4), the 11-command sweep and `python311._pth` coupling, and the Lead 5 re-verification are all confirmed exactly. ## Executive Summary

- The full `#[tauri::command]` sweep of `src-tauri/src/main.rs` (11 commands, the file is the only `.rs` file in `src-tauri/src/`) found **two new confirmed compile-breaking bugs**, separate from the already-known `install_python`/Windows-only issue: `tauri_plugin_updater` and `tauri_plugin_deep_link` are registered **unconditionally** in `main()` (`src-tauri/src/main.rs:582`, `:585`) even though their crate dependencies are excluded for Android/iOS in `Cargo.toml` (`:36-37`, `:48-50`). Only `tauri_plugin_single_instance` is correctly wrapped in `#[cfg(desktop)]` (`main.rs:570-578`). An `android`/`ios` build of this crate as it stands today would fail to compile with "unresolved import"/"failed to resolve" errors on those two plugin references.
- Lead 3's premise — that `isTauri === true` will stop meaning "desktop" once Android ships — is **already an active bug today** in the sense that these call sites exist and are unguarded by any mobile check, though the exact failure mechanism needed **[corrected]**: three concrete spots call desktop-only Tauri window/plugin APIs guarded only by `isTauri`, with no `isMobile`/platform check: `appWindow.maximize()` (`src/ts/bootstrap.ts:61`), `changeFullscreen()` → `appWindow.setFullscreen()`/`isFullscreen()` (`src/ts/util.ts:223-229`, called from `bootstrap.ts:119`), and `checkRisuUpdate()` → `@tauri-apps/plugin-updater`'s `check()` (`src/ts/update.ts:48`, called from `bootstrap.ts:118`) — the last of which invokes a Rust plugin that literally isn't compiled into an Android build (see above). **Of these three, only `changeFullscreen()` is actually capable of aborting `loadData()`'s startup sequence**: `checkRisuUpdate()` wraps its own logic in a local try/catch (`update.ts:47-92`) that logs the error and resolves normally, so a failure there is contained and does *not* reach `bootstrap.ts`'s outer catch — it's a wasted, incorrectly-attempted call on Android, not a startup-aborting one. `appWindow.maximize()` (`bootstrap.ts:61`) is called without `await`/`.catch()`, so an async rejection there does not route into the surrounding synchronous `try` either — it would instead surface as an unhandled promise rejection, not a caught exception that skips later init. Only `changeFullscreen()` (`bootstrap.ts:119`, which *is* awaited) can actually propagate into `loadData()`'s outer `catch` (`bootstrap.ts:264-266`, which just calls `alertError(error)`) and skip the remaining init steps (`saveDb()`, `moduleUpdate()`, `cleanChunks()`, `alertTOS()` at `bootstrap.ts:255-262`) — assuming these window APIs actually reject on Android rather than resolve as no-ops, which is plausible but **unverified** (no Android build/runtime test was performed).
- A fourth `isTauri`-not-`isMobile` conflation: the MCP "stdio" transport in `src/ts/process/mcp/mcp.ts:103-111` gates arbitrary local-process spawning (`Command.create` from `@tauri-apps/plugin-shell`) behind `if(!isTauri){ throw ... }` only. This is fundamentally incompatible with Android's app sandbox (no shell, no `npx`/`uvx`/`node` on PATH, no permission to exec arbitrary binaries) — it would need an explicit desktop-only gate, not an `isTauri` gate, once Android ships.
- Bundle-footprint check (lead 4): `public/` is **95 MB**, of which **77 MB is `public/token/*`** — bundled LLM tokenizer files (`tokenizer.json`/`.model`), fetched lazily at runtime via relative `fetch("/token/...")` calls in `src/ts/tokenizer.ts:261-382`, but physically part of the built frontend (`dist/`) that Tauri embeds into every desktop app package today, and would need to ship inside an Android APK/AAB too since there's no evidence of an external CDN fallback for these paths. Individual files run up to 18 MB (`public/token/gemma/tokenizer.json`) and 13 MB (`public/token/cohere/tokenizer.json`). This is a real, non-trivial mobile-distribution cost worth flagging even though it's not a correctness bug.
- Lead 5 re-verification: `installPython()` in `src/ts/process/models/local.ts:10-29` **does** now check `install_python`'s boolean return and stops with `alertError(...)` (`local.ts:25-29`) instead of falling through to Windows-only steps — confirmed fixed. No other frontend caller of `install_pip`, `post_py_install`, `install_py_dependencies`, or `run_py_server` exists anywhere under `src/` besides `local.ts` — confirmed via repo-wide grep. The Rust-side `install_python`/`install_pip`/`install_py_dependencies`/`run_py_server` functions themselves are unchanged from the first pass (still Windows-only / `python.exe`-hardcoded / panic-prone via `.unwrap()`/`.expect()`), so they remain a latent risk only if some future caller reintroduces the old behavior — not an active bug today given the confirmed single call site.
- Five of the eleven `#[tauri::command]` functions in `main.rs` (`greet`, `check_auth`, `native_request`, `oauth_login`, `check_requirements_local`) have **no frontend caller anywhere under `src/`** (confirmed via repo-wide grep for each command name and for `invoke(` call sites). They're dead/unused from the app's perspective today; `oauth_login` in particular has its own platform-fragile behavior (see Lead 1 below) that would matter if it's ever wired up.

## Lead 1: Full sweep of every `#[tauri::command]` in `src-tauri/src/main.rs`

`src-tauri/src/` contains only `main.rs` (confirmed via `find`). All 11 `#[tauri::command]` functions, in file order:

### 1. `greet` — `main.rs:4-7`
```rust
fn greet(name: &str) -> String { format!("Hello, {}! You've been greeted from Rust!", name) }
```
**CHECKED-NO-ISSUE.** Pure string formatting, no OS/path/panic surface. **No frontend caller found** (repo-wide grep for `greet` invocation in `src/` returns nothing) — dead scaffold command from the Tauri template.

### 2. `native_request` — `main.rs:34-98`
Generic `reqwest`-based HTTP fetch, base64-encodes the response body, returns JSON as a string.
**CHECKED-NO-ISSUE for platform-specifics.** No hardcoded paths, no OS branching. Contains several `.unwrap_or("")`/matched `Err` branches that degrade gracefully rather than panic (e.g. `value.as_str().unwrap_or("")` at `main.rs:49`). **No frontend caller found** in `src/` (searched for `native_request` invocation) — appears unused; `streamed_fetch` (below) is the one actually wired up for HTTP.

### 3. `oauth_login` — `main.rs:125-184`
**CONFIRMED BUG (latent — currently unreferenced from the frontend, but real if ever wired up).**
- `main.rs:131`: `std::fs::write("pkce_verifier.txt", pkce_verifier.secret()).unwrap()` writes to a **relative path in the process's current working directory**, not an app-data directory obtained via Tauri's `path` API (contrast with every other file-writing command in this file, which correctly uses `BaseDirectory`/joins against a passed-in `path`). On Android, an app's working directory is not guaranteed to be writable by the app (Android sandboxes apps into per-app storage, not an arbitrary CWD), and even on desktop this depends on whatever directory the OS launched the binary from — this would need `path::app_data_dir()` or similar to be portable.
- `main.rs:111-113, 146, 148, 157, 174, 183`: six more `.unwrap()`/`.expect()` calls on OAuth flow state (URL parsing of hardcoded literal strings, HTTP client build, mutex locks, emit results, token exchange result) — none of these are OS-specific per se (they'd panic identically on any platform if triggered), but they compound the risk that this command, if ever invoked, would panic rather than degrade on any target, mobile included, where a Tauri window's `emit`/`listen` timing might behave differently.
- **No frontend caller found** in `src/` (searched for any `invoke` of `oauth_login`) — appears to be scaffold/dead code today, but it is the single most panic-prone command in the file and is worth fixing or removing before Android work resumes if it's ever reactivated.

### 4. `check_auth` — `main.rs:187-227`
Checks a file exists, is a file, is <1000 bytes, and its contents match an expected auth string.
**CHECKED-NO-ISSUE for platform-specifics**, but has one generic (non-OS-specific) panic risk: `std::fs::metadata(&fpath).unwrap()` at `main.rs:203` will panic if the file is deleted between the `path.exists()` check (`main.rs:191`) and the `metadata()` call (TOCTOU race) — not an OS/arch issue, just a general robustness gap. **No frontend caller found** in `src/`.

### 5. `install_python` — `main.rs:229-294`
**CONFIRMED BUG — already fully documented in the first-pass report** (`04-tauri-platform-expansion.md`, "The `src-python` Component" section). Re-confirmed present and unchanged: `os == "windows"` early-return at `main.rs:241-246` means every non-Windows OS returns `false` before ever reaching the Linux/macOS extraction branches at `main.rs:264-269`, which are dead code. `py_exec_path = py_path.join("python.exe")` at `main.rs:275` is Windows-only. Not re-investigating further per instructions — see Lead 5 below for what's changed (nothing on the Rust side; the frontend caller was fixed).

### 6. `install_pip` — `main.rs:296-326`
**CONFIRMED BUG (already known from first pass, re-confirmed).** `py_exec_path = py_path.join("python.exe")` at `main.rs:299` — Windows-only path, no `python`/`python3` fallback for POSIX. `reqwest::get(...).await.unwrap()` (`main.rs:301`), `std::fs::File::create(...).unwrap()` (`main.rs:303`), `out.write_all(...).unwrap()` (`main.rs:308`), `String::from_utf8(o.stdout).unwrap()` (`main.rs:314`) — four more panics, none OS-specific individually but all would fire immediately on any non-Windows OS since `python.exe` won't exist there, turning what should be a clean "unsupported OS" message into a hard panic. This is the same failure mode already flagged in the first-pass report's "silent no-op" correction — worth reiterating because it's a second, distinct command hitting it (not just `install_python`).

### 7. `check_requirements_local` — `main.rs:330-365`
Probes for system `python` and `git` on PATH via `Command::new("python")`/`Command::new("git")`.
**CHECKED-NO-ISSUE for platform-specifics.** Uses bare command names (`"python"`, `"git"`) rather than `python.exe`/`git.exe` — this is actually the *correct*, portable pattern (relies on OS `PATH` resolution, which handles `.exe` suffixing automatically on Windows and needs no suffix on POSIX). Errors are handled via `match`/`Err` branches returning descriptive strings, not `.unwrap()`. This is the one command in the file that's written in an OS-agnostic style. **No frontend caller found** in `src/` — this "bring your own Python" path is fully unwired, consistent with the first-pass report's observation.

### 8. `post_py_install` — `main.rs:367-379`
Edits `python311._pth` to uncomment `import site`, then writes a `completed.txt` marker.
**CONFIRMED BUG (path-name coupling, not previously flagged).** `py_pth_path = py_path.join("python311._pth")` at `main.rs:370` hardcodes the Windows embeddable-Python filename convention (`pythonXXX._pth`, matching the specific 3.11 embeddable zip `install_python` downloads). If `install_python` is ever extended to other OSes/versions (per the first-pass report's top recommendation), this filename would silently mismatch and `std::fs::read_to_string(&py_pth_path).unwrap()` at `main.rs:372` would panic — flagging this as a linked follow-on fix, since it's easy to miss when only reading `install_python` in isolation.

### 9. `install_py_dependencies` — `main.rs:381-404`
**CONFIRMED BUG (already known pattern, re-confirmed).** `py_exec_path = py_path.join("python.exe")` at `main.rs:385` — same Windows-only hardcoding as `install_pip`. Unlike `install_pip`/`install_python`, this one returns `Result<(), String>` and uses `?`-free but still non-panicking `match` on the `Command::output()` call (`main.rs:393-403`) — so a missing `python.exe` on non-Windows produces a clean `Err(...)` here rather than a panic, which is comparatively well-behaved. Still blocked by the same root cause as everything else in this cluster.

### 10. `run_py_server` — `main.rs:406-430`
**CONFIRMED BUG (already known, re-confirmed) + one new panic surface.** `py_exec_path = Path::new(&py_path).join("python").join("python.exe")` at `main.rs:408` — Windows-only, as documented in the first-pass report. New in this pass: `.spawn().expect("failed to execute process")` at `main.rs:427` will **panic** (not return an error) if spawning fails — e.g. exactly the scenario where `python.exe` doesn't exist because the OS is non-Windows. Given the frontend fix (Lead 5) now stops the call chain before reaching this function when `install_python` returns `false`, this is only reachable today via the single confirmed call site in `local.ts`, which is gated — but it's worth noting for completeness that this function's failure mode is a hard panic, not a graceful error, unlike `install_py_dependencies`.

### 11. `streamed_fetch` — `main.rs:432-564`
Generic streaming HTTP fetch/proxy with base64 body encoding, emits Tauri events per chunk.
**CHECKED-NO-ISSUE for platform-specifics.** No hardcoded paths, no OS branching, no `.exe` assumptions. Contains internal `.unwrap()` calls on decode/emit results (`main.rs:470, 486, 496, 527, 559`) but these are protocol/logic-level (malformed base64, emit-after-window-closed), not OS-specific — same risk profile on every platform. This is the one actively-used HTTP command (confirmed caller at `src/ts/globalApi.svelte.ts:1891`).

### Sweep completeness note
All 11 commands were examined individually above (5 checked-no-issue for platform-specifics, 6 confirmed-bug or bug-adjacent, all traced to frontend callers or confirmed to have none). No additional `.rs` files exist under `src-tauri/src/` to sweep (`find src-tauri/src -name "*.rs"` returns only `main.rs`).

## Lead 3: `src/ts/platform.ts` and frontend platform-detection conflation

`src/ts/platform.ts:19-22` defines the core flags:
```ts
export const isTauri: boolean = !!(window as ...).__TAURI_INTERNALS__
export const isNodeServer: boolean = !!(globalThis as ...).__NODE__
export const isWeb: boolean = !isTauri && !isNodeServer && location.hostname === 'risuai.xyz'
export const isMobile: boolean = /Android|iPhone|iPad|iPod|webOS/i.test(browserNavigator.userAgent);
```
**Design-level observation (CHECKED-NO-ISSUE for the flags themselves):** `isMobile` is computed independently from `isTauri` (pure user-agent sniffing), so the two flags are *orthogonal* by construction — `isTauri && isMobile` is a representable, non-contradictory state once Android ships. The flags themselves are not the bug; the bug is that call sites throughout the codebase use `isTauri` alone as a proxy for "safe to call desktop-only Tauri APIs," which was a safe assumption only because Android has never been a real target until now. Four such call sites were found:

1. **`src/ts/bootstrap.ts:61`** — `appWindow.maximize()`, called unconditionally inside `if (isTauri) { ... }` (`bootstrap.ts:59`), not awaited, no `.catch()`. `Window.maximize()` is a desktop-only Tauri window API. **CONFIRMED BUG, corrected blast radius**: since this call is not awaited, its promise rejection (if the API rejects rather than no-ops on Android — itself unverified) would **not** be caught by the surrounding synchronous `try`/`catch` and could not skip later `loadData()` steps the way originally claimed; it would instead surface separately as an unhandled promise rejection. Still a real platform-conflation bug, just not the startup-aborting one.
2. **`src/ts/util.ts:221-230`** (`changeFullscreen`), called from **`src/ts/bootstrap.ts:119`** inside the same `isTauri`-only branch — calls `appWindow.isFullscreen()` (`util.ts:223`) and `appWindow.setFullscreen(...)` (`util.ts:225`/`:228`), both desktop-only window APIs. **CONFIRMED BUG, and per correction above, this is now the *only* one of the three startup-path items that can actually abort `loadData()`** — it *is* awaited (`bootstrap.ts:119`), so a rejection here does propagate as a thrown exception into the outer catch. Whether these window APIs actually reject (vs. resolve as a no-op) on an Android Tauri build is **unverified** — no Android build/runtime test was performed as part of this investigation; treat the startup-abort consequence as a plausible risk, not a demonstrated one.
3. **`src/ts/update.ts:46-59`** (`checkRisuUpdate`), called from **`src/ts/bootstrap.ts:118`**, also inside the same `isTauri`-only branch — calls `check()` from `@tauri-apps/plugin-updater` (`update.ts:5, 48`). **CONFIRMED BUG, but corrected severity**: this function wraps its update-check logic in its own local try/catch (`update.ts:47-92`) that logs the error and resolves normally rather than throwing — so, unlike originally claimed, a failure here does **not** propagate to `bootstrap.ts`'s outer catch and does **not** abort startup. The bug is narrower than stated: it's still backed by a Rust plugin (`tauri-plugin-updater`) that per Lead 2 isn't compiled into an Android build, so the `invoke` call itself would fail/reject on Android — but that failure is silently swallowed locally, making this an unnecessary-failing-call/observability gap, not a startup blocker.
   - **Blast radius, corrected via `src/ts/bootstrap.ts`:** items #1–#3 all execute sequentially inside `loadData()`'s single `try` block (`bootstrap.ts:58` opens it, `bootstrap.ts:264-266` is the only `catch`, which just calls `alertError(error)`), but **only item #2 (`changeFullscreen`) is actually capable of triggering that catch and skipping the remaining init steps** (`saveDb()`, `moduleUpdate()`, `cleanChunks()`, `alertTOS()` at `bootstrap.ts:255-262`) — and even that is contingent on the unverified assumption that these window APIs reject rather than no-op on Android. Item #1 (`maximize`) would surface as a separate unhandled rejection rather than aborting startup; item #3 (`checkRisuUpdate`) is self-contained and silently logs rather than propagating. The overall "startup would visibly fail on Android" conclusion from the original draft is not supported as strongly as stated — the more defensible claim is "these three call sites are unsafely gated on bare `isTauri` and need fixing before Android ships," independent of exactly how each one currently fails.
4. **`src/ts/process/mcp/mcp.ts:103-111`** — the MCP "stdio" transport spawns arbitrary local processes via `Command.create` from `@tauri-apps/plugin-shell`, gated only by `if(!isTauri){ throw new Error('stdio MCPs are only supported in Local Version'); }` (`mcp.ts:103-105`). **CONFIRMED BUG (functional, not compile-time)** — `tauri-plugin-shell` itself compiles fine on Android (Lead 2), but spawning arbitrary executables (`npx`, `uvx`, or any user-specified `command`) is not something Android's app sandbox supports the way desktop OSes do; there's no general-purpose shell/PATH environment for a sandboxed Android app to exec into. This needs a desktop-only gate (e.g. `isTauri && !isMobile`), not an `isTauri`-only gate, once Android is real.

No other `isTauri`-guarded call sites reviewed (the remaining ~25 files matching `isTauri` — `globalApi.svelte.ts`, `characterCards.ts`, `cbs.ts`, `parser.svelte.ts`, various `Setting`/`ChatScreens` Svelte components, etc.) were found to call desktop-only window/plugin APIs; they mostly branch between Tauri filesystem APIs (`readFile`/`writeFile` with `BaseDirectory.AppData`, which **is** mobile-supported by `tauri-plugin-fs`) versus `forageStorage`/`fetch`-based web/node fallbacks — these are legitimate platform branches, not conflation bugs, and were checked-no-issue.

## Lead 4: Bundle size / resource footprint for mobile distribution

- `src-tauri/tauri.conf.json:17-19`: `"resources": ["src-python/*"]` — measured at **6.0 KB** (`main.py` 3.7 KB, `run.py` 246 B, `requirements.txt` 54 B). **CHECKED-NO-ISSUE** — negligible size; the Python sidecar's problem is functional (Windows-only, Lead 1/5), not size.
- `src-tauri/icons/` — **872 KB** total (all platform icon sets combined, including the already-staged `android/mipmap-*` set from the first-pass report). **CHECKED-NO-ISSUE** — normal icon-asset size.
- **`public/` — 95 MB total, flagged as a real practicality concern (not a correctness bug).** Breakdown of the largest contributors (`du -sh public/* | sort -rh`):
  - `public/token/` — **77 MB**, by far the largest single directory. Contains per-model tokenizer files under `public/token/{claude,cohere,deepseek,gemma,glm4,glm5,llama,mistral,nai,trin}/`. Individual largest files: `gemma/tokenizer.json` 18 MB, `cohere/tokenizer.json` 13 MB, `llama/llama3.json` 9.1 MB, `glm5/tokenizer.json` 8.3 MB, `glm4/tokenizer.json` 8.2 MB, `deepseek/tokenizer.json` 7.8 MB, `deepseek/v4/tokenizer.json` 4.2 MB, `gemma/tokenizer.model` 4.1 MB, `claude/claude.json` 1.7 MB, `trin/spiece.model` 1.2 MB.
  - `public/sample/` — 7.4 MB, `public/assets/` — 5.1 MB, `public/logo_typo_trans_bg.png` — 4.0 MB, `public/welcome/` — 544 KB, plus smaller logo/icon/webp assets.
  - **How these ship:** `src/ts/tokenizer.ts` fetches these lazily at runtime via relative paths (e.g. `fetch("/token/llama/llama3.json")` at `tokenizer.ts:261`, similarly for the other 9 model families at `tokenizer.ts:326-382`) — so they are not eagerly bundled into a JS chunk and not all loaded on every startup. However, for a Tauri desktop build, `public/` is copied wholesale into the Vite `dist/` output (`frontendDist` per `tauri.conf.json:5`) and that entire directory is what Tauri embeds as the app's local web assets — there's no evidence in this repo of these files being served from an external CDN at runtime (the fetch paths are relative, same-origin). The same packaging model would apply to a Tauri Android build: the APK/AAB would need to embed the same `dist/` output, meaning **all ~77 MB of tokenizer data would ship inside the installed app regardless of which model(s) a given user actually uses**, since Android has no separate "web server" to lazily serve these from either.
  - **Why this matters specifically for Android/mobile distribution and not just desktop:** desktop installers (NSIS/deb/rpm/AppImage/DMG) are comparatively insensitive to a `~100 MB` app size, but mobile is a different cost class — Google Play has historically nudged toward Android App Bundle size-on-disk targets, cellular users on metered connections are size-sensitive at install time, and per-tokenizer-family lazy-loading in the JS layer (already implemented) suggests the app author was aware most users only need 1-2 of these files at a time — but that lazy-loading benefit is lost if the whole 77 MB still has to be embedded in the installed package regardless. Recommendation-relevant, not a "confirmed bug": worth a follow-up spike into whether Tauri's Android build can be configured to fetch these from a CDN at runtime instead of embedding them, ahead of any Android work.
- **Verdict: no single file/resource is a build-breaking size (nothing exceeds typical CI/store hard limits on its own), but the aggregate `public/token/` footprint is disproportionate to the on-disk app most users would expect, and is worth pre-emptively addressing (CDN-hosting or on-demand-download the tokenizer files) before or during Android work, independent of the RAM/perf gating already noted in the first-pass report.**
