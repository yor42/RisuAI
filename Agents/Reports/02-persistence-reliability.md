# Save/Persistence Reliability Investigation

Scope: data-loss / partial-write / race-condition risk in the save pipeline, primarily the web build. Asset "corruption" and RAM/perf are covered by other reports and are only flagged here where they visibly overlap. This report is read-only static analysis (Read/Grep only, no source files modified).

> **Cross-validated** via an independent Codex adversarial-review pass (`Agents/CodexReviews/02-persistence-reliability.codexreview.md`). Verdict: **partially confirmed with corrections**. The central risks (no automatic retry after a failed save, OPFS gating that leaves it unreachable, the un-awaited `stream.close()`, absent quota-specific handling, and `remoteSaveCleanup.test.ts`'s irrelevance to the web build) are all confirmed. Five corrections were applied in place below: the autosave loop's actual retry/alert behavior (there is no automatic retry at all — the original description of "4 silent retries then permanent idling" was inaccurate), which `changeTracker` fields actually get cleared, an unsubstantiated OPFS-vs-IndexedDB durability comparison that's been hedged, a factual error about Tauri routing remote-block writes through `AutoStorage` (it doesn't — it bypasses it), and several cross-platform failure-frequency claims that were stated as fact but are actually unproven hypotheses.

## Executive summary

- **The single biggest, most concrete bug: a failed autosave write is never automatically retried, and can permanently drop the pending change.** In the main save loop (`src/ts/globalApi.svelte.ts:409-485`), the loop's `changed` flag is cleared *before* the actual write is attempted (`globalApi.svelte.ts:447-467`), and the `catch` block (`globalApi.svelte.ts:474-482`) never re-sets `changed = true` on failure. **[corrected]** The original draft of this bullet overstated two details, corrected here: (1) `changeTracker` is not uniformly "trimmed/reset" — the character/chat entries retain their newest value, only `botPreset`/`modules` are cleared, and `loadouts`/`plugins`/`pluginCustomStorage` aren't reset at all; and (2) there is no automatic retry loop to speak of, so "logs/alerts after 4 consecutive failures" is misleading phrasing — failures 1-4 are simply logged with no retry attempt, and a user-facing alert only fires from the 5th *accumulated* failure onward across whatever later save attempts happen to occur. The loop does return to `if (!changed) { sleep(500); continue }` (`globalApi.svelte.ts:410-413`) after a failure, so it does **not** automatically retry — but "idles forever" is conditional, not absolute: if any other mutation happens to re-fire a tracking `$effect` before the tab closes, `changed` gets re-armed and a fresh save attempt is made (still with no awareness that a prior attempt failed). Net effect stands: a failed save has no dedicated retry/recovery path and can be lost if the user doesn't happen to make another edit. This is a plausible root cause for "I edited something, closed the tab, and it wasn't saved" reports. (The report's original claim that web write paths fail "far more often" than Tauri's native filesystem calls is a reasonable hypothesis but is not established by anything in this repository — see the Web-specific reliability gaps section's correction below.)
- **OPFS is effectively dead code for the main database on this fork.** `AutoStorage.Init()` only selects `OpfsStorage` when `localStorage.getItem('opfs_flag!') === "able"` (`src/ts/storage/autoStorage.ts:177-179`), but nothing in `src/` ever sets that flag — it is grep-clean outside the one read site. So despite AGENTS.md describing OPFS as one of the active backends, the real web default for `database/database.bin` falls through to **LocalForage** (`src/ts/storage/autoStorage.ts:214-217`). **[corrected]** Two claims here were stated more strongly than the code establishes: (1) "LocalForage → IndexedDB" isn't guaranteed purely by this code — LocalForage performs its own driver selection (normally IndexedDB in supported browsers, but not guaranteed), so this should be read as "normally IndexedDB," not an absolute; (2) the blanket statement that this has "weaker durability semantics than OPFS's atomic swap-on-close model" is a reasonable inference but isn't demonstrated by anything in this repository and should be treated as a hypothesis, not an established fact. Cold storage *does* use OPFS directly, but only in its non-account-sync, non-Node-server branch (`src/ts/process/coldstorage.svelte.ts:87-196`) — i.e. ordinary browser profiles, not unconditionally across every web configuration. With that scoping, the app's actual behavior is still a split: main DB on LocalForage, cold storage on OPFS for plain browser profiles, with no shared code path between them.
- **`OpfsStorage.setItem` (the class that would back the main DB if the flag were ever set) has a genuine atomicity bug: it does not await the writable stream's `close()`.** `src/ts/storage/opfsStorage.ts:12-14` calls `await stream.write(...)` but then `stream.close()` without `await`. The OPFS spec's atomic swap only completes when `close()` resolves; not awaiting it means `setItem()` can resolve (and callers can proceed, e.g. to the next save cycle or to closing the tab) before the underlying file swap is durable. By contrast, the *unrelated* cold-storage OPFS write path does this correctly: `await writable.close()` (`src/ts/process/coldstorage.svelte.ts:190`). This inconsistency is a real, fixable bug even though it's currently unreachable via the flag gate above — and would immediately become live/dangerous if the flag were ever turned on or defaulted to true.
- **No storage-quota handling anywhere in the save path.** There is no call to `navigator.storage.estimate()`, no `QuotaExceededError` handling, and no pre-write size check in `risuSave.ts`, `globalApi.svelte.ts`, `autoStorage.ts`, `opfsStorage.ts`, or `accountStorage.ts` (confirmed by repo-wide grep for `quota`/`QuotaExceeded`/`storage.estimate`). **[corrected]** A quota failure surfaces only as a generic thrown error, which — per the bug above — is logged but not automatically retried (not "swallowed after 4 retries," which implies a retry loop that doesn't exist; see the corrected Executive Summary bullet above for the precise failure/alert behavior). Either way, there's no quota-specific recovery path or user-facing "storage full" messaging — a generic error is all that happens.
- **The save format is genuinely block/chunked** (`RisuSaveType` enum, `src/ts/storage/risuSave.ts:93-106`), and incremental saves only re-encode blocks that changed (`RisuSaveEncoder.set`, `risuSave.ts:202-302`). This is good for save latency but means a save that fails partway through `RisuSaveEncoder.encode()`/the actual disk write can, in principle, leave the previous `database.bin` value intact (encode() builds the whole buffer in memory first, `risuSave.ts:304-326`, and only one `setItem` call writes it) — so the *in-file* format itself is reasonably safe against torn writes at the JS level. The real danger is at the storage-backend layer (IndexedDB transaction semantics, OPFS close(), or HTTP write for account sync), not the in-memory block model.
- **`remoteSaveCleanup.test.ts` covers only the decision-table logic, not the actual filesystem/IndexedDB deletion side effects**, and the only wired-up caller (`src/ts/bootstrap.ts:511-589`, inside `cleanChunks()`) is gated to `if (isTauri)` (`bootstrap.ts:524`) — so this cleanup, and its test coverage, says nothing about web-build reliability at all; it only prevents remote-character-block orphan buildup on desktop.

## Storage backend architecture as actually implemented

`AutoStorage` (`src/ts/storage/autoStorage.ts`) is the single entry point used everywhere via the module-level singleton `forageStorage = new AutoStorage()` (`src/ts/globalApi.svelte.ts:49`). Its `Init()` (`autoStorage.ts:165-219`) picks a backend in this priority order, evaluated once and cached on `this.realStorage`:

1. **Account sync** (`AccountStorage`) if `localStorage.accountst === 'able'` (`autoStorage.ts:167-171`) — an HTTP-backed store hitting `/api/account/*` (hub-backed), see below.
2. **Node server** (`NodeStorage`) if `isNodeServer` (`autoStorage.ts:172-176`) — HTTP calls to a self-hosted `/api/*` server.
3. **OPFS** (`OpfsStorage`) only if the browser supports `navigator.storage.getDirectory` **and** `FileSystemFileHandle.prototype.createWritable` **and** `localStorage.getItem('opfs_flag!') === "able"` (`autoStorage.ts:177-179`). As noted above, nothing sets this flag, so in practice this branch is dead for the shipped app.
4. **LocalForage/IndexedDB** as the unconditional fallback (`autoStorage.ts:214-217`) — this is what essentially every web-build user is actually on for `database/database.bin`.

This directly **corrects AGENTS.md's brief description**: OPFS is not actually in the active rotation for the main save file; it is scaffolding gated behind a flag nothing sets. The degradation is silent — there is no user-facing indication of which backend is active, and no warning that IndexedDB (used) has different durability characteristics than OPFS (unused, but implied "supported" by the code's existence).

Tauri desktop bypasses `AutoStorage` entirely, including for remote blocks. `src/ts/globalApi.svelte.ts:454-457` branches on `isTauri` and calls `@tauri-apps/plugin-fs`'s `writeFile` directly to `database/database.bin` under `BaseDirectory.AppData`, i.e. real native filesystem writes. **[corrected]** The original draft of this paragraph incorrectly implied `AutoStorage` is "exercised by Tauri for `remotes/*.local.bin` blocks" — it is not: `risuSave.ts:401-410`'s `isTauri` branch calls `writeFile` directly, bypassing `AutoStorage` there too, exactly as it does for the main DB write. `AutoStorage`'s remote-block code path is only actually exercised on the **Node-server** backend (`isNodeServer`), not Tauri.

Account-sync storage (`src/ts/storage/accountStorage.ts`) is a thin HTTP client: `setItem` POSTs to `/api/account/write` with a session-number header and a `x-risu-save-date` header used for conflict/staleness detection server-side (`accountStorage.ts:22-99`), and separately mirrors the write into a local `cachedForage` IndexedDB cache (`accountStorage.ts:59-63`) — note this mirror write is fire-and-forget (`.then(...)` with no `await`, `accountStorage.ts:60-62`), so the local cache can lag or fail silently relative to the confirmed remote write. `getItem` supports a 303 "not modified, use cache" response (`accountStorage.ts:126-135`), meaning correctness depends on the cache actually having been populated by that earlier fire-and-forget write.

Node-server storage (`src/ts/storage/nodeStorage.ts`) is a comparably thin HTTP client over `/api/write`, `/api/read`, `/api/list`, `/api/remove`, authenticated with an ECDSA-signed JWT (`nodeStorage.ts:72-143`). Structurally it's simpler than `AccountStorage` (no session/date staleness headers, no local cache mirror), and unlike the web IndexedDB/OPFS paths it delegates all persistence to whatever the self-hosted server does — so the Node path's reliability characteristics are defined by server-side code not reviewed here, not by anything in this file.

## Block/chunk save model details

`src/ts/storage/risuSave.ts` defines `RisuSaveType` (`risuSave.ts:93-106`): `CONFIG`, `ROOT`, `CHARACTER_WITH_CHAT`, `CHAT`, `BOTPRESET`, `MODULES`, `REMOTE`, `CHARACTER_WITHOUT_CHAT`, `ROOT_COMPONENT`, `PLUGINS`, `LOADOUTS`, `PLUGIN_STORAGE`.

- `RisuSaveEncoder.init()` (`risuSave.ts:129-200`) builds one block per logical section: `root` (everything except characters/botPresets/modules), `preset`, `modules`, `loadouts`, `plugins`, `pluginStorage`, one block **per character** keyed by `chaId`, and a `config` block.
- `RisuSaveEncoder.set()` (`risuSave.ts:202-302`) is the incremental path used by every autosave cycle: it only re-encodes blocks flagged in the `toSaveType` change tracker (`risuSave.ts:83-91`), reuses cached blocks for everything else, and rebuilds a `root.__directory` array listing all current block keys (`risuSave.ts:295-301`) so the decoder knows what to expect.
- Each block is a small self-describing record: type byte, compression flag byte, 1-byte name length, name bytes, 4-byte little/native-endian length, then the payload (`RisuSaveEncoder.encodeRawBlock`, `risuSave.ts:345-376`). `encode()` (`risuSave.ts:304-326`) concatenates a magic header (`RISUSAVE\0`) plus all current blocks into a **single in-memory `ArrayBuffer`**, which is what actually gets handed to the storage backend's `setItem`.
- "Remote" blocks (`RisuSaveType.REMOTE`) are a level of indirection: instead of embedding character data in the main buffer, the character JSON is written to a *separate* storage key (`remotes/<chaId>.local.bin`, via `AutoStorage`/Tauri fs — `risuSave.ts:378-422`) and the main buffer only stores a small pointer record. This is used when `isTauri || isNodeServer` and remote saving isn't disabled (`encodeBlock`, `risuSave.ts:328-343`) — **not** on plain web/IndexedDB, so web-build users don't get this indirection or its associated cleanup logic at all (see remoteSaveCleanup section).
- Decoding (`RisuSaveDecoder.decode`, `risuSave.ts:432-620`) walks the buffer's block records; on the `ROOT` block it recovers `__directory` and, for any directory entry not already present in the buffer, pulls it from a side IndexedDB cache `risuSaveCacheForage` (`risuSave.ts:121-123`, populated on every raw-block encode at `risuSave.ts:370-374`). Errors decoding a non-ROOT block are caught and skipped per-block (`risuSave.ts:605-611`); a ROOT-block decode failure is fatal (`risuSave.ts:608-610`, throws), meaning ROOT corruption is unrecoverable but a single corrupt character block just silently vanishes from the loaded database with only a `console.error`.

## Atomicity & partial-write risk analysis

- **In-buffer assembly is atomic-ish by construction**: `encode()` builds the whole multi-block buffer in JS memory before any I/O happens (`risuSave.ts:304-326`), and the storage write is a single `setItem(key, buffer)` call per backend. So a crash *during* block assembly can't produce a half-written file — either the full buffer is handed to the backend or nothing is.
- **The backend `setItem` call itself is where atomicity guarantees can break down**, and this differs sharply by platform:
  - **Tauri**: `@tauri-apps/plugin-fs`'s `writeFile` is a native OS file write; the desktop OS/filesystem's own write semantics apply (out of scope for this JS-level review, but generally far more durable than a browser storage API).
  - **IndexedDB (via localforage, the real web default)**: IndexedDB transactions are atomic at the browser-engine level for a single `put`, so `AutoStorage`/localforage's `setItem` is reasonably safe against torn writes for a *single key* — but this repo does two sequential writes per save cycle (`database/database.bin` then `database/dbbackup-<ts>.bin`, `globalApi.svelte.ts:460-462`) with no transaction wrapping them together, so a crash between the two leaves the backup out of sync with the primary (minor risk, since the primary is the one actually read back).
  - **OPFS (`OpfsStorage`, currently unreachable per above, but reviewed as if live)**: `setItem` does `await stream.write(...)` then **un-awaited** `stream.close()` (`opfsStorage.ts:12-14`). This much is confirmed directly from the code: `setItem()` can resolve, and a caller can treat the save as "done," before `close()`'s promise actually settles — meaning any asynchronous rejection from `close()` is silently dropped (never propagated to the caller). **[corrected]** The remainder of this paragraph's claims — that this reliably breaks the OPFS atomic swap on a crash/tab-close, and that a second `setItem()` call on the same key shortly after would race and throw `NoModificationAllowedError` — are plausible consequences consistent with the general shape of the File System Access API's `createWritable()`/atomic-rename-on-close behavior, but they are not established by this repository's code or by a reproduction performed during this investigation. Treat them as a hypothesis worth testing, not a confirmed failure mode. What is confirmed and actionable regardless: the missing `await` should be added so `setItem()` cannot resolve before `close()` has actually settled, matching the pattern already used correctly in `coldstorage.svelte.ts:190`.
  - **Account sync / Node server (HTTP)**: atomicity is delegated entirely to the remote server implementation; the client only knows success/failure via HTTP status. `AccountStorage.setItem` retries on 403 (re-auth) but has no retry for network failures/5xx beyond throwing (`accountStorage.ts:93-95`), which flows into the same no-automatic-retry gap described above (see the corrected Executive Summary/Concurrency-section detail on actual failure/alert behavior).
- **Remote-block writes (Tauri/Node "prefer remote" path) are not transactional with the root block.** `RisuSaveEncoder.encodeRemoteBlock` writes the character payload to `remotes/<chaId>.local.bin` first (`risuSave.ts:401-410`), then returns a small pointer block that gets folded into the root buffer later. If the process crashes after the remote file write but before the root block (containing the updated `__directory`) is itself durably written, the remote file becomes a harmless orphan (cleaned up eventually by `cleanChunks`/`remoteSaveCleanup`, Tauri-only). The inverse — root written pointing at a remote block whose file write never completed — is guarded against because `encodeRemoteBlock` awaits the remote file write before returning the pointer block that goes into `encode()`, so this specific interleaving looks safe on inspection, contingent on the underlying `writeFile`/`forageStorage.setItem` awaits being honored (they are, `risuSave.ts:406`, `risuSave.ts:409`).

## Concurrency/race-condition risk analysis

- **Single autosave loop, cross-tab coordination via `BroadcastChannel`.** `saveDb()` is invoked exactly once, unawaited, at bootstrap (`src/ts/bootstrap.ts:255`; confirmed no other caller via repo-wide grep). It runs one `while(true)` loop for the process lifetime (`globalApi.svelte.ts:409-485`), so there's no risk of two competing save loops *within one tab*. Across tabs, it opens a `BroadcastChannel('risu-db')` and posts its `sessionID` before writing (`globalApi.svelte.ts:296-313`, `438-440`); if another tab's message arrives first, this tab sets `gotChannel = true`, shows a "reload" prompt, and skips saving thereafter (`globalApi.svelte.ts:301-312`, `433-437`). This is a reasonable soft-lock but is advisory only — it relies on `BroadcastChannel` delivery timing, not any real mutex, so a genuinely simultaneous write race between two tabs during the timing window is still theoretically possible (not proven exploitable here, flagged as hypothesis).
- **The pending-change bookkeeping (`changeTracker`) is mutated *before* the write is confirmed, not after.** This is the mechanism behind the Executive Summary's core bug: `toSave` is snapshotted and `changeTracker` is cleared (`globalApi.svelte.ts:428-432`) synchronously, then the async write happens (`447-467`). There is no rollback of `changeTracker` in the `catch` (`474-482`), and `changed` is never re-armed on failure there. **[corrected]** Precisely: character/chat tracker entries retain their newest value rather than being wiped, only `botPreset`/`modules` are actually cleared, and `loadouts`/`plugins`/`pluginCustomStorage` are untouched by this clear at all. There is no retry queue or failure counter that "invisibilizes after the 4th occurrence" in the sense of a formal retry mechanism — failures 1-4 are logged via `console.error`, and a user-facing alert begins once 5 failures have accumulated across whatever save attempts actually occur (which only happen again if something else re-arms `changed`). The edit is at risk of being dropped, but not deterministically — it depends on whether any other DB mutation happens to fire before the tab/app closes.
- **Cloud "Drive" restore competes with the live autosave loop with no lock.** `loadDrive()` (`src/ts/drive/drive.ts:205-389`) writes a freshly-downloaded database directly to the same `database/database.bin` key (`drive.ts:365-384`) that the autosave loop is continuously writing to, with no coordination between them. On web it finishes with `location.search = ''` to force a reload (`drive.ts:379`), and on Tauri with `relaunch()` (`drive.ts:369`) — both eventually terminate the old process/tab and its autosave loop, but there is a window between the drive-restore write and that reload/relaunch during which the pre-existing autosave loop (driven by stale in-memory `DBState`) could fire again and overwrite the just-restored data with the old in-memory state. This is a plausible race (unverified whether it's been hit in practice) given the loop's short (`500`ms-`1`s) sleep intervals.
- **`RisuSaveEncoder.set()` reads the live Svelte-5 reactive `$state` object, not a snapshot, when building save data for the autosave loop.** `globalApi.svelte.ts:441` calls `let db = getDatabase()` with no `{ snapshot: true }` option, unlike `getDatabase({ snapshot: true })` used elsewhere (e.g. `autoStorage.ts:41`, `drive.ts:113` via `safeStructuredClone(getDatabase())`). `getDatabase()` without the option returns `DBState.db` directly (`database.svelte.ts:732-737`), a live reactive proxy. Because `RisuSaveEncoder.set()` `await`s between blocks (character-by-character, `risuSave.ts:215-249`), and the UI can keep mutating `DBState` between those awaits (e.g. streaming a new chat message while a save is in flight), it is possible for a single save cycle to serialize some characters' *newer* state and others' *older* state — a form of torn read across the multi-block save, not a torn write. This wouldn't corrupt any individual block, but could produce a save where character A reflects an edit made after the save started while character B (already serialized) doesn't, which on reload could look like a message/edit "reverting." Flagged as hypothesis — plausible from the code shape, not confirmed by a reproduction.

## Quota handling analysis

No quota-awareness exists anywhere in the save path. Confirmed by:
- Repo-wide grep for `QuotaExceeded`, `storage.estimate`, and `quota` (case-insensitive) across `src/` returns no hits in any storage/save/drive file (the only incidental hit is unrelated prompt text in `src/ts/storage/defaultPrompts.ts:5`).
- `persistant.ts` (`src/ts/storage/persistant.ts`) only requests **persistent storage mode** (`navigator.storage.persist()`) to reduce eviction risk under storage pressure (`persistantStorageRecommended`/`requestPersistantStorageMain`, `persistant.ts:6-48`) — it never checks *how much* quota is used or remaining, and is purely advisory (recommended once `db.characters.length > 5`, `persistant.ts:43-45`).
- There is no `QUOTA_WRITE_CEILING`-style safety margin anywhere comparable to the community plugin referenced in the task context. A `QuotaExceededError` thrown by IndexedDB (or OPFS, if ever enabled) on a large save would be caught by the generic `try/catch` in the autosave loop (`globalApi.svelte.ts:417-482`) and hit the same no-automatic-retry gap described above — there is no differentiated handling (no "your storage is full, delete some characters" messaging, no automatic reduction of what's saved, no backoff/retry).
- Given the save model duplicates a full `database/dbbackup-<timestamp>.bin` on every single save cycle in addition to the primary file (`globalApi.svelte.ts:454-463`), and only prunes backups down to the most recent 20 (`getDbBackups`, `globalApi.svelte.ts:493-529`), storage pressure from the backup files themselves is a plausible contributor to quota exhaustion on accounts with large save files, compounding the missing-quota-handling gap.

## What `remoteSaveCleanup.test.ts` already tells us about known issues

`src/ts/storage/remoteSaveCleanup.ts` (38 lines) is pure decision-table logic with **no I/O** — it takes a file name plus context (active character IDs, whether a `.meta` sidecar exists, the meta's `lastUsed` timestamp) and returns one of `'ignore' | 'keep' | 'create-meta' | 'delete'` (`remoteSaveCleanup.ts:13-38`). The design it encodes: an orphaned remote-character payload (`*.local.bin` no longer referenced by any character) is not deleted immediately — it first gets a `.meta` sidecar recording `lastUsed = Date.now()` (`create-meta`), and is only actually deleted once that meta file is older than a 7-day grace period (`remoteSaveCleanupGraceMs = 1000*60*60*24*7`, `remoteSaveCleanup.ts:2`) — i.e., a two-phase mark-then-sweep specifically to avoid deleting a payload the very save cycle it became orphaned (protects against a race where a character is transiently missing from `activeCharacterIds` during a save).

The test file (`remoteSaveCleanup.test.ts`, 70 lines) exercises: name-extraction correctness (`.local.bin` vs `.local.bin.meta` vs unrelated `.bin`), `keep` for active characters, `create-meta` for first-seen orphans, `keep` within the grace window, `delete` after the grace window, and `keep` when `metaLastUsed` is malformed (non-number) — a defensive test guarding against corrupted/foreign `.meta` JSON causing an unintended delete. This is solid coverage of the *decision function*, but it is narrow in scope:
- It does not test the actual file I/O in `cleanChunks()` (`src/ts/bootstrap.ts:511-589`) — no test exercises the `exists`/`readFile`/`writeFile`/`remove` Tauri-fs calls, error handling around them (the `try { } catch (error) { console.log('error', remote.name) }` swallow at `bootstrap.ts:587-589`), or what happens if `writeFile`/`remove` itself fails mid-cleanup.
- **This whole cleanup *caller* is `isTauri`-gated** (`bootstrap.ts:524`, the enclosing `cleanChunks` guard), while remote blocks themselves are produced whenever `isTauri || isNodeServer` in the encoder (`risuSave.ts:328-337`). **[corrected]** This is a real distinction worth being precise about: on the pure web/IndexedDB build, `RisuSaveType.REMOTE` blocks are never produced at all, so the tested decision logic is entirely inapplicable there — that part of the original claim stands. But the Node-server backend *can* produce remote blocks (`isNodeServer` is true there) while this `cleanChunks()` cleanup routine is never invoked for it either (it's gated to `isTauri` specifically, not `isTauri || isNodeServer`) — so Node-server remote-block orphans are also never swept by this mechanism, not just web ones. The one area with dedicated unit tests remains, by design, the area least relevant to the "mainly web version" bug reports this investigation was scoped around, and it also doesn't cover Node-server's own orphan accumulation.

## Web-specific reliability gaps (why this skews web-only)

**[corrected]** Cross-validation flagged that several claims in this section are comparative/empirical assertions (web fails "far more often" than Tauri, native writes are "generally more durable," one reload mechanism is "less immediately effective" than another) that are plausible but not established by anything in this repository — no runtime measurement or reproduction was performed. They're retained below as reasoned hypotheses about *why* the underlying, code-confirmed mechanisms (more failure-prone write paths, no persistent-storage guarantee, OPFS unreachable, advisory-only multi-tab lock, an unlocked restore-vs-autosave race) would plausibly manifest more often on web — but they should not be read as measured facts.

1. **Failure surface is larger on web** *(hypothesis, structurally plausible but unmeasured)*. Tauri's save path is a direct native `writeFile` (`globalApi.svelte.ts:454-457`) — OS-level file I/O. The web path goes through `AutoStorage` → LocalForage (`autoStorage.ts:214-217`), or for account-sync users, a full HTTP round trip (`accountStorage.ts:22-99`) subject to network flakiness, auth-session churn (403/`reloadSession` handling, `accountStorage.ts:35-92`), and server-side conditions entirely outside this codebase. More failure-prone write paths reaching the same no-automatic-retry gap (see corrected Executive Summary bullet) means more *opportunities* for a web user to silently lose an edit — this is a reasonable inference from the code shape, not a measured comparison.
2. **Browser storage eviction risk is real and only partially mitigated.** `persistant.ts` asks for `navigator.storage.persist()` but only recommends it once a user already has 5+ characters (`persistant.ts:43-45`), and only actively prompts on Firefox/Chromium-with-notification-permission flows (`persistant.ts:6-35`) — a new or small-library user's IndexedDB data is subject to normal browser storage-pressure eviction with no persistent-storage guarantee, something that simply doesn't apply to Tauri's app-data directory. This point is a direct code finding, not a comparative hypothesis.
3. **OPFS — the storage backend with the best atomicity story on web — is unreachable** (no code path ever sets `opfs_flag!`), so web users get LocalForage's guarantees instead of OPFS's atomic-swap file model, even though `OpfsStorage` exists in the codebase and cold storage already proves the OPFS API works fine here, for ordinary browser profiles (`coldstorage.svelte.ts:87-196`). The specific claim that LocalForage/IndexedDB has "weaker guarantees" than OPFS is the same unsubstantiated durability comparison corrected in the Executive Summary above.
4. **Multi-tab is a web-native failure mode.** Users routinely have RisuAI open in multiple browser tabs; Tauri desktop apps typically don't have an equivalent "N processes writing the same file" scenario unless a user deliberately runs multiple app instances. The `BroadcastChannel` soft-lock (`globalApi.svelte.ts:296-313`) is the only defense, and it's advisory/best-effort, not a real mutex — see Concurrency section. Direct code finding, not a hypothesis.
5. **The Drive-restore-vs-autosave-loop race** (see Concurrency section, `drive.ts:365-384`) is reachable on both platforms — that part is confirmed. *(Hypothesis)* the web variant's mitigation (`location.search = ''`, a same-document navigation) being "less immediately effective" at halting the old JS execution context than Tauri's `relaunch()` is a reasonable inference from how each mechanism works, but was not verified by tracing exact JS-engine teardown timing on either platform.

## Recommendations, ranked by (impact, implementation effort)

1. **(High impact, low effort) Give the autosave loop a real retry path.** In `src/ts/globalApi.svelte.ts`, move the `changeTracker` clear (lines 429-432) to *after* a successful write, or keep a rollback copy and restore it (merge back in) inside the `catch` block (474-482); and explicitly set `changed = true` in the `catch` so the loop actually retries on the next 500ms poll — today it does not retry at all on failure, relying entirely on some unrelated mutation to re-arm `changed`. This directly addresses the most likely explanation for "my edit silently disappeared" reports.
2. **(High impact, low effort) Await `stream.close()` in `OpfsStorage.setItem`.** `src/ts/storage/opfsStorage.ts:14` — add `await` before `stream.close()`. Trivial fix, currently latent because the `opfs_flag!` gate makes the class unreachable, but should be fixed regardless before anyone flips that flag (or removes the gate).
3. **(Medium impact, low effort) Surface write failures to the user immediately, not only once alerts begin at the 5th accumulated failure.** `globalApi.svelte.ts:474-482` — even a non-blocking toast on the first failure would let users notice before closing the tab. Combine with recommendation 1 so a genuine retry actually happens instead of relying on incidental re-triggers.
4. **(Medium impact, medium effort) Add basic quota awareness.** Before the write in `saveDb()` (`globalApi.svelte.ts:447-467`), optionally check `navigator.storage.estimate()` and warn (not block) when usage/quota crosses a threshold (mirroring the `QUOTA_WRITE_CEILING`-style margin used elsewhere in the ecosystem); and explicitly catch `QuotaExceededError` to give a specific, actionable error message (e.g., "storage full — delete old chats/backups") instead of the generic alert path.
5. **(Medium impact, medium effort) Prune `database/dbbackup-*.bin` more aggressively or make it opt-in for non-Tauri users.** Every single autosave cycle currently writes a full extra backup copy in addition to the primary file (`globalApi.svelte.ts:454-463`), pruned only down to the most recent 20 (`getDbBackups`, `globalApi.svelte.ts:493-529`). For large save files this meaningfully accelerates quota exhaustion on web, worsening item 4's blast radius; consider debouncing/rate-limiting the backup write independent of the primary save cadence.
6. **(Medium impact, medium effort) Add a real lock/coordination between `loadDrive()`'s restore write and the running autosave loop**, e.g. a module-level flag the autosave loop checks before writing, set for the duration of a drive restore, to close the race window described in the Concurrency section (`drive.ts:365-384` vs. `globalApi.svelte.ts:409-485`).
7. **(Low-medium impact, medium effort) Snapshot the database before/at the start of each `RisuSaveEncoder.set()` call** (`globalApi.svelte.ts:441`, `risuSave.ts:202-302`) using `getDatabase({ snapshot: true })` instead of the live reactive object, to eliminate the theoretical torn-read-across-blocks risk during multi-await incremental encoding.
8. **(Low impact, low effort) Decide OPFS's fate deliberately.** Either wire up a real UI/settings path that sets `opfs_flag!` (so the better-atomicity backend is actually used on capable browsers) or remove the dead `OpfsStorage` class and its `AutoStorage` branch to reduce confusion for future contributors (and correct AGENTS.md's description of the active backend set).
9. **(Low impact, medium effort) Extend `remoteSaveCleanup`'s test coverage (or explicitly document its scope) to cover the I/O side in `cleanChunks()`** (`bootstrap.ts:511-589`), or, if remote blocks remain Tauri/Node-only, note in AGENTS.md that this test suite doesn't exercise the web build's persistence path at all, so future contributors don't over-index on "there are tests here, so this area is covered."
