# Investigation: "Corrupted" Character/Module/Persona Image Assets

Read-only investigation. No source files were modified. All findings below are traceable to file:line references in the repository as it exists at the time of this investigation (main branch, commit `51bc23b7` at HEAD), unless explicitly marked "external/unverified claim."

> **Cross-validated** via an independent Codex adversarial-review pass (`Agents/CodexReviews/03-asset-corruption.codexreview.md`). Verdict: **partially confirmed with corrections**. All four root-cause mechanisms are independently confirmed as real. Four corrections were applied in place below: the GC-omission finding's impact was overstated for NAI/Wavespeed assets (they retain separate base64 copies used for generation, so deletion mainly breaks the *preview*, not the feature — GPT-SoVITS is the one case with genuine functional loss since TTS calls `loadAsset(assetId)` directly), `reference_image_multiple` shouldn't have been listed as an omitted field (no current asset-writing path populates it), the zero-byte cache-poisoning finding's "forever"/"permanent" language oversold it (cache entries can still be evicted or cleared — it persists until removed, not literally forever), and the `checkImg()` finding's "every re-render" and "arbitrary" match language was broader/less precise than the code supports (it reruns tied to `markParsingResult` resolution, and the nearest-neighbor match is deterministic with asset-order tie-breaking, not arbitrary).

## Executive Summary

The bug is real, has at least **three independent root causes**, and the community browser extension's reverse-engineered model of it is **highly accurate** — nearly every specific file:line claim it makes checks out against the current source, often to the exact line. This is unusual for third-party reverse-engineering and means the plugin's evidence can be trusted as a strong lead, though it was still independently re-derived here rather than taken on faith.

The three confirmed mechanisms, roughly in order of severity:

1. **Unbounded fuzzy image-name collapse in `ChatBody.svelte`'s `checkImg()`** (opt-in, but severe when triggered): once `newImageHandlingBeta` is on, `checkImg()` re-scans already-resolved `<img src="/sw/img/<hex>">` elements, fails to recognize that src as "already resolved," and falls into an unbounded Levenshtein nearest-neighbor search with no distance cap — collapsing many different images onto one wrong asset. This is a genuine, serious bug in current code, not a stale claim. **[corrected]** Two details in the original phrasing were broader than the code supports: this doesn't rerun on literally "every re-render" — it's tied to the `markParsingResult` derived value's resolution (runs once immediately and again when that promise resolves); and the resulting mismatch isn't "arbitrary" — the nearest-neighbor search is deterministic for a given asset ordering, with ties broken by that order, not by chance.
2. **Incomplete boot-time GC allowlist (`getUncleanablesSync`) sweeping still-referenced assets out of local storage.** Several fields that legitimately reference `assets/*` paths (image-generation reference images, TTS ref-audio) are never added to the "uncleanable" set, so `cleanChunks()` deletes their local copies on a normal boot while the character/database still points at them. **[corrected]** The functional impact differs by field, corrected here: GPT-SoVITS reference audio is the strongest genuine-data-loss case, since TTS calls `loadAsset(assetId)` directly against the now-deleted local copy. NAI image-gen and Wavespeed reference images are less severe than originally stated — both also retain a separate base64-encoded copy used directly by the generation flow, so deleting the `assets/*` copy mainly breaks the cached *preview* rendering, not the underlying feature. `reference_image_multiple` should not have been listed as an omitted field at all — no current UI/asset-writing code path was found that populates it via `saveAsset`; the active "vibe" flow uses a separately-encoded `vibe_data` field instead.
3. **Zero-byte service-worker cache poisoning.** `getFileSrc()` can `fetch("/sw/register/...")` with an `undefined`/null body when a forage read misses; the service worker (`public/sw.js`) happily caches that as a 0-byte `Response`. From then on `/sw/check/` reports `able:true`, so the app never re-registers the image. **[corrected]** "Renders blank forever" overstates this: the failure is persistent and self-sustaining under normal app behavior (nothing in the app's own logic will ever fix it), but the underlying `CacheStorage` entry is still an ordinary cache entry that can be evicted by the browser or manually cleared — so "persists until the entry is removed or evicted" is the accurate framing, not a literal permanent/forever state.

A fourth, lower-severity issue (stale `risuSaveBlock_*` rows never pruned) is confirmed as a literal fact but is storage bloat, not asset corruption, because the `__directory` mechanism already excludes orphaned rows from being loaded.

None of the six "corrupt" grep hits in `src/ts` turned out to be about image assets at all — they're unrelated (save-file corruption, cold-storage chat corruption, memory-system JSON corruption, script-import corruption). This is itself a useful negative finding: there is no first-party code today that detects or names "asset corruption" as a concept.

## Verification Results

### Hypothesis 1 — Service worker / CacheStorage as a leaky front for asset bytes
**CONFIRMED.** `public/sw.js:3-84` implements `/sw/img/`, `/sw/check/`, `/sw/register/`, `/sw/init/`, `/sw/share/` against `caches.open('risuCache')` (line 88/103/112). `getSource()` (line 102-105) simply does `cache.match(url)` with no fallback to a source of truth if the cache entry is stale or wrong — the service worker is a pure cache-shaped proxy, not a validating one. `src/ts/globalApi.svelte.ts:136-172` (`getFileSrc`, `usingSw` branch) confirms the source of truth is `forageStorage.getItem(loc)` (localforage/OPFS/node/account per backend), fetched into the SW cache lazily via `/sw/register/` only on a cache miss (line 145-159) — so once an entry exists in `risuCache`, it is never revalidated against local storage again. This is the structural precondition for every other bug below: nothing keeps the cache honest after the first write.

### Hypothesis 2 — `getUncleanablesSync` allowlist omits legitimate asset references
**CONFIRMED, exact.** `src/ts/globalApi.svelte.ts:933-1028` (`getUncleanablesSync`) walks `db.customBackground`, `db.userIcon`, each character's `image`/`emotionImages`/(for non-group characters) `additionalAssets`/`vits.files`/`ccAssets`, `db.modules[].assets`/`.icon`, `db.personas[].icon`/`.embeddedModule`, and `db.characterOrder[].imgFile` (lines 954-1026). There is **no reference anywhere in this function, or in `getUncleanables` at lines 909-924, to `gptSoVitsConfig`, `NAIImgConfig`, or `wavespeedImage`** — grepping the whole function body confirms these identifiers do not appear. The plugin's claim is exactly right, down to the cited line range matching this repo's current line range almost verbatim.

`cleanChunks()` in `src/ts/bootstrap.ts:511-638` then uses this set directly as the deletion allowlist. On non-Tauri (web/localforage) profiles, the `else` branch at lines 592-603 iterates every `forageStorage` key, and for any key starting with `assets/` whose `getBasename()` is not in `uncleanable`, calls `await forageStorage.removeItem(asset)` (line 601) unconditionally — no confirmation, no dry run. This runs on **every normal boot** via `cleanChunks()` at `bootstrap.ts:257`, gated only by `db.account?.useSync` (line 516-518) and `db.coldstorage` (line 519-521).

**Practical effect:** any user who has ever set a GPT-SoVITS reference audio, an NAI image-gen reference/character image, or a Wavespeed reference image will have that asset's `assets/*` local-storage copy silently deleted on the very next app boot — even though the character/database JSON still points at it. **[corrected]** The severity differs by field, and the original draft of this paragraph generalized too far. GPT-SoVITS reference audio is the clearest case of genuine, eventual functional loss: TTS reads it back via `loadAsset(assetId)` directly, with no fallback, so once the local copy is gone and its SW cache entry (Hypothesis 1) is eventually evicted, the reference becomes unresolvable and TTS breaks for that character. NAI and Wavespeed reference/character images are less severe than stated: both features also retain a separately-encoded base64 copy that the actual generation call reads from, independent of the `assets/*` local-storage copy — so deleting the local copy mainly breaks the cached *preview* image shown in the UI, not the generation feature itself. `reference_image_multiple` should not be included in this list at all — no current asset-writing code path was found that populates it via `saveAsset`. The remaining, corrected claim — that the image keeps rendering only as long as the SW cache entry happens to survive, and becomes unresolvable once it's evicted — still matches the reported symptom of assets going bad "randomly" and later rather than immediately, for the fields where it genuinely applies (GPT-SoVITS ref-audio in particular).

### Hypothesis 3 — Trash retention window and account/cold-storage bail-out
**CONFIRMED, exact.** `src/ts/bootstrap.ts:496-503`:
```
for (let i = 0; i < db.characters.length; i++) {
    const trashTime = db.characters[i].trashTime;
    const targetTrashTime = trashTime ? trashTime + 1000 * 60 * 60 * 24 * 3 : 0;
    if (trashTime && targetTrashTime < Date.now()) {
        db.characters.splice(i, 1);
        i--;
    }
}
```
This is literally a 3-day (`1000*60*60*24*3` ms) retention window inside `checkNewFormat()`, called at `bootstrap.ts:227`, i.e. *before* `cleanChunks()` runs at line 257 on the same boot — matching the plugin's claimed ordering exactly. `cleanChunks()` itself bails at lines 516-518 (`db.account?.useSync`) and 519-521 (`db.coldstorage`) before building the uncleanable set or touching storage, confirming the account-sync/cold-storage exemption claim precisely.

### Hypothesis 4 — `checkImg()` unbounded fuzzy re-collapse of already-resolved `/sw/img/` URLs
**CONFIRMED — and this is the most serious finding in the investigation.** `src/lib/ChatScreens/ChatBody.svelte:181-256`:

- Line 182: gated by `DBState.db.newImageHandlingBeta` (an off-by-default advanced setting — confirmed no default assignment in `src/ts/storage/database.svelte.ts`, and it's exposed as a checkbox in `src/ts/setting/advancedSettingsData.ts:164`, labeled "New Image Handling (Beta)" per `src/lang/en.ts:1530`).
- Line 185: the query selector excludes `src^="data:"`, `http:`, `https:`, `blob:`, `file:`, `tauri:`, and `[noimage]` — but **not** a bare root-relative path like `/sw/img/<hex>`. An already-resolved `<img>` (set at line 216: `img.src = await getFileSrc(foundAsset)`, which for a `usingSw` profile returns exactly `"/sw/img/" + encoded` per `globalApi.svelte.ts:148/159/171`) matches none of the exclusions and is re-selected on the *next* invocation of `checkImg()`.
- `checkImg()` re-runs via the `$effect` at lines 260-267 (`markParsingResult.then(checkImg)`) — invoked once immediately and again when that promise resolves. **[corrected]** "On essentially every message re-render" overstates the trigger frequency; more precisely, it reruns when the derived markdown-parse result (`markParsingResult`) changes and again on that parse's resolution, not on every arbitrary re-render.
- Line 200: `name = img.getAttribute('src')?.toLocaleLowerCase()` — for a re-selected element this is the full `/sw/img/<hex>` string.
- Line 205: `name.includes(':')` is checked — `/sw/img/<hex>` contains no colon, so it passes.
- Line 211: exact-match lookup in `exactAssets` fails (no asset is literally named `/sw/img/<hex...>`).
- Lines 224-237: fallback fuzzy search. `prefixLoc = name.lastIndexOf('.')` — a hex string has no `.`, so `prefixLoc <= 0` and `prefix = ''`. The loop `for (const asset of normalizedAssets) { if (!asset.name.startsWith(prefix)) continue; ... }` therefore accepts **every** asset (empty-string `.startsWith('')` is always true), and computes `getDistance(name, asset.name)` with **no maximum-distance cutoff** — `currentDistance` starts at `1000` and is simply minimized, with no reject threshold analogous to `assetMaxDifference` in the parser's `getClosestMatch` (`parser.svelte.ts:619`).
- Line 238-243: whatever asset has the smallest edit distance to the hex string gets assigned: `img.setAttribute('src', got)`. **[corrected]** This selection is not "arbitrary" — for a given hex string and a given ordering of `normalizedAssets`, the minimization is deterministic; ties are simply broken by iteration order over that array, not by chance.

Net effect: with the beta setting on, every already-correctly-resolved image in the chat is at risk of being silently reassigned, on a later render pass, to whichever asset happens to have the smallest Levenshtein distance to its own `/sw/img/<hex>` URL — which, since hex strings are all long and character-similar, tends to collapse onto the *same* one or two assets across many different images. This matches the plugin's description of "many different images collapsing onto one wrong asset" precisely, and the mechanism was independently re-derived here by reading the selector, the exact/fuzzy branches, and the `$effect` re-trigger, not merely trusted from the plugin's comment.

Severity caveat: this path requires `newImageHandlingBeta === true`, an opt-in advanced setting with no default. It is not the default-path cause of the bug, but for any user who *has* enabled it, it is a severe and easily reproducible corruption source. **[corrected]** The "randomness" reported by users is better attributed to *which* markdown-parse events happen to trigger `checkImg()` and to asset-list ordering at the time, rather than to any nondeterminism in the match itself — the match, once triggered, is deterministic, not random.

### Hypothesis 5 — Stale `risuSaveBlock_*` forage rows
**CONFIRMED as a literal fact, but downgraded in impact.** `src/ts/storage/risuSave.ts:370` (`encodeRawBlock`) writes `risuSaveCacheForage.setItem(\`risuSaveBlock_${arg.name}\`, ...)` for every block (root, characters, modules, etc.) on every save. A repo-wide grep for `risuSaveCacheForage.removeItem` and `removeItem(\`risuSaveBlock` returns **zero matches** — there is genuinely no code path that ever deletes a `risuSaveBlock_*` row. However, reading the decoder (`risuSave.ts:480-521`) shows the `ROOT` block carries an `__directory` array (written at `risuSave.ts:295`: `obj["__directory"] = Object.keys(this.blocks).filter(key => key !== 'root')`), and only keys listed in `__directory` get loaded back as character blocks (lines 492-518). A deleted character's stale row is simply never referenced again — it is orphaned but does not get loaded, does not get mistaken for a live character, and does not on its own cause an image to render wrong. It is disk/IndexedDB bloat (unbounded growth of `risuSaveCache`'s `keyvaluepairs` store), not asset corruption. It only becomes relevant to the corruption story indirectly: it means naive corruption-detection heuristics (like scanning all rows) will over-count "existing" characters, which is why the plugin's own code explicitly filters by `liveBlockNames`/`__directory` before doing anything else.

## Root-Cause Synthesis (independent conclusion)

Based only on the code read in this repository, "corrupted" character/module/persona images are not one bug but the visible symptom of a storage architecture with three layers that don't stay synchronized, plus one severe (opt-in) rendering bug:

1. **No layer revalidates the service-worker cache against the source of truth.** `sw.js` is a pure lookup cache (`cache.match`) with a lazy, one-shot populate-on-miss (`getFileSrc`'s `/sw/register/` call). Nothing ever re-checks a cached entry once written, so any divergence between local storage and the cache — however it originates — is permanent until a manual cache-bust.
2. **The boot-time GC (`getUncleanablesSync` → `cleanChunks`) is not kept in sync with new features that reference `assets/*`.** GPT-SoVITS ref-audio, NAI image-gen images, and Wavespeed reference images are recent-ish feature additions whose asset-referencing fields were never added to the allowlist function. This is a straightforward maintenance gap — the allowlist function is manually enumerated rather than derived from a schema/registry of "all places an assets/ path can appear" — so it will keep drifting as new features are added. **[corrected]** GPT-SoVITS is the clearest match for "this is the most likely explanation for TTS-related reports" — NAI/Wavespeed's retained base64 copies mean this maintenance gap there is more likely to produce a broken/stale *preview* than a broken feature (see the corrected GC-omission finding above).
3. **A zero-byte cache write is treated as a successful cache hit that the app's own logic will never self-correct.** `getFileSrc()` doesn't guard against `forageStorage.getItem(loc)` returning `undefined`/`null` before POSTing it as the register body; `registerCache()` in `sw.js` doesn't reject empty buffers; `/sw/check/` can't distinguish "cached and valid" from "cached and empty." **[corrected]** Any transient local-storage miss (e.g., racing with the GC sweep above, or reading during a backend switch) becomes a blank image that persists until the cache entry is removed or evicted (by the browser, or manually) — the original "permanent"/forever framing overstated this; it's self-sustaining under normal app behavior, not a guaranteed-permanent state.
4. **(Opt-in) `checkImg()`'s unbounded fuzzy search is an outright logic bug**, independent of the storage layers above: it re-processes URLs it itself produced, misclassifies them as unresolved asset names because its exclusion filter only checks for URL schemes and not for its own output shape, and has no distance ceiling on the fallback match. This can corrupt *correctly cached, perfectly healthy* assets purely through the rendering pipeline, with no cache or GC involvement at all — which likely explains reports where "wrong image" happens rather than "blank image." **[corrected]** The resulting mismatch is deterministic (asset-order tie-breaking), not arbitrary, and the trigger is tied to markdown re-parse events, not literally every render.

None of these four mechanisms are mutually exclusive, and a single affected user could easily be hitting more than one — which is consistent with "corrupted" being reported as a vague, seemingly random catch-all symptom rather than one clean bug.

## What the Community Plugin's Remediation Implies a First-Party Fix Should Cover

The plugin's design (read in `main-world.js`, `content.js`, `popup.js`) implies these functional pieces are necessary for a complete fix:

- **Delivery-path check** (`diagnose()`): distinguish "service worker isn't controlling the page" (needs a reload) from "cache is actually wrong" — these look identical to the user (blank/wrong images) but need completely different fixes.
- **Zero-byte detection and purge** (`purgeEmpty()`): find and drop cache entries with `byteLength === 0`, since RisuAI's own `/sw/check/` logic treats their mere existence as success and will never re-register them.
- **Cache-vs-source-of-truth verification and rewrite** (`verify()`/`rebuild()`): byte-compare each `/sw/img/` cache entry against local storage's copy of the same asset, and rewrite mismatches from local storage — but only when local storage's copy isn't suspiciously *smaller* than the cached one (their `SHRINK_REFUSAL_RATIO` guard), since a shrink might mean the cache is actually the good copy.
- **GC-survivor prediction before deletion** (`purgeVerified()`): before deleting any cache entry, predict whether the upcoming boot's `cleanChunks()` sweep would delete the *local* copy too (by replicating `getUncleanablesSync`, deliberately including its known omissions) — because deleting the last-resort cache copy of an asset the GC is about to orphan turns a recoverable problem into permanent data loss.
- **Duplicate/collapse detection** (`fingerprint()`, `diagnoseNames()`, `diagnoseResolution()`, `inspectRendered()`): hash cache entries to find accidental duplicates, and separately simulate the chat-name-resolution pipeline (including the fuzzy fallback) to show which asset *names* collapse onto which *files* — this is the only way to catch the `checkImg()`-style bug, since it's invisible to byte-level cache comparison.
- **A live DOM guard** as a stop-gap for the `checkImg()` bug specifically: rewrite `/sw/img/` src attributes to their absolute form (so they fail `checkImg()`'s selector on the next pass) and pre-emptively mark truly-unresolvable names `noimage` — i.e. patch around the bug's *trigger condition* (relative URL matching the "needs resolving" selector) rather than its root cause.

## Recommendations, Ranked by (Impact, Effort)

1. **(High impact, Low effort) Fix `checkImg()`'s selector to exclude already-resolved `/sw/img/` sources.** Add `:not([src^="/sw/img/"])` (or equivalently check `src.startsWith(location.origin + '/sw/img/')`/`'/sw/img/'`) to the query selector at `ChatBody.svelte:185`, matching the exclusions already present for `data:`/`http:`/`https:`/`blob:`/`file:`/`tauri:`. This alone eliminates the entire unbounded-collapse bug at its trigger point with a one-line change, for the population of users who have `newImageHandlingBeta` on.

2. **(High impact, Low effort) Add a distance ceiling to `checkImg()`'s fuzzy fallback**, mirroring `parser.svelte.ts:619`'s `if (closestDist > DBState.db.assetMaxDifference) return null`. Currently `ChatBody.svelte:226-237` has no reject threshold at all — even without Recommendation 1, this bounds the blast radius of any bad match to genuinely close names instead of "whatever asset happens to be closest out of everything."
