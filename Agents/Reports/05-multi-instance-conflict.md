## Summary

RisuAI has effectively **zero real, verifiable conflict detection** for concurrent writers on any path this repository's code controls. The one mechanism that resembles one — the `BroadcastChannel('risu-db')` guard in `saveDb()` (`src/ts/globalApi.svelte.ts:379-626`) — only works within one browser profile on one device, is far more aggressive than "same-tab protection" (it fires a forced-reload prompt in every other open tab the moment *any* tab starts its very first save, discarding that tab's unsaved in-memory edits without asking), and is silently absent whenever `window.BroadcastChannel` doesn't exist. The plain-browser (LocalForage) and self-hosted Node-server backends are **confirmed** last-write-wins with no version counter, ETag, timestamp check, or lock — `server/node/server.cjs`'s `/api/write` is a bare `fs.writeFile`. The account-sync cloud backend's conflict behavior is **not confirmed either way** by this repository: it sends a `x-risu-session`/`x-risu-save-date` header pair and can be told to `reloadSession`, which is suggestive of *some* server-side enforcement, but that logic lives entirely on Risu's remote hub service, outside this repo, and could not be inspected. Separately, and more urgently: account-sync bootstrap has a **confirmed** bug where a transient cache-mismatch signal from the server (`303`/`match:false`) is indistinguishable, in the client code, from "no remote database exists yet," and is handled by silently overwriting the real remote database with an empty one (`src/ts/bootstrap.ts:157-163`) — a data-loss path that requires no multi-writer race at all, just one unlucky read.

## 1. Local multi-tab (same browser)

Full mechanism, `src/ts/globalApi.svelte.ts:379-626`:

- On `saveDb()` start, each tab generates a fresh `sessionID = v4()` (line 383) and, if supported, opens `new BroadcastChannel('risu-db')` (lines 384-387).
- `channel.onmessage` (lines 389-399): if a message arrives whose payload isn't this tab's own `sessionID`, and this tab hasn't already flagged `gotChannel`, it sets `gotChannel = true` and calls `alertNormalWait(language.activeTabChange).then(() => location.reload())` — a **blocking, user-dismissable alert** (`alertNormalWait` at `src/ts/alert.ts:92-98` calls `waitAlert()`) after which the tab hard-reloads, discarding all in-memory state.
- Inside the save loop, every single time this tab is about to write (not just the first time — every iteration where `changed` was true and `gotChannel` is still false), it does `channel.postMessage(sessionID)` (line ~564) immediately before encoding/writing.
- If `gotChannel` is already true for this tab, it skips writing entirely, re-merges `toSave` back into the live tracker via `mergeUnsavedChanges`, sleeps 1s, and loops (lines ~556-560) — i.e. once a tab has "lost", it stops trying to persist anything locally and just waits to be reloaded.

**Is it effective?** Only as a *nag-to-reload*, not as a conflict resolver, and it is far more aggressive than the background brief assumed:

- **It fires on the very first save, not just on an actual conflicting write.** Because `postMessage` happens on *every* save cycle in every tab, opening a second tab and letting either tab's debounce timer fire (~500ms–1.5s after any edit) will trigger the reload prompt in the *other* tab almost immediately — even if the two tabs never touched the same character/chat. This isn't fine-grained conflict detection; it's "only one tab may ever be the active writer," enforced by nagging every other tab into reloading.
- **The reload itself is a data-loss vector.** When the losing tab's user clicks through `alertNormalWait` (or if some UI path auto-dismisses it), `location.reload()` runs unconditionally. Any edits typed in that tab since its last successful save — including edits made in the ~1.5s window between the debounce firing and this message arriving — are discarded with no "save first?" prompt. The very mechanism meant to prevent silent overwrite causes a different flavor of silent loss (in-memory unsaved edits in the losing tab).
- **Race window between "tab A posts intent" and "tab B reacts":** `postMessage` is fire-and-forget; tab A proceeds immediately to `encoder.set()` / `encode()` / `writeFile`/`setItem` without waiting for any acknowledgment from tab B. If tab B is mid-way through its *own* `encoder.set()`/write when A's message arrives (B hasn't reached the `if (gotChannel)` check yet, e.g. it's still inside `await encoder.set(db, toSave)` or the storage write awaits), B will still complete and issue *its* write after A's, because the `gotChannel` check only gates the *next* loop iteration, not an in-flight one. Two writes can still land back-to-back with no ordering guarantee tied to which edit is "newer" — whichever async write's Promise resolves last on the storage backend wins.
- **No `window.BroadcastChannel` support:** `channel` stays `undefined` (line 386's `if (window.BroadcastChannel)` guard), `if (channel)` blocks are skipped entirely (lines 389, ~562-564), and the tab silently runs with **no cross-tab awareness whatsoever** — it neither announces its own saves nor listens for others'. This is the exact same code path as running in a browser/private mode that disables `BroadcastChannel` (documented as possible in some privacy-hardened browsers/extensions). In that case two tabs behave exactly like two independent devices/browsers hitting the same storage backend: pure last-write-wins with zero UI warning.
- **Backgrounded/throttled tabs:** A backgrounded tab's JS timers (including `setTimeout`-based debounce and the `while(true)` loop's `await sleep(...)`) can be throttled by the browser (Chrome throttles background timers to ~1/min under aggressive power-saving, or suspends via bfcache/discarding). A `BroadcastChannel` message itself is typically still delivered even to a backgrounded page (it's not timer-gated), but the *handler's reaction* (showing the alert, and more importantly the throttled tab's own save loop) can lag arbitrarily. A user who edits in a foregrounded tab, then switches to a long-backgrounded tab and resumes editing without it ever having reloaded, can still clobber the foreground tab's newer save once its throttled loop finally wakes up and writes.

## 2. Account-sync (cloud) backend

Entry points: `db.account.useSync` is read in `src/ts/storage/autoStorage.ts:48` (`checkAccountSync`) and gates whether `AutoStorage.realStorage` becomes an `AccountStorage` instance; `AccountStorage` itself lives in `src/ts/storage/accountStorage.ts`.

- **Write path** (`accountStorage.ts:22-100`, `setItem`): POSTs the full encoded blob to `/api/account/write` on the hub (`fetchProtectedResource`, `sionyw.ts`), with headers `x-risu-key` (storage key, e.g. `database/database.bin`), `x-risu-session` (a per-tab `sessionNumber` fetched once from `/api/account/getsessionnumber` and cached in the module-level `risuSession` variable, line 39-46), and `x-risu-save-date` (`Date.now()` at call time, line 37).
- The server can respond with a JSON body containing `warning` (surfaced via `AccountWarning` store) or `reloadSession: true`, which — like the BroadcastChannel path — forces `alertNormalWait(language.activeTabChange)` then `location.reload()` (lines 73-79), followed by `await sleep(100000000)` to permanently stall that call.
- The presence of a per-session number and a `reloadSession` signal strongly suggests the hub *does* do some server-side "only one active writer session per account" enforcement, conceptually similar to the BroadcastChannel mechanism but extended across devices/browsers via the network. **However, the actual server-side logic is not in this repository** (`server/node/server.cjs` implements only the self-hosted Node-server API, `/api/*`, not `/api/account/*` — those are hub endpoints on Risu's remote service). I could not verify: whether `reloadSession` is triggered by an actual conflicting write, by session count, or by something unrelated (e.g. token rotation); whether `x-risu-save-date` is used for any last-write comparison or is purely informational/logging; or whether the server rejects a stale write (e.g. via a 409) — no such status code is handled in `accountStorage.ts`'s `setItem`, which only branches on `status === 403` (auth) and `status === 304` (cache-hit, read-only path) — **there is no 409/412/428 handling anywhere in `accountStorage.ts`, so if the hub does reject conflicting writes with a conflict status, the client code has no logic to act on it** and would fall through to `if(da.status < 200 || da.status >= 300){ throw await getDaText() }` (line 93-95), surfacing as a generic save error/retry rather than a merge or reload prompt.

  **[Corrected — Codex round 1]** The line above stops at the right place: this section should not, and originally did not intend to, assert account-sync's cross-device conflict behavior as *confirmed* last-write-wins. That stronger claim appeared in this report's Summary and in Scenario 1 (section 6) and has been walked back there — the honest position is that account-sync's conflict handling is **unverified and hub-dependent**, not a confirmed gap, given the session/date/reloadSession machinery that clearly exists for *some* purpose we can't fully characterize from this repo alone.
- **Read path** (`getItem`, lines 101-168) appends a fresh `v4()` UUID to the request path specifically for `database`-containing keys (line 114) — presumably a cache-buster — and sends the last-cached `x-risu-save-date` (from `cachedForage`) so the server can reply `304` (unchanged, read from `cachedForage`) or `303` with `{match: true}` (also read from cache) or `303` with `{match:false}` implying "your cache is stale, don't trust it" (`da.status === 303` handling, lines 126-135) — `303`+`match:false` returns `null`, which callers must handle as "no data," a subtlety that could itself cause a false "empty database" read if mis-handled upstream (not verified further; out of this investigation's direct scope but flagged in section 7).
- **Debounce/timer independence across devices:** each device runs its own independent `saveDb()` loop with its own debounce timer (500ms after last edit, `saveTimeoutExecute`, lines ~419-425) and its own `await sleep(500)`/`sleep(1000)` cadence in the `while(true)` loop. There is no cross-device coordination of *when* a save fires — two devices editing around the same time will each independently decide to push a full snapshot on their own schedule, so "last writer" is genuinely "whichever device's local timer/network round-trip happens to complete last," with no relation to which edit is semantically newer or more complete. This matches the background brief's suspicion exactly.
- **Backups are explicitly disabled for account-sync web users**: `getDbBackups()` (`src/ts/globalApi.svelte.ts:632-635`) starts with `if (db?.account?.useSync && !isTauri && !isNodeServer) { return [] }` — i.e., pure browser + account-sync has **no local numbered backup files at all** (see section 4).
- **Risu-Kei opt-in server backup** (`src/ts/kei/backup.ts`): a *separate*, optional, account-gated (`db.account.kei`) auto-backup feature that POSTs the full `db` object to a distinct "Kei" server (`keiServerURL()`) at most once per 5 minutes (`saveDbKei`, lines 82-114), and exposes a restore UI (`autoServerBackup`, lines 6-80) that lists named/timestamped backups and lets the user pick one to restore via `setDatabase()`. This is the only real point-in-time history mechanism for account-sync users, but: (a) it's off by default and requires opting in, (b) it's rate-limited to 5-minute intervals so an overwrite-then-immediately-another-overwrite within that window can still land between two Kei snapshots, and (c) it saves the *survivor's* view of the DB, not necessarily the loser's — if device A's save clobbers device B's edit and then Kei's 5-minute timer fires on device A, the snapshot captured is the clobbered (data-losing) state, not a recovery point for B's lost edit.

## 3. Self-hosted Node server backend

`src/ts/storage/nodeStorage.ts` (client) and `server/node/server.cjs` (server), confirmed by direct read:

- Client `setItem` (`nodeStorage.ts:72-90`) POSTs to `/api/write` with a hex-encoded `file-path` header and a JWT-like `risu-auth` header (ES256-signed, 5-minute expiry, `createAuth()` lines 13-38) — no version/ETag/If-Match header is sent at all.
- Server handler `app.post('/api/write', ...)` (`server.cjs:1278-1305`): validates auth, validates the path is hex (`isHex`), then unconditionally does `await fs.writeFile(path.join(savePath, filePath), fileContent)` and responds `{success:true}`. **There is no locking, no version check, no read-before-write, no atomic rename-swap, no ETag/If-Match support, no conflict rejection of any kind.** Two concurrent `POST /api/write` calls to the same `filePath` (e.g. two devices/browsers pointed at the same self-hosted server, each pushing `database/database.bin`) simply race at the OS `fs.writeFile` level — whichever call's write syscall completes last wins, full stop. `fs.writeFile` in Node is not guaranteed atomic across concurrent writers to the same path (it opens, writes, and closes; two interleaved writers to the same file can in the worst case even interleave bytes, though in practice with typical single-shot buffer writes on most filesystems it's more likely a clean "last write replaces the file" outcome — I could not verify which without a live concurrency test against the actual server, noted as an open question).
- `/api/read` (`server.cjs:1183-1213`) and `/api/list` (1261-1276) are equally simple — plain file read / directory listing, no version metadata returned alongside content that a client could use to detect staleness.
- Net effect: the self-hosted Node server is **strictly last-write-wins with no partial mitigation whatsoever** — weaker than account-sync (which at least has *some* session/date headers, even if their enforcement is unverifiable) and, unlike Tauri, has no local numbered-backup file rotation either (see section 4) beyond what `getDbBackups()` does when `isNodeServer` is true.

## 4. Recovery paths

- **Tauri desktop**: every successful save writes both `database/database.bin` and a new `database/dbbackup-<timestamp/100ms>.bin` in the same call (`globalApi.svelte.ts` isTauri branch, ~lines 573-575), and `getDbBackups()` (lines 636-651) keeps the most recent 20, pruning older ones. Because the backup write happens **as part of, immediately after, the very save that may have clobbered another writer's data**, by the time a user notices something is missing, the backup rotation has very likely already recorded (and possibly already pruned, since it caps at 20) the *overwriting* state, not a pristine copy of the *victim's* pre-clobber data — unless the victim's own device also independently wrote its own backup before being overwritten (only true for the write that *lost* the race, i.e. was itself overwritten later locally, which doesn't apply to the cross-device case where the overwrite happens entirely on the other device's storage). In short: Tauri's backups protect against *this device's own* bad save/corruption, not against a **remote/other-device** overwrite, because Tauri bypasses shared storage entirely (writes straight to its own local filesystem — see background brief) and never sees the other device's write at all.
- **Plain browser (LocalForage/IndexedDB), non-account**: same pattern via `forageStorage.setItem('database/dbbackup-...')` and `getDbBackups()` (lines 653-666), 20-backup cap, but this is **per-browser-profile local storage** — it does nothing for cross-tab/cross-browser/cross-device conflicts, only for recovering from this profile's own bad save.
- **Account-sync (web, cloud)**: **no local backup rotation at all** — `getDbBackups()` explicitly short-circuits to `[]` for this case (`globalApi.svelte.ts:632-635`, guarded by `db?.account?.useSync && !isTauri && !isNodeServer`). The only recovery path is the opt-in Risu-Kei auto-backup described in section 2, which is off by default.
- **Node-server-backed browser**: `getDbBackups()`'s early-return only excludes the pure-account-web case; `isNodeServer` is explicitly allowed through to the LocalForage-style backup branch (line 632's condition), so `forageStorage.setItem('database/dbbackup-...')` still runs on the *client's own browser* IndexedDB when talking to a self-hosted Node server — meaning the numbered backups live in the browser's local cache, not on the Node server itself. If the browser's IndexedDB is cleared (or a different browser/device is used against the same server), those backups are gone even though the server-side `database.bin` persists. The server itself keeps no backup/history of its own — `/api/write` just overwrites in place (section 3).
- **In-memory-only "BackupDb"**: `syncDrive()` (`src/ts/drive/drive.ts:112-115`), called at the very top of every `saveDb()` invocation, just does `BackupDb = safeStructuredClone(getDatabase())` — despite the name, this is **not** a real Google-Drive sync or persisted backup; it's a single in-memory snapshot variable that lives only in that tab's JS heap and is lost on reload/crash. (Flagged more explicitly in section 7 as a possibly-misleading name/no-op-looking side effect, since a reader skimming `saveDb()` could easily assume "the drive gets synced here" when nothing is persisted.) The actual Google Drive backup (`backupDrive`, `drive.ts:118+`) is a separate, presumably manually-triggered upload flow, not part of the autosave loop's conflict story.
- **Conclusion**: for the two multi-device-capable backends (account-sync and self-hosted Node server) — the ones where a real cross-device conflict can actually occur — the built-in automatic backup mechanisms either don't run at all (account-sync web) or run against local-only client storage that doesn't travel with the shared server state (Node-server browser cache). A user who loses data to a cross-device overwrite has, at best, the opt-in Kei history (account-sync only) and otherwise **no built-in way to recover the clobbered version**.

## 5. Chat-level granularity

`RisuSaveEncoder` (`src/ts/storage/risuSave.ts:124-303`) builds a set of named "blocks" (root, preset, modules, loadouts, plugins, pluginStorage, and one block per character — `RisuSaveType.CHARACTER_WITH_CHAT`, which embeds **that character's entire chat history**, not per-chat granularity; `chat` in `toSaveType` — `risuSave.ts:83-91` — is used only to decide *which character* needs re-encoding, there is no separate per-chat block type actually used for storage). `set()` (lines 202-302) is genuinely incremental in the sense that it only re-`encodeBlock`s the characters/sections flagged dirty in `toSave`, reusing cached blocks (`this.blocks[...]`) for everything else — this is a real optimization for encode *cost*, not for reducing conflict *blast radius* at the storage layer, because:

- `encode()` (lines 304-326) always concatenates **every** block currently held (dirty or not) into one single `ArrayBuffer`, and `saveDb()` always writes that single buffer to the single key `database/database.bin` (`globalApi.svelte.ts` ~line 570 for Tauri, ~line 578 for `forageStorage.setItem`). So for plain browser storage and for account-sync, **every autosave writes the entire database as one blob**, regardless of whether only one message in one chat changed — full last-write-wins blast radius every time.
- The one partial exception is `encodeBlock`'s `remote: 'prefer'` option (used only for character blocks, `risuSave.ts:181-190, 218-238`), which — **only when `isTauri || isNodeServer`** (`encodeBlock`, lines 328-343) and remote saving isn't disabled (`db.enableRemoteSaving`, checked via `disableRemoteSaving()`) — routes each character's actual JSON content to a *separate* storage key (`remotes/<chaId>.local.bin`, written via its own `forageStorage.setItem`/`writeFile` call, `encodeRemoteBlock`, lines 378-422), leaving only a small pointer block in the main `database.bin`. For the self-hosted Node server specifically, this means each character is a **separate HTTP `POST /api/write`** call to its own server-side file — genuinely reducing blast radius to "per character" for that backend (two devices editing *different* characters concurrently on the same self-hosted server would not stomp each other's character data, though they would still race on the small shared `database.bin` root/pointer blob, which is comparatively low-risk metadata but could still drop, e.g., a newly-created-character's directory entry if two `database.bin` writes race).

  **[Corrected — Codex round 1, was previously left as an open question in section 7]** This per-character mitigation is **opt-in, off by default**. There is no initializer anywhere in the codebase that sets `db.enableRemoteSaving`, and `disableRemoteSaving()` (`risuSave.ts:24-30`) returns `!db.enableRemoteSaving` — which evaluates to `true` (i.e. remote saving *disabled*) whenever the field is unset/undefined. So a default, freshly-configured Tauri or Node-server install gets **no** blast-radius reduction at all: every save is the same single monolithic `database.bin` write as account-sync, and two devices editing *different* characters against a default-config self-hosted server can still clobber each other's entire database, not just the shared root/pointer block. The per-character reduction described above only applies to users who have explicitly enabled this setting.
- **Account-sync gets none of this protection**: `remote: 'prefer'` requires `isTauri || isNodeServer`, which account-sync (a plain browser context, not a self-hosted node) never satisfies, so account-sync always falls to `encodeRawBlock` and inlines full character+chat JSON directly into the one monolithic blob. This means account-sync — the backend most likely to be used across multiple real-world devices (phone + laptop, etc.) — has the *worst* blast radius of all backends: any concurrent edit anywhere in the database, even to an unrelated character, risks the entire database being overwritten in one shot.

## 6. Concrete failure scenarios

1. **[Corrected — Codex round 1: downgraded from "confirmed" to "plausible but unverified," since it depends entirely on hub behavior this repo cannot inspect.] Two devices, account-sync, different characters — possible silent full-database rollback.** User has account-sync enabled on both a laptop and a phone. They send a message to Character A on the phone at 10:00:00, then five minutes later open the laptop (which still has the app open from that morning, showing the pre-10:00:00 state) and edit Character B's persona at 10:05:00. If the hub does not itself detect or reject the laptop's stale write (unverified — see section 2), the laptop's `saveDb()` loop, on its own independent debounce/timer, would encode and push the *entire* database — including its stale, pre-10:00:00 copy of Character A — to the account-sync backend, silently overwriting the phone's earlier push. If the hub *does* enforce single-writer-per-session (plausible, given the `x-risu-session`/`reloadSession` machinery), this scenario may instead surface as a `reloadSession` reload on one device rather than silent data loss. This report cannot determine which behavior actually occurs. Recovery, if the loss does occur: only possible if the user has Risu-Kei enabled (off by default) and a 5-minute-interval snapshot happened to capture the phone's state before the laptop's overwrite.

2. **[New — Codex round 1, promoted from section 7's "open question" list] Account-sync bootstrap: a single unlucky read silently blanks the remote database.** A confirmed bug, independent of any multi-writer race. On account-sync bootstrap, `AccountStorage.getItem('database/database.bin', ...)` can return `null` when the server responds `303` with `match:false` (`accountStorage.ts:126-135` — this is a "your cache is stale" signal, not "no data exists"). `src/ts/bootstrap.ts:157-163` treats any `null`/nullish result from this call as "no remote database yet" and immediately does `gotStorage = encodeRisuSaveLegacy({})` followed by `await forageStorage.setItem('database/database.bin', gotStorage)` — writing an **empty** database back to the account-sync remote, unconditionally, with no retry-with-fresh-body and no distinction between "genuinely new account" and "stale local cache". A user who hits this on a normal load (not a new account) would have their real remote database silently replaced with an empty one, no confirmation, no warning.

3. **Same browser, two tabs, no real conflict at all — forced reload discards unsaved work.** User opens the app in two tabs "just to compare something" (e.g. reference Character A's settings in tab 1 while editing Character B in tab 2) — a totally common, non-malicious pattern. The moment either tab's autosave debounce fires (≤1.5s after any keystroke that touches tracked state), it broadcasts its `sessionID`. The other tab immediately shows a blocking "active tab changed, please reload" alert and, on dismissal, reloads — discarding anything typed in that tab since its last successful save, even though the two tabs were never actually editing the same data. This isn't a rare race; it is the guaranteed, designed outcome of having two tabs open at all.

4. **[Corrected — Codex round 1: default-config blast radius is actually the full database, not just the named character; see section 5's correction on `enableRemoteSaving`.] Self-hosted Node server, two browsers/devices pointed at one server, simultaneous edits.** Two family members (or one user on two devices) both have the self-hosted server URL configured and both have the same character's chat open. Both send a message within the same autosave window. Both browsers' `saveDb()` loops independently `POST /api/write` the same `remotes/<chaId>.local.bin` key (character content) and the shared `database.bin` (root). `server.cjs`'s `/api/write` handler does a bare `fs.writeFile` with no lock or version check (section 3), so whichever POST's write syscall lands last wins outright; the other device's message is gone from that character's chat log with no error surfaced to either user (both requests return `{success:true}` — the server doesn't know it just clobbered a very recent write).

5. **BroadcastChannel silently unsupported — cross-tab last-write-wins with zero warning.** A user on a browser/profile/extension configuration where `window.BroadcastChannel` is falsy (e.g., certain hardened-privacy browser modes or configurations that disable it) opens two tabs. Neither tab ever posts nor listens for anything (`if (window.BroadcastChannel)` guard, `globalApi.svelte.ts:384-387`, and the corresponding `if (channel)` checks are simply skipped). The two tabs behave exactly like two independent devices against the same LocalForage/account-sync backend: pure last-write-wins, with **no reload prompt at all** — the user doesn't even get RisuAI's own (admittedly blunt) safety net, and has no indication anything was lost.

## 7. Other concurrency-adjacent bugs/observations noticed in passing

- **`syncDrive()` is not a sync.** `src/ts/drive/drive.ts:112-115`, called unconditionally at the top of every `saveDb()` run, just clones the current DB into an in-memory module variable (`BackupDb`) that is never read back anywhere obviously tied to conflict recovery in the code paths reviewed, and is lost on reload. The name strongly implies it participates in the Google Drive backup/sync feature; it doesn't touch Drive at all. This is a naming/readability trap more than a functional bug, but worth a second look — it's exactly the kind of thing that could mislead a future contributor into thinking there's a recovery mechanism here when there isn't.
- **No conflict/4xx handling for the hub's possible conflict signaling in `accountStorage.ts`.** As noted in section 2, `setItem`'s status handling only special-cases `403` (auth) and `304`; any `409`/`412`/`428`-style "you're stale" response the hub might send would fall into the generic `throw await getDaText()` error path (line 93-95), which the outer `saveDb()` catch block treats as a generic retryable save failure (`savetrys += 1`, retry after 1s, `globalApi.svelte.ts:601-616`) — i.e. even if the server *does* try to reject a stale write, the client would just blindly retry the same stale write up to `savetrys > 4` before finally surfacing a raw error toast to the user, not a merge/reload prompt. This would make server-side rejection nearly useless in practice unless the client is also changed to re-fetch-then-retry.
- **`x-risu-session`/`risuSession` is cached indefinitely per tab, never refreshed after the first fetch** (`accountStorage.ts:39-46`, only fetched `if(risuSession === '')`). If the hub's session-based conflict detection (if any) is tied to session freshness/expiry, a long-lived tab could be operating on a stale session identifier for its entire lifetime, which — depending on unknown server logic — could either cause spurious `reloadSession` kicks or, worse, cause the server to *not* recognize genuinely-new concurrent sessions from the same tab correctly. Unverifiable without the hub's source.
- **303 "cache mismatch" read path returns `null` on `match:false`** (`accountStorage.ts:126-135`) — if any caller treats a `null` database read as "brand new/empty database" rather than "go fetch fresh," that would be a separate, serious data-loss bug (silently nuking a user's view of their own data), but tracing every caller of `AccountStorage.getItem('database/database.bin')` was outside this investigation's scope; flagging for a follow-up look rather than asserting a bug.
- **Tauri desktop has no protection at all against two OS-level process instances.** `BroadcastChannel` in Tauri's webview is scoped to that webview's browsing context; if a user runs two separate instances of the Tauri app (two OS processes — accidentally double-launching, or running both a portable build and an installed build against the same AppData profile), there is no shared JS realm for `BroadcastChannel` to bridge them, `syncDrive`'s in-memory `BackupDb` is per-process, and the write path (`writeFile('database/database.bin', ...)`) has no OS-level file lock. This reduces to the same last-write-wins situation as two separate devices, but for a scenario (two windows/instances of the same desktop app) a user might reasonably assume is "the same app, so it must coordinate."

## Design options for a fix (sketched, not implemented)

1. **Revision/ETag-based optimistic concurrency.** Add a monotonically increasing revision number (or content hash) to `database.bin` (and, if granular, to each block/character file). Every writer reads the current revision before saving, includes it in the write request (`If-Match`-style), and the storage layer (Node server, hub) rejects the write with a real conflict status if the revision has moved since the read. Client then needs to fetch-merge-retry or prompt the user. *Tradeoffs*: clean, well-understood pattern; requires changes on all three backends (Node server needs a real conflict check instead of blind `fs.writeFile`; hub is out of this repo's control unless Risu's team also changes it); still needs a merge or user-facing conflict UI on rejection, which is nontrivial given the monolithic blob format (see option 3).

2. **Per-chat/per-character granular sync with independent revisions.** Extend the existing `remote: 'prefer'` per-character file mechanism (currently Tauri/Node-server only) to account-sync too, and push it one level further to per-chat granularity, each with its own revision/ETag. This shrinks blast radius dramatically (a stale write to Character A's chat can no longer clobber a concurrent edit to Character B, or even a different chat within the same character), and pairs naturally with option 1's optimistic concurrency applied per-block instead of per-database. *Tradeoffs*: substantially more storage calls (already a concern the code hints at, e.g. Node-server rate limiting elsewhere in this codebase per the round-2 investigation reports); more moving parts in the encode/decode format; still doesn't solve true concurrent edits to the *same* chat.
3. **CRDT-ish or operation-log merge for chat content.** Instead of shipping a full serialized snapshot every autosave, ship an append-only log of chat operations (new message, edit, delete) keyed by chat+timestamp+device, and merge logs from multiple devices instead of overwriting whole-database blobs. This is the only option that could recover from a *true* same-chat concurrent edit without data loss (e.g. two devices both appending a new message to the same chat within the same window would both end up preserved, just interleaved/ordered by timestamp) rather than merely detecting and refusing/prompting on it. *Tradeoffs*: the largest engineering lift by far — touches the save format, the encoder/decoder, and likely the chat data model itself; ordering/idempotency edge cases (out-of-order delivery, clock skew across devices) need careful design; probably overkill unless true concurrent same-chat editing (not just "two devices with the app open") is a real target use case.
4. **Hard single-writer lock with explicit takeover UI.** Formalize what the BroadcastChannel mechanism already informally does for same-browser tabs, and extend it to a real cross-device lock: a backend-held "lease" (e.g., a TTL'd row per account/server saying "device X holds the write lock until timestamp Y"), acquired before a device is allowed to save, renewed periodically, and explicitly surfaced in the UI ("Your other device is currently editing — [Take over] / [View read-only]") instead of the current blunt discard-and-reload. *Tradeoffs*: much better UX than silent overwrite or a forced reload that eats unsaved edits; still fundamentally "only one writer at a time" (no true concurrent editing), but that may be an entirely acceptable product tradeoff for a single-user chat app where genuinely simultaneous multi-device editing of the very same chat is rare; requires a persistent lock store on every backend (straightforward for the hub and Node server, awkward for pure client-side LocalForage-only usage which has no server to hold the lease at all — same-browser BroadcastChannel would remain the only option there).
