## Executive Summary

- **Current shipped targets** are Windows x64 (NSIS), macOS (Intel + Apple Silicon, DMG/APP), and Linux x64 (deb/rpm/AppImage). Confirmed in `src-tauri/tauri.conf.json:20` and `.github/workflows/github-actions-builder.yml:14-29`. macOS ARM (`aarch64-apple-darwin`) is **already** built today — RisuAI is not ARM-naive, just ARM-naive specifically on Linux/Windows/Android.
- **ARM Linux** (`aarch64-unknown-linux-gnu`) is low-to-medium effort: mostly a CI/build-matrix problem plus one native Rust dependency (`tiktoken-rs`, which wraps a Rust BPE implementation — no C extension — so it should cross-compile cleanly) and the bundled Python/llama-cpp-python sidecar, which today only ships a Windows embeddable interpreter anyway (see below), so it's a non-issue for the Tauri app itself on Linux ARM.
- **Windows on ARM** (`aarch64-pc-windows-msvc`) is low-to-medium effort at the Tauri/Rust layer, but is complicated by the **Python sidecar** feature (`install_python` in `src-tauri/src/main.rs:230-246`), which is hardcoded to fetch only the `amd64` CPython embeddable build. **[corrected]** The original claim that Windows ARM hits the `else` branch and returns `false` is wrong: `install_python` branches on `std::env::consts::OS`, which reports `"windows"` regardless of CPU architecture — so an ARM64 Windows build *does* enter the Windows branch and downloads the pinned amd64 interpreter, not dead code. Whether that amd64 interpreter (and `llama-cpp-python`'s native extension inside it) then actually works under Windows' x64-emulation layer on ARM64 is unverified either way — that part of the original uncertainty stands, just for a different reason than originally stated.
- **Android** (`aarch64-linux-android` and friends) is **not started** at the Tauri layer: `src-tauri/gen/` contains only `schemas/` (no `android/` subfolder), meaning `tauri android init` has never been run in this repo (confirmed by directory listing). A **prior, now-abandoned Android attempt existed** — via Capacitor, not Tauri — and was fully removed except for orphaned assets and a config file (see below). **Per explicit project-owner constraint, Android support must NOT be scoped as a standalone "just add the target" item** — it is gated behind the RAM/performance rework identified in a separate investigation (the current architecture is described to hold the entire save database as one large in-memory reactive object with no virtual scrolling, which will OOM on low-RAM Android devices if cross-compiled as-is). This report treats Android purely as groundwork/sequencing, not as an actionable near-term task.
- The Android icon/resource claim from the project owner is **confirmed, but more nuanced than "one misplaced folder."** There are two independent, unrelated sets of Android-shaped assets in the repo (detailed below): one is an orphaned leftover from a 2024 Capacitor-based Android prototype that has nothing to do with Tauri's pipeline, and the other is a correctly-generated, Tauri-convention set that is already sitting in the right place, just unused because `tauri android init` was never run.
- The biggest concrete blocker for **any** target that isn't already built (and a moderate complication even for the ones that are) is the **`src-python` sidecar**: it bundles/expects `llama-cpp-python`, a package with compiled native (and optionally CUDA/Metal) extensions, invoked via a hand-downloaded, Windows-only embeddable CPython interpreter. This is Windows-only today, has no Linux/macOS/Android install path, and `llama-cpp-python` itself has no official Android wheels — this is a hard blocker for shipping local-LLM support on Android and a real complication for ARM Linux/Windows-ARM parity.

## The `mainx.txt` Finding

`src-tauri/src/mainx.txt` (5 lines) contains:
```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]

fn main() {
    alib::run();
}
```
This is **not** currently compiled — it has a `.txt` extension, not `.rs`, so `rustc`/Cargo ignores it, and it is not referenced by `src-tauri/Cargo.toml`'s `[[bin]]`/`[lib]` sections (the `[lib]` block in `Cargo.toml:44-46` that would define a crate named `alib` is commented out, confirmed at `src-tauri/Cargo.toml:44-46`).

What it actually is: this is boilerplate from Tauri's **mobile-compatible project template**. Tauri 2 projects that support Android/iOS need a `src-tauri/src/lib.rs` exposing a public `run()` function (compiled as a `cdylib`/`staticlib` so the Android/iOS native shell can call into it), with a thin `main.rs` that just calls `<crate>::run()` for the desktop binary entry point. `mainx.txt`'s content (`alib::run()`) matches that pattern exactly, and the commented-out `[lib]` section in `Cargo.toml` (`name = "alib"`, `crate-type = ["staticlib", "cdylib", "rlib", "lib"]`) is the matching disabled library target.

**[corrected]** What the repository actually establishes, confirmed via `git log`/`git blame`: `mainx.txt` and the commented-out `[lib]` block in `Cargo.toml` were introduced *together* in the same commit (`5a931d4`, "Migrate to Tauri V2"). Its content is a byte-for-byte match for Tauri's mobile-compatible project template shape (a `lib.rs`-exposed `run()` called from a thin `main.rs`), and it is inert today — has zero effect on any current build, confirmed above. Beyond that, the original draft's narrative — that it was "renamed from `main.rs`," reflects an "incomplete attempt to prepare this project for Tauri mobile," or is "mostly-ready" as a starting point — is inference, not something established by the repository's history or content. There is no `lib.rs` in the repo today, and re-enabling this scaffold would require writing one and reconciling it with the current (substantial) `main.rs`, so "mostly-ready" overstates how close this is to usable. The safe, established conclusion: this is the mobile-template file/Cargo shape from the Tauri V2 migration, currently inert, with unknown further intent behind it.

## The `src-python` Component

Files: `src-tauri/src-python/main.py` (126 lines — corrected from an original miscount of 125), `src-tauri/src-python/run.py` (8 lines), `src-tauri/src-python/requirements.txt` (4 lines — corrected from an original miscount of 3: `pydantic`, `llama-cpp-python`, `uvicorn[standard]`, `fastapi`).

**What it does:** it's a local FastAPI/uvicorn HTTP server (`src-tauri/src-python/main.py:13`) that exposes two endpoints — `/llamacpp` (streaming completion, `main.py:106-110`) and `/llamacpp/tokenize` (`main.py:117-126`) — backed by `llama_cpp.Llama` (the `llama-cpp-python` bindings for llama.cpp), i.e. it's RisuAI's **local/offline GGUF model inference backend**, reachable from the frontend as a local HTTP API secured by a random UUID key written to `key.txt` next to the Python executable (`main.py:14-21`).

**How it's invoked — not PyO3 embedding, not a prebuilt sidecar binary. It's "app self-installs its own Python distribution at runtime, then shells out to it":**
- `src-tauri/tauri.conf.json:17-19`: `"resources": ["src-python/*"]` bundles the raw `.py` source files into the Tauri app's resource directory (via `BaseDirectory::Resource`, `src-tauri/src/main.rs:411`), but ships **no interpreter and no dependencies** with the app package.
- `install_python` (`src-tauri/src/main.rs:230-246`) downloads a CPython embeddable zip on demand from `python.org`, but is **hardcoded to a single Windows amd64 URL**: `"https://www.python.org/ftp/python/3.11.7/python-3.11.7-embed-amd64.zip"` (`main.rs:242`). The function's `if os == "windows" { ... } else { println!("OS not supported"); return false; }` branch (`main.rs:241-246`) means this feature is **already Windows-only** — it returns `false` on macOS and Linux today, x64 or ARM. Dead/unreachable branches for `"linux"` and `"macos"` exist later in the same function's *extraction* logic (`main.rs:264-269`, using `tar`/`zip` respectively) but are unreachable because the `os == "windows"` check above already returns early for every non-Windows OS before a `url` is ever set for them — this looks like an incomplete port, not working cross-platform support. **[corrected]** Calling this behavior a "silent no-op" overstates how gracefully it degrades: the frontend caller (`src/ts/process/models/local.ts:22-54`) does not check `install_python`'s returned boolean and proceeds anyway into `install_pip`, `install_py_dependencies`, and `run_py_server` — steps that assume the Windows-specific files `install_python` would have produced and that contain `unwrap`/`expect` calls internally. The observable behavior on Linux/macOS is therefore closer to a rejected promise or a panic somewhere downstream than a clean, silent no-op.
- `install_pip` (`main.rs:296-326`) and `install_py_dependencies` (`main.rs:381-404`) hardcode `python.exe` (`main.rs:299`, `main.rs:385`) — Windows path convention only, would need `python`/`python3` handling for POSIX targets even if the download step were fixed.
- `run_py_server` (`main.rs:406-430`) also hardcodes `python.exe` (`main.rs:408`) and spawns `python -m uvicorn --port 10026 main:app` as a child process.
- Separately, `check_requirements_local` (`main.rs:330-365`) probes for a **system-installed** `python`/`git` on PATH — an alternate, not-fully-wired "bring your own Python" path that isn't OS-gated the same way, but nothing in the reviewed code calls it as part of the automated install flow shown here.

**Cross-arch/cross-platform implications — this is the single biggest blocker for Android and a real complication for the new desktop ARM targets:**
1. `llama-cpp-python` is a Python package with **compiled native extensions** (a C/C++ llama.cpp core built per-platform-per-arch, optionally with CUDA/Metal/Vulkan acceleration). It has no official prebuilt wheels for Android at all — Android isn't a supported `pip install` target for this package. Getting local GGUF inference working on Android would require either compiling `llama-cpp-python` for `aarch64-linux-android` from source against Android NDK (nontrivial, not something `pip install` will do inside a Termux-less embedded Android runtime) or dropping this feature on Android entirely.
2. Even setting Android aside, the *installer* code path (`install_python`) that fetches the interpreter only knows how to fetch a Windows x64 interpreter. It has never been extended to Linux/macOS at all (let alone ARM variants) — so this isn't "will ARM Linux/Windows-ARM cross-compile," it's "the feature that downloads Python doesn't work on Linux/macOS/any-ARM today, full stop," independent of the platform-expansion effort. **[corrected]** Per the correction above, this is worse than "non-functional" in the sense of a clean no-op — the frontend proceeds past the failed install into steps that assume Windows-specific files and contain `unwrap`/`expect` calls, so the actual observable behavior on Linux/macOS/any-ARM is closer to an error/rejection or a panic than a silent absence of the feature. Fixing this (extending the OS branch to Linux/macOS, and having the frontend actually respect a failed install) is a prerequisite that is orthogonal to, but should probably be bundled with, ARM enablement.
3. Windows on ARM specifically: CPython does publish official win-arm64 embeddable builds as of relatively recent 3.11.x/3.12.x releases, but `install_python`'s URL is pinned to `python-3.11.7-embed-amd64.zip` (`main.rs:242`) with no `arch` branching at all — this would need an explicit `win-arm64` branch added, or reliance on Windows' x64 emulation layer for ARM64 devices (unverified whether the emulated x64 CPython + llama-cpp-python native extension would even run correctly under emulation; not tested as part of this investigation).
4. `src-tauri/Cargo.toml:22-23` (`zip = "0.6.6"`, `tar = "0.4.40"`) are pure-Rust crates used to extract the downloaded interpreter — these are not themselves cross-compilation blockers.

## Per-Target Feasibility Assessment

### ARM Linux (`aarch64-unknown-linux-gnu`)
- **Feasibility: Medium-low effort, no fundamental blockers found.**
- Rust deps in `src-tauri/Cargo.toml` are almost entirely pure-Rust or have good cross-platform track records: `tiktoken-rs` (pure Rust BPE, no native codec dependency beyond what cargo handles), `reqwest`, `base64`, `serde_json`, `zip`, `tar`, `eventsource-client`, `futures`, `url`, `uuid`, `oauth2`, `tokio` — none are architecture-gated in the file (only `target."cfg(any(target_os = \"macos\", windows, target_os = \"linux\"))"` gates `tauri-plugin-deep-link` at `Cargo.toml:36-37`, which explicitly *includes* Linux regardless of arch, and `target.'cfg(not(any(target_os = "android", target_os = "ios")))'` at `Cargo.toml:48-49` gates `tauri-plugin-single-instance`/`tauri-plugin-updater` to desktop OSes generically, not by arch).
- The `src-python` sidecar's Windows-only `install_python` gap (see above) means "local LLM via bundled Python" would not work on Linux **at all today, x64 included** — so this is a pre-existing feature gap, not something ARM enablement introduces or worsens.
- CI work needed: add an `aarch64-unknown-linux-gnu` entry to the matrix in `.github/workflows/github-actions-builder.yml:14-29`, either via a native `ubuntu-24.04-arm` GitHub-hosted runner (available as of 2024) or cross-compilation with `cross`/QEMU — note the repo already has working QEMU/buildx-based ARM64 CI experience in `.github/workflows/docker-build.yml:49`, which can be used as a template/precedent.
- The `deb`/`rpm`/`appimage` bundle targets in `tauri.conf.json:20` all support arm64 packaging in Tauri 2 without config changes beyond the build target triple.

### Windows on ARM (`aarch64-pc-windows-msvc`)
- **Feasibility: Medium effort.** Rust/Tauri side is comparable to ARM Linux — no arch-specific `cfg` gates found blocking it in `Cargo.toml`. `tauri-plugin-single-instance`, `tauri-plugin-updater`, `tauri-plugin-deep-link` all apply to Windows generically, not x64-specifically (`Cargo.toml:36-37`, `48-49`).
- Two concrete gaps to close, both in `src-tauri/src/main.rs`:
  1. `install_python`'s hardcoded amd64-only download URL (`main.rs:242`) needs an `arch`-aware branch for `win-arm64` (CPython does publish official win-arm64 embeddable zips for recent 3.11/3.12 releases — needs verification of exact URL availability for whatever version is pinned).
  2. `llama-cpp-python`'s prebuilt-wheel availability for win-arm64 needs verification (unverified in this investigation) — if unavailable, local LLM inference again silently degrades on this target, same pattern as ARM Linux/macOS today.
- The `nsis` bundle target (`tauri.conf.json:20`) supports building an ARM64 NSIS installer in Tauri 2 via the target triple; no `tauri.conf.json` changes are needed beyond adding the CI matrix entry once a `windows-11-arm` (or cross-compiled) runner is available.
- CI: add a `windows-11-arm`-class runner (GitHub added ARM64 Windows hosted runners) or cross-compile from `windows-latest` with `--target aarch64-pc-windows-msvc`, to `.github/workflows/github-actions-builder.yml:14-29`.

### Android (`aarch64-linux-android` and friends)
- **Feasibility: Not started; substantial effort; explicitly gated (see next section) — do not scope as a near-term standalone task.**
- Groundwork present but incomplete/inert: the `mainx.txt`/commented-out `[lib]` scaffold (see above) is a head start but not wired up; the Tauri-convention `src-tauri/icons/android/mipmap-*` staged icons (Set 2 above) are ready to be picked up by `tauri android init`; nothing under `src-tauri/gen/android` exists yet.
- `tauri-plugin-single-instance` and `tauri-plugin-updater` are explicitly excluded on Android/iOS already (`Cargo.toml:48`: `cfg(not(any(target_os = "android", target_os = "ios")))`) — i.e. whoever last touched `Cargo.toml` was already aware these two plugins are desktop-only and pre-emptively gated them out, which is a small positive sign of forward-looking design, but also means these features (single-instance enforcement, in-app auto-update) will simply be absent on Android and need an intentional decision (skip, or replace with Play Store update flow) rather than silently missing.
- `tauri-plugin-deep-link`'s cfg gate (`Cargo.toml:36`) is `cfg(any(target_os = "macos", windows, target_os = "linux"))` — this **excludes Android explicitly** (and iOS). The `deep-link` plugin config in `tauri.conf.json:44-48` (custom scheme `risuailocal`, used for OAuth-style flows per `oauth_login` in `main.rs:126-184`) would need Android's own deep-link/App Links mechanism wired up separately — Tauri 2's `tauri-plugin-deep-link` does support Android, but this repo has not enabled it for that target.
- `src-python`/`llama-cpp-python` (see above): no realistic path to local on-device GGUF inference on Android without a from-source NDK cross-compile of `llama-cpp-python`, which is a substantial, separate engineering effort; more realistically this feature would need to be disabled/hidden on Android rather than ported.
- Capabilities (`src-tauri/capabilities/desktop.json:3-7`) declare `"platforms": ["macOS", "windows", "linux"]` explicitly — an Android/mobile capability file does not exist and would need to be authored (Tauri 2 supports per-platform capability files; this is additive work, not a blocker, but confirms zero mobile capability config exists today).
- Existing frontend mobile-awareness is a positive signal for *UI* readiness independent of the Tauri layer: `src/lib/Mobile/` already contains `MobileBody.svelte`, `MobileCharacters.svelte`, `MobileFooter.svelte`, `MobileHeader.svelte`, and `src/ts/storage/` already has platform-specific storage adapters including behavior documented in `AGENTS.md:174` ("Tauri FS, LocalForage, Mobile, Node, OPFS") — the app already has a notion of a "Mobile" storage/UI mode, likely built for responsive/narrow-viewport desktop use or the earlier Capacitor attempt, which is reusable groundwork but has not been verified in this investigation to be Tauri-Android-ready as-is.

## Sequencing Constraint: Android Is Gated Behind RAM/Performance Fixes

Per explicit instruction from the project owner for this investigation: **do not recommend "just add Android support" as a standalone, immediately-actionable item.** A separate investigation found the current implementation is RAM-heavy — no virtual scrolling, and the entire save database appears to live in one large reactive in-memory state object — and naively cross-compiling that as-is to Android would cause OOM crashes on low-RAM Android devices. This report treats Android strictly as a **later-phase target**, sequenced strictly *after* that RAM/performance rework lands, not as a parallel or independent workstream. Everything under "Android" above (icon staging, plugin cfg gates, mobile UI groundwork, `mainx.txt` scaffold) should be read as "useful context for a future phase," not as a punch list to start now.

## Recommendations (ranked by impact × effort)

1. **(High impact, low effort) Clean up the orphaned Capacitor-era assets.** Delete `resources/icon-background.png`, `resources/icon-foreground.png`, `resources/icon-only.png`, `resources/splash.png`, `resources/splash-dark.png`, and `capacitor.config.ts` at the repo root — or, if the art is still wanted as source material for a future `tauri icon` regeneration, move it into a clearly-labeled `design/` or `src-tauri/icons/source/` location with a comment/README noting it predates the current Tauri icon pipeline. As-is, it is confusing dead weight that could cause a future contributor (human or AI) to waste time investigating whether it's load-bearing. This is the direct fix for the "misplaced Android icon" claim's actionable half.
2. **(High impact, low effort) Fix `install_python`'s OS/arch gating in `src-tauri/src/main.rs:230-246`.** Today it is silently non-functional on every non-Windows-x64 target. Add explicit URL branches for Linux x64/arm64, macOS (universal/arm64), and Windows arm64 (verify CPython's official embeddable-zip availability per target first), and replace the hardcoded `python.exe` paths in `install_pip`/`install_py_dependencies`/`run_py_server` (`main.rs:299`, `385`, `408`) with an OS-conditional `python3`/`python.exe` selection. This unblocks local-LLM support parity across every desktop target this report was asked to evaluate, independent of new-arch work.
3. **(Medium impact, low effort) Add `aarch64-unknown-linux-gnu` to the CI build matrix** in `.github/workflows/github-actions-builder.yml`, using a GitHub-hosted `ubuntu-24.04-arm`-class runner (avoids cross-compile complexity) or reusing the QEMU/buildx pattern already proven in `.github/workflows/docker-build.yml:49`. No `tauri.conf.json` or Cargo.toml changes appear necessary given the current dependency set.
