# Remote-Block Versioning Design Feasibility

**STATUS:** reference

Scope note: this report does not re-litigate whether the reverted Stage 3 gap is real — it was independently confirmed by Codex adversarial-review (`Agents/CodexReviews/tierb-stage2-4/tierb-stage2-4-round1.codexreview.md`) and by this investigation's own direct reading of `src/ts/storage/risuSave.ts`. It sizes what a proper fix — "publish remote blocks under unique/versioned names, then atomically/conditionally commit the root referencing the exact version, garbage-collect unreferenced versions later" — would actually require in this codebase, so that a future Stage 3 retry (per `Agents/Roadmap.md`, Phase 1.5 Tier B item 5) can be scoped correctly before implementation starts. **No code was changed by this investigation.**

**[Corrected after Codex adversarial-review — see `Agents/CodexReviews/topic07/07-remote-block-versioning-design.codexreview.md`.]** The review found three issues, all now corrected inline below: (1) the original draft's garbage-collection design ("delete immediately once a version isn't referenced by the current root, no grace period needed") has a real race — a concurrent boot-time GC sweep can observe an old root and delete a just-published, not-yet-referenced new block in the window between a writer publishing it and that writer's root write committing; if the root write then succeeds, it references a payload that no longer exists. The existing GC's 7-day meta/`lastUsed` grace period exists for a reason and must be kept, not dropped, for versioned remote blocks too — corrected in the "Garbage collection" section. (2) The original draft characterized the GC-side version-awareness update as "a small addition to the existing `cleanChunks()` loops" (parse the version out of each `remotes/*` filename, compare against the current root's pointer). This understates the actual plumbing needed: `cleanChunks()` operates on `getDatabase()`, whose characters have already been fully materialized by `RisuSaveDecoder` — the decoder's `REMOTE` case reads the external file and folds the decoded character into the database, but does not preserve or expose the pointer's version/hash anywhere the decoded `Database` object can be inspected afterward, and the root's own `__directory` lists block *names*, not remote filenames or versions. Determining "which version does the current root actually reference" therefore needs new decoder-to-GC plumbing (new metadata exposed by `RisuSaveDecoder`, or a second, GC-specific parse of the raw `database.bin` bytes), not just a filename-parsing loop — corrected in the "Garbage collection" section. (3) The original draft stated as **confirmed** that `accountStorage.ts` proves the account-sync hub has "no coordination primitive of any kind" and that a revision-counter scheme is "permanently infeasible" there. This overstates what was actually verified: `accountStorage.ts` proves only that *this client's* visible contract exposes no version-minting operation — the file also sends session/save-date headers, handles `304` responses, and reacts to a server-directed `reloadSession` signal, none of which rules out the hub having *some* internal versioning concept this client simply never asks for. The hub's actual implementation remains absent from this repo and its conflict semantics remain genuinely unverifiable (same standing limitation Report 06 already established) — corrected throughout to the narrower, actually-supported claim: no version-minting operation is exposed by the repository-visible account-sync client contract, so absent a documented hub capability or a hub-side change (neither obtainable, see `Agents/Summary.md` §5), Option B cannot be implemented from this repository, while Option A requires no hub cooperation at all either way. This narrowing does not change the report's recommendation (Option A remains correct regardless of what the hub's internals actually are), only the strength of the claim about *why* Option B is ruled out.

**[Corrected after Codex adversarial-review, round 2 — see `Agents/CodexReviews/topic07/07-remote-block-versioning-design-round2.codexreview.md`.]** Round 2 found the round-1 corrections were incomplete or, in the GC case, insufficient. Four further issues, all now corrected inline below: (4) the round-1 grace-period fix does not actually close the original race in the case where a content-addressed key gets *reused* — if a root commit fails after a block was published, that block can sit orphaned (no root references it) until a boot-time GC sweep creates a `.meta` file for it and, eventually, marks it expired past the grace window; if a *later* save happens to produce byte-identical content for the same character (a real possibility given content-addressing's whole point is that identical content maps to the identical filename), that later write is treated as an idempotent no-op against the *existing* file — but nothing in the original design refreshed that file's now-stale, already-expired meta timestamp as part of republishing it, so a GC sweep racing against that second writer's not-yet-committed root could still delete the file it just "republished," between publish and commit. Corrected in the "Garbage collection" section: publishing (or re-publishing) a remote block must refresh/create its GC liveness timestamp as part of the publish step itself, before the root commit — not rely on GC's own lazy, scan-time meta creation, which is exactly the gap that let a stale expired timestamp survive a legitimate republish. (5) The report significantly understated a genuine blocker for account-sync GC: `AccountStorage.keys()` (`accountStorage.ts:181-184`) returns `getUncleanablesSync(db, 'pure')` — a computed list derived from the *in-memory decoded database*, not a real listing of what keys actually exist in hub storage — and `AccountStorage.removeItem()` (`accountStorage.ts:185-187`) unconditionally throws. This repository's account-sync client code has **no way to enumerate arbitrary stored keys on the hub, and no way to delete any key at all**, which means the "small dedicated remotes sweep" and "GC carve-out" language used throughout the original draft was not achievable as described — there is no client-side capability to build a sweep out of. Corrected in the "Garbage collection" section, the per-backend table, the incremental adoption path (Stage 3b/3c), and the "product decision" closing section: account-sync GC (and therefore safely extending remote-block eligibility to account-sync at all) is now flagged as blocked on a real capability gap, not merely "needs a small carve-out." (6) Several absolute claims about the account-sync hub survived the round-1 correction in places other than the Summary — "cannot be modified at all," "is not achievable," "impossible on the hub," "hard-blocked" — restated below, throughout, to the same narrower, actually-supported claim used in the Summary: not implementable *from this repository* given its visible client contract, not a proven fact about the hub's internal capabilities. (7) The closing "product decision" section's GC bullet restated the already-rejected "delete immediately once superseded, no grace period" framing as if it were still the report's live sketch, directly contradicting the corrected "Garbage collection" section — rewritten below to separate the non-negotiable publish-time liveness/grace requirement (a correctness issue, not a product choice) from the genuinely optional product question of retaining more history than the minimum safe window.

**[Corrected after Codex adversarial-review, round 3 — see `Agents/CodexReviews/topic07/07-remote-block-versioning-design-round3.codexreview.md`.]** Round 3 found two further issues: (8) the round-2 "refresh the timestamp before root commit" fix does not actually close the GC race — `cleanChunks()`'s real implementation reads a liveness timestamp, decides to delete, and only later executes that decision with no re-validation in between, so a sweep that read a stale/expired timestamp can still execute an already-made deletion decision after a writer has since republished and refreshed it, and there is a separate, unaddressed ordering gap between a writer publishing a payload and that same writer refreshing its timestamp. ## Summary

**Recommendation: content-addressed naming (`remotes/<chaId>.<sha256-or-similar>.bin`), not a revision-counter scheme, and — the more consequential finding of this pass — the fix requires almost no change to `saveDb()`'s write *ordering* at all.** The existing pipeline already writes remote/leaf blocks before the root block, in the shape the Codex review asked for ("publish blocks first, then commit root") — `RisuSaveEncoder.set()` calls `encodeRemoteBlock()`, which durably writes `remotes/<chaId>.local.bin` via `forageStorage.setItem()`, and only *after* every character's block (and every other dirty block) has been folded into `obj.__directory` does `saveDb()` reach its own write of `database/database.bin` (`globalApi.svelte.ts:748-780`), which is the one write Stage 1/2's revision checking already guards. The bug Codex found is not a missing ordering guarantee — it is that the remote block's filename is **stable and mutable** (`remotes/<chaId>.local.bin`, unconditionally overwritten on every save, no version or hash in the name at all — confirmed by direct read of `encodeRemoteBlock()`, `risuSave.ts:456-500`). Because the filename never changes, a write to it is visible to *every* root that references that character, including a root that was already accepted before this write happened, and including a root a rejected writer's own retry will never get to commit. Making the name unique per-version (content hash, or a per-character monotonic counter) turns each remote-block write into an append of a brand-new, never-again-mutated object; visibility of a version is then controlled entirely by which version the *current, atomically-committed* root's directory pointer names, which is exactly the "publish then atomically reference" shape being asked for — achieved by a naming change plus a small pointer-format bump, not a new transactional/two-phase-commit primitive.

Between the two naming schemes: **content-addressing is the clearly smaller and safer increment.** A monotonic revision-counter scheme (`remotes/<chaId>.<n>.bin`) needs a *revision-issuing authority* that every writer agrees on before it ever contacts the write endpoint — i.e., it needs to literally reuse (or duplicate) Stage 1's `server.cjs` per-key revision store, but in a new mode ("mint me the next version number for key K to author a brand-new immutable file with," not "check whether my known revision for K still matches") that the current `/api/write` handler does not do today. **[Corrected — Codex round 1]** No such minting operation is exposed anywhere in account-sync's client-visible contract either (`accountStorage.ts` sends an arbitrary `key` header plus session/save-date headers and reacts to `304`/`reloadSession`, but nothing resembling "give me the next version number"), so Option B cannot be implemented from this repository as things stand — but this is a claim about what the *client* exposes and what this repo can build, not a proven fact about the hub's internals, which remain unverifiable (same limitation Report 06 already established; the hub's own implementation is absent from this repo). Content-addressing needs **zero server cooperation on any backend**: the hash is computed entirely client-side before the write, is naturally immutable (the content IS the version), and naturally deduplicates (two writers who happen to save byte-identical character state produce the same filename and the second write is a no-op). This makes content-addressing the only one of the two schemes that is verifiably implementable across Tauri, Node-server, *and* account-sync with the same code path, without depending on any assumption about hub internals — which matters a lot here, since the entire reason Stage 3 exists is to extend this mechanism's eligibility to account-sync.

Also verified and worth stating plainly, since the task description's framing of it turned out to be only half right on direct inspection: **the boot-time `remotes/` garbage-collection path (`src/ts/bootstrap.ts`'s `cleanChunks()`) is not Tauri-only.** It has a real, working non-Tauri branch (`bootstrap.ts:635-679`) that already walks `forageStorage.keys()` and applies the same meta-file/last-used eviction logic to `remotes/*` entries for any non-Tauri backend whose keys route through `forageStorage` — which includes the Node server today. What actually excludes a backend is a single early return at the top of `cleanChunks()` (`bootstrap.ts:559`, `if (db.account?.useSync || forageStorage.isAccount) { return }`), which skips the *entire* function — asset GC and remote-block GC together — for account-sync specifically, not for "everywhere but Tauri." **[Corrected — Codex round 1]** This means a *bare-name*, un-versioned remote block is already GC-eligible for Tauri/Node-server today — but making GC *version-aware* (know which of possibly several versions of a character's remote block is the one the current root actually references, and safely retain the rest for a grace period rather than deleting them the moment a newer version exists) needs real new plumbing on every backend, not just account-sync — see the "Garbage collection" section below for the corrected scope.

## Background actually verified in this pass

- `RisuSaveEncoder.encodeRemoteBlock()` (`risuSave.ts:456-500`): writes `arg.data`'s encoded bytes to `remotes/${arg.name}.local.bin` — `arg.name` is always the bare `chaId`, confirmed by both call sites in `init()` (`risuSave.ts:228-238`) and `set()` (`risuSave.ts:262-286`), both of which pass `name: character.chaId` and option `{ remote: 'prefer' }`. No hash, revision, or timestamp appears anywhere in the filename. It then returns a small pointer block of type `RisuSaveType.REMOTE` whose payload is `JSON.stringify({ v: 1, type: arg.type, name: arg.name })` — `name` here is again the bare chaId, not a specific version identifier.
- `RisuSaveDecoder`'s `REMOTE` case (`risuSave.ts:686-724`): reconstructs the filename identically, `` `remotes/${remoteInfo.name}.local.bin` ``, and reads whatever is currently there — there is no way today for a decoder to ask for "the version the root I'm currently decoding actually meant," because the pointer never recorded one.
- `encodeBlock()`'s eligibility gate (`risuSave.ts:375-390`): `option.remote === 'prefer' && (isTauri || isNodeServer) && !disableRemoteSaving()`. `disableRemoteSaving()` (`risuSave.ts:24-31`) returns `true` (i.e., disabled) unless `db.enableRemoteSaving` is explicitly `true` — confirmed still opt-in-only by grepping the whole repo for `enableRemoteSaving`: its only writer is the settings checkbox at `src/ts/setting/advancedSettingsData.ts:200` (`id: 'adv.remoteSave', type: 'check', ... bindKey: 'enableRemoteSaving'`), no code path sets a default value anywhere.
- `saveDb()`'s actual write sequence (`globalApi.svelte.ts:748-798`), read start-to-finish: `await encoder.set(db, toSave)` runs first — this is the call that, internally, performs every dirty character's `encodeRemoteBlock()` write (an unconditional `forageStorage.setItem(fileName, encoded)`, `risuSave.ts:487`) as a side effect, entirely before returning. Only after `encoder.set()` has returned does `saveDb()` call `encoder.encode()` (serializes the in-memory block map, including the just-updated `REMOTE` pointer blocks, into one buffer) and then, further down, perform the one write that is actually revision-checked: `await forageStorage.setItem('database/database.bin', dbData)` (`globalApi.svelte.ts:779`), under `dbWriteLock` (an in-process mutex unrelated to cross-writer revision checking — it only prevents this same client's own `loadDrive()` restore from interleaving with its own autosave, per Phase 1 item 4). This confirms the two writes are already sequenced "leaf writes, then root write, then the root write is the one gated" — the missing piece really is naming, not sequencing.
- `AccountStorage.setItem`/`getItem` (`accountStorage.ts:44-224`), read in full: both take an arbitrary string `key` (sent as the `x-risu-key` header on write, and hex-encoded into the URL path plus `x-risu-key` header on read) with no server-side schema constraint visible anywhere in this file — the hub's only documented contract from the client's point of view is "give me any key string, I'll store/return bytes for it," which is exactly what a content-addressed or versioned key-naming scheme needs and nothing more. This confirms the task's framing claim by direct reading, not by assumption.
- `server.cjs`'s Stage 1 revision machinery (confirmed present, read via targeted grep + the surrounding code already documented in `Agents/Roadmap.md`'s Phase 1.5 Tier B Stage 1 entry): a per-file `revisions` map (`__revisions.json`, atomically persisted), a `withFileWriteLock`/`withFileWriteLocks` per-key critical section, and a `withRevisionTransaction` global queue serializing revision bumps. This is a **conditional-write** primitive — "tell me if key K is still at revision R, and if so let me overwrite it and bump R" — not a **version-minting** primitive — "give me a new, guaranteed-unique identifier to name a brand-new file with." The two are different operations even though they'd share the same underlying `revisions` map; reusing this machinery for version-minting would need new server logic, not just a new client header, and an equivalent would separately need to exist for account-sync's hub — which this repository has no way to add, and no visibility into whether something equivalent already exists there.
- `cleanChunks()` (`bootstrap.ts:546-679`), read in full: early-returns for account-sync before either the Tauri or non-Tauri branch runs (line 559); the non-Tauri branch (lines 635-679) already GCs `remotes/*` keys read through `forageStorage.keys()`, using a `.meta` companion file's `lastUsed` timestamp and a 7-day threshold, structurally parallel to (though independently implemented from, not code-shared with) the Tauri branch's `getRemoteSaveCleanupAction()` helper (`src/ts/storage/remoteSaveCleanup.ts`, also used by the Tauri branch at `bootstrap.ts:613`).

## Option A: Content-addressed naming (`remotes/<chaId>.<hash>.bin`)

### File-by-file, what would actually change

- **`src/ts/storage/risuSave.ts`**:
  - `encodeRemoteBlock()` needs to hash `arg.data` (or the already-encoded `encoded` bytes — content used for the write, not the pre-encoding string, so a hash mismatch can never happen from an encoding-step difference) with a fast, already-available digest — `crypto.subtle.digest('SHA-256', ...)` is already used elsewhere in this codebase for asset addressing (Phase 1 item 6's `verifyAssetCacheEntry()` reuses the same "asset is named after its own content hash" convention `saveAsset()` already establishes — this is a pattern this repo already trusts, not a new one), so no new dependency. Truncating to e.g. the first 16 hex chars is plenty for collision safety at this per-user, per-character key-space scale, and keeps filenames short.
  - The write target changes from the always-identical `remotes/${arg.name}.local.bin` to `remotes/${arg.name}.${hash}.bin`. Since the hash is a function of content, writing the *same* character state twice in a row (e.g., an autosave tick with nothing dirty, if that can ever reach this call — worth double-checking against `toSave` dirty-tracking, but harmless even if it does) produces the same filename and the same bytes — an idempotent no-op overwrite, not a new version, which is the dedup property called out in the Summary.
  - The `REMOTE` pointer payload needs a new field to carry the version: `{ v: 2, type: arg.type, name: arg.name, hash: <hex> }`. Bumping the pointer's own `v` field (already present, currently hardcoded to `1` in every existing writer — confirmed, no other value is ever written) is the natural discriminator for the decoder to know which filename-construction rule to use — this is the same "fail-closed on an unrecognized version, and let the existing value keep meaning what it always meant" pattern the block-format's own top-level version byte already uses (`decodeRisuSave`'s `versionByte !== 0 && versionByte !== 1` check, `risuSave.ts:801-804`) — reusing an established convention in this same file, not inventing a new one.
  - `RisuSaveDecoder`'s `REMOTE` case needs a branch: `v === 1` (old pointers, and therefore old already-saved files) keeps reading `remotes/${remoteInfo.name}.local.bin` exactly as today — no migration needed for existing data, since the decode logic for that shape doesn't change at all. `v === 2` reads `remotes/${remoteInfo.name}.${remoteInfo.hash}.bin` instead. Both branches otherwise do the same isTauri/forageStorage existence-check-then-read.
  - This is a real but small change confined to one file: one new field on the pointer payload, one new filename-construction branch in the encoder, one new filename-construction branch in the decoder, gated by a version discriminator the format already has a slot for.

- **`src/ts/globalApi.svelte.ts`**: **no changes needed.** `saveDb()`'s call sequence (`encoder.set()` then `encoder.encode()` then the revision-checked root write) is already exactly the shape this fix needs — see the Summary's ordering finding. The only thing that changes is what happens *inside* `encoder.set()`'s call to `encodeRemoteBlock()`, which `saveDb()` doesn't need to know or care about.

- **`src/ts/storage/nodeStorage.ts` / `accountStorage.ts`**: **no changes needed.** Both already accept arbitrary string keys for `setItem`/`getItem` with no server-side involvement in choosing the key — a content-addressed `remotes/<chaId>.<hash>.bin` key is just another string to either backend, same as today's stable-named key was.

- **`server/node/server.cjs`**: **no changes needed.** The per-key revision store treats every distinct `filePath` as its own independent key already (confirmed: `revisions[filePath]`, keyed by the full hex-encoded path string, no special-casing of `remotes/` anywhere in the file). A new, never-before-seen `remotes/<chaId>.<hash>.bin` key just gets revision `0`→`1` on its first write like any other new key — this is existing, already-shipped, already-9-rounds-reviewed behavior, not new surface.

### Server-side changes needed?

**No, on any backend.** This is the decisive advantage over a revision-counter scheme: the version identifier is computed entirely client-side from content the client already has in hand before it ever talks to a server, so it needs no endpoint, no new header semantics, and no coordination with the account-sync hub — which this repository has no way to add new endpoints or logic to, regardless of what it may already support internally (see the round-2 correction above).

### New persisted state?

Yes, but modest and self-cleaning by construction: each save that touches a character now durably persists one new `remotes/<chaId>.<hash>.bin` object (instead of overwriting the one stable file). Nothing new is needed server-side beyond what already exists (both backends already store arbitrary keyed blobs). The accumulation of old versions is exactly what garbage collection (below) exists to bound.

### New UI?

None. This is entirely an internal storage-format change; no user-visible surface changes shape.

## Option B: Monotonic revision-counter naming (`remotes/<chaId>.<n>.bin`)

### File-by-file, what would actually change

- **`src/ts/storage/risuSave.ts`**: same shape of change as Option A (pointer gets a new field, encoder/decoder get a version-discriminated filename rule) — but the value minted into that field is a monotonically-increasing integer per `chaId`, not a hash. The complication is entirely in *where that integer comes from*, not in the encode/decode mechanics, which are otherwise identical to Option A.
- **Revision authority, Node server**: to avoid two concurrent writers picking the *same* next revision number for *different* content (which would be a genuine collision/overwrite on that one version file — defeating the entire point), something has to hand out revision numbers under mutual exclusion. `server.cjs`'s existing `withFileWriteLock`/`withRevisionTransaction` machinery is the right *shape* of primitive to build this on, but it is not directly reusable as-is: today it implements "read current revision for key K, optionally compare against a client-presented value, write new content for K, bump K's own revision" — all against **one fixed key** (`filePath`) whose content itself is being replaced each time. Minting a version number for a *new, distinct* key (`remotes/<chaId>.<n>.bin`, different key per version) is a different operation: "atomically read-and-increment a per-`chaId` counter, independent of writing any particular file's content." This needs either (a) a new server endpoint (`/api/reserve-revision` or similar) built on the same lock/persistence pattern, or (b) a real reuse trick — e.g., treat a fixed sentinel key like `remotes/<chaId>.counter` as the thing whose *existing* revision-bump-on-write behavior is repurposed as the counter (write an empty/trivial body to it purely to get back the bumped revision number in the response, then use that number to name the real content file) — workable, but a genuine new protocol convention layered on top of Stage 1, not a zero-touch reuse as first framed.
- **Revision authority, account-sync**: **not implementable from this repository.** **[Corrected — Codex round 1]** No revision-counter/version-minting concept is exposed anywhere in `accountStorage.ts`'s client-visible contract (session/save-date headers, `304`/`reloadSession` handling, and an arbitrary `key` header — nothing resembling "mint the next version"), and this repo has no way to add a new coordination endpoint to the hub itself, per the same hard constraint that blocks every other server-enforced idea in Report 06. This rules out Option B *as buildable from this repo*, which is what matters for scoping this fix — but it is not the same as a proven fact about the hub's internal implementation, which remains absent from this repo and genuinely unverifiable either way (same standing caveat as every other account-sync question in Report 06). A monotonic-counter scheme is therefore not implementable from here regardless of what the hub may or may not already do internally.
- **Garbage collection**: needs to know, for a given `chaId`, which revision numbers are safe to delete — same "compare against what the current root actually references" logic as Option A, no material difference here.

### Assessment

Strictly more work than Option A for a capability Option A already provides for free (immutable, dedup-by-construction versioning), and it is the one shape of this fix that is not implementable from this repository for account-sync — which is precisely the backend Stage 3 exists to extend this mechanism to. The only genuine advantage a counter scheme has over content-addressing is human-readable ordering (revision 47 is obviously newer than revision 12; two different hashes carry no inherent ordering) — but nothing in this pipeline actually needs to compare two arbitrary versions' recency directly; the *only* thing that ever needs to know "which version is current" is the root's own pointer, which is authoritative by construction under either scheme (whichever version the current, revision-checked root names, that's the current one — recency between two blocks that are both no longer referenced by any live root is irrelevant, since both are just GC-eligible garbage regardless of which is "newer"). This removes the one advantage a counter scheme would have, so the added server-side minting complexity isn't buying anything a real workflow needs.

## Atomic root-referencing: what actually needs to change (both options)

This section applies identically to A and B once a version identifier exists at all, since the mechanism is the naming scheme, not a new transaction primitive:

- `saveDb()`'s existing call order (`encoder.set()` → `encoder.encode()` → revision-checked write of `database/database.bin`) already *is* "publish leaf blocks, then atomically/conditionally commit the root that references them" — confirmed by direct trace above. No new locking, no new two-phase-commit logic, and no change to `dbWriteLock` (which serves an unrelated purpose — same-client mutual exclusion against its own `loadDrive()` restore, not cross-writer conflict detection) is needed.
- The only genuinely new invariant this relies on, and that's worth stating explicitly as a design requirement rather than assuming: **a remote block's filename must never be reused for different content.** Content-addressing gets this for free (same content ⇒ same hash ⇒ same filename ⇒ writing it again is a true no-op, not a collision). A counter scheme gets it only if the counter-minting step is genuinely exclusive per `chaId` across every writer — which is exactly the new server-side complexity Option B needs and Option A doesn't.
- One real edge case worth flagging for whoever implements this, not resolved by this report: if the root write itself fails for a *non-conflict* reason (e.g., a network/generic I/O error, not a 409) after the remote block(s) were already durably written, `saveDb()`'s existing catch-and-retry path (`globalApi.svelte.ts:807-887`) will re-run `encoder.set()` on the next iteration and re-encode the same (still-dirty, per `mergeUnsavedChanges`) character — under content-addressing this produces the *same* hash and thus the *same* filename as the block already sitting on disk from the failed attempt (harmless idempotent overwrite); under a counter scheme it would mint a *new* number for functionally identical content on every retry, needlessly inflating the version count until GC catches up. This is a second, independent point in content-addressing's favor, surfaced only by actually tracing the retry path rather than assuming a single successful write per save attempt.

## Garbage collection

**[Corrected after Codex adversarial-review, round 1 — the original draft of this section claimed superseded versions could be deleted immediately with no grace period, and characterized the version-awareness update as a small filename-parsing addition. Both claims were wrong; corrected below.]**

- **The immediate-delete design has a real race, and must not be built.** The original draft proposed: once a version isn't referenced by the current root, delete it immediately, no meta file or grace period needed. This is unsafe. A boot-time GC sweep reads *some* snapshot of the current root; a concurrent writer can durably publish a brand-new versioned block (step one of the publish-then-commit sequence this whole design relies on) and then, before its root write actually commits, have that GC sweep observe the *old* root (which doesn't yet reference the new block) and conclude the new block is unreferenced garbage — deleting a payload the writer's about-to-commit root is seconds away from pointing at. If that root write then succeeds, it references a version that no longer exists. The same reasoning applies to retained database backups (Phase 1 item 3's throttled `dbbackup-*.bin` snapshots) if those are ever considered restorable: an older backup's root can still legitimately reference an older version that a "current root only" liveness check would consider garbage. **The existing GC's 7-day meta/`lastUsed` grace period exists precisely to make this kind of race survivable, and versioned remote blocks need the same kind of grace period, not "immediate delete once unreferenced."** Whoever implements this needs to explicitly decide the grace-period length and whether backups count as GC roots (deferred here — the report's job is to flag that the question exists and that "immediate delete" is the wrong default, not to answer it).
  **[Corrected — Codex round 2]** A grace period alone does not fully close this race, and the round-1 correction above was insufficient as stated. The existing GC pattern only *creates* a `.meta`/`lastUsed` timestamp lazily, the first time a scan notices an unreferenced payload with no meta file yet — it does not *refresh* an existing meta file for a payload that's still actively referenced or being actively republished. Under content-addressing, a failed (non-conflict) root commit can leave an orphaned block with a meta file that a later sweep marks expired. If a *subsequent, unrelated* save later happens to produce byte-identical content for that same character — a real possibility, since identical content is exactly what content-addressing is designed to map to the identical filename — `encodeRemoteBlock()`'s idempotent-overwrite behavior would write the *same* key again without necessarily touching that key's now-stale, already-expired meta timestamp, since meta-timestamp maintenance was assumed to be GC's job, not the writer's. A GC sweep racing against that second writer's not-yet-committed root could then delete the file this second writer just "republished," using the stale expired timestamp, before that writer's root commits — reproducing the exact same class of race the grace period was meant to close.
  **[Corrected — Codex round 3: the round-2 fix above is still not sufficient.]** Requiring publish to refresh the liveness timestamp "before the root commit" only fixes the case where GC's *read* of that timestamp happens after the refresh. It does not close the actual TOCTOU: `cleanChunks()`'s existing GC implementations (`bootstrap.ts:601-627`, `656-675`) read a timestamp, *decide* to delete based on that one read, and only *later* actually perform the deletion — with no re-validation in between. So the race has (at least) two independent windows, not one: (a) a sweep can read the *old, expired* timestamp, commit to deleting, and then actually execute that already-made deletion decision *after* a writer has since republished and refreshed it — the refresh happened, but too late to stop a decision GC had already locked in from stale data; and (b) there is no specified ordering between "writer publishes the payload bytes" and "writer refreshes the timestamp" — if GC's sweep (read timestamp → decide → delete) can interleave inside that gap, it can delete the payload after it's published but before its timestamp is refreshed, then the writer's subsequent root commit still succeeds and now points at nothing. A multi-day grace window does not protect against a deletion *decision* that was already authorized from a stale read; it only widens how long a payload must sit unreferenced before that stale read becomes possible, not whether the decision-then-execute gap itself is safe.
  **This is a genuine, unresolved concurrency design problem, and this report is not going to settle it by further prose patching.** It is the same *class* of bug — a decision based on one read, executed later without re-validating against what may have changed in between — that took Tier B Stage 1 nine rounds of dedicated adversarial review and standalone concurrency stress-testing to close correctly for `server.cjs`'s revision store (see `Agents/Roadmap.md`'s Stage 1 entry, round 1's TOCTOU finding specifically). The honest scope of this report is to flag that the same rigor is needed here, not to assert a fix that hasn't actually been verified against concurrent interleavings. Plausible directions for whoever implements this (not verified, not recommended as final — flagged only as starting points for real design work): (i) make GC's *delete* step re-validate liveness (both the current root reference and the liveness timestamp) immediately before executing the deletion, in the same synchronous step as the delete itself, so a decision cannot go stale between being made and being acted on; (ii) serialize publish and GC-deletion per remote-block key, analogous to Stage 1's `withFileWriteLock`, so the two operations can never interleave in a way that produces a lost-update; (iii) a tombstone/soft-delete step with its own grace window before a hard delete, so an in-flight republish has a second chance to cancel a pending deletion. **Whichever direction is chosen, it needs the same treatment Stage 1 got — explicit interleaving analysis, standalone concurrency stress tests, and iterative adversarial review — before Stage 3a is considered safe to ship, not a report-level description assumed correct on first read.** This is now the single largest open risk in this whole design, larger than the naming/pointer-format work itself.
- **Implementation scope is larger than "parse the filename," for both Tauri and Node-server.** The original draft characterized the fix as a small addition to `cleanChunks()`'s existing loops: parse the version out of each `remotes/*` filename, compare against "the current, freshly-decoded root's directory pointer's version." This doesn't actually work as described: `cleanChunks()` operates on `getDatabase()` — a `Database` object whose characters have already been fully materialized by `RisuSaveDecoder`. The decoder's `REMOTE` case (`risuSave.ts:693-731`) reads the external remote-block file and folds the *decoded character* into the database as a side effect, but it does not preserve or expose the pointer's own version/hash field anywhere on the resulting `Database` object — and the root block's own `__directory` field lists block *names*, not remote filenames or their versions. So there is currently no place in the already-decoded, in-memory database that GC could read "which version does the current root actually reference" from. Making this work needs either (a) new decoder-side plumbing — `RisuSaveDecoder` retaining and exposing each `REMOTE` pointer's version/hash alongside (or instead of just folding into) the decoded character, in a form `cleanChunks()` can consume — or (b) a second, GC-specific pass that re-parses the raw `database.bin` bytes independently of the normal decode path just to extract pointer versions. Either way this is real, new, cross-file design work spanning `risuSave.ts` and `bootstrap.ts`, not a same-file filename-parsing loop — this changes the effort sizing for Stage 3a/3b (below) from "small" to "small-medium," and any version-liveness check also needs to handle a live pointer whose payload file is unexpectedly missing without losing the pointer information GC needs. `cleanChunks()`'s Tauri branch (`getRemoteSaveCleanupAction()`, `src/ts/storage/remoteSaveCleanup.ts`) needs the equivalent plumbing, not just the non-Tauri branch.
- **Account-sync: not a small carve-out — a real, currently-unresolved capability gap.** **[Corrected — Codex round 2]** The original draft characterized this as needing only a narrowed `cleanChunks()` early return (`bootstrap.ts:559`, currently blocking the function entirely for account-sync for a reason unrelated to remote blocks — the comment there says the function's *asset*-cache GC and integrity-sampling logic are "meaningless or worse, misleading" against account-sync's different asset-caching model) plus "a small dedicated account-sync remote-block GC path." That framing assumed a sweep-and-delete capability that doesn't actually exist for this backend: `AccountStorage.keys()` (`accountStorage.ts:181-184`) returns `getUncleanablesSync(db, 'pure')` — a list computed from the *in-memory decoded database*, not a real enumeration of what keys actually exist in hub storage — and `AccountStorage.removeItem()` (`accountStorage.ts:185-187`) unconditionally throws (`"Error: You cannot remove data in account. report this to dev if you found this."`). **This repository's account-sync client code has no way to discover arbitrary superseded remote-block keys on the hub, and no way to delete any key at all**, versioned or not. A "carve-out" cannot be built on top of a capability that isn't there. Closing this needs one of: (a) the hub already exposing a listing/delete capability this client simply never calls (unverified and unverifiable from this repo, same standing limitation as every other account-sync question in this and Report 06), (b) obtaining hub cooperation to add one (not achievable, per the confirmed upstream-only constraint), or (c) an explicit product decision to extend remote-block eligibility to account-sync *without* reclamation, accepting unbounded per-character version accumulation on the hub as a known, quantified tradeoff (not sized by this report — would need real usage-pattern estimation before being acceptable). Until one of these is resolved, extending eligibility to account-sync (Stage 3c below) should not proceed. This remains the one piece of this whole feature that doesn't already have a working analog somewhere in the codebase to extend — more than "the one piece needing new work," it is the one piece this report cannot currently size a safe implementation for at all.
- **[Corrected — Codex rounds 1 and 4]** Cost shape: GC does not need to retain or reconstruct *every* prior root's directory — it only ever needs each `remotes/*` file's liveness against the *current* root's directory, plus a `lastUsed`-style timestamp/threshold check, not an unbounded history walk. **This describes the data GC needs to look at, not a sufficient safety protocol.** Per the round-3 correction above, a timestamp/grace check alone does not close the publish-vs-delete race — GC's read-decide-then-later-delete structure can still execute a deletion decision made from stale data after a legitimate republish. "One comparison plus one timestamp check" is accurate as a description of GC's *data requirements*; it is not a complete or sufficient description of what GC must *do* to be safe, which additionally needs the unresolved concurrency protocol described above before this can be considered a finished design.

## Migration

Genuinely low-friction, confirmed by the decoder-side design in both options above: because the pointer's own `v` field cleanly discriminates old-shape (`v:1`, bare-name lookup) from new-shape (`v:2`, hashed/versioned-name lookup), **no explicit one-time migration pass is needed.** Existing un-versioned `remotes/<chaId>.local.bin` files for users who already opted in on Tauri/Node-server keep being read exactly as today by any root whose directory still carries a `v:1` pointer for that character. The migration happens lazily and incrementally, per character, the next time that specific character is dirtied and re-saved — at that point `encoder.set()` writes a fresh `v:2` pointer and a new versioned file, and the old `v:1` file becomes exactly the kind of superseded-and-unreferenced garbage the GC pass above needs to reclaim. **[Corrected — Codex round 5]** That reclamation is subject to the grace-period policy, the decoder-to-GC plumbing (recognizing the legacy bare-name shape as a possible orphan candidate is part of that same plumbing work, not a separate addition), **and** the unresolved publish-vs-delete concurrency protocol described in the "Garbage collection" section — not just the first two. A legacy `v:1` file is not safe to reclaim any sooner than a `v:2` file is; both are gated on the same not-yet-designed safety mechanism.

## Incremental adoption path

1. **Stage 3a (encoder/decoder pointer-versioning plus a real, verified GC concurrency protocol, Tauri + Node-server only, matching today's existing eligibility):** add the `v:2` pointer shape and content-addressed filenames to `risuSave.ts`; add the decoder-to-GC plumbing `cleanChunks()` needs to actually know which version a live root references (new `RisuSaveDecoder` metadata, or an equivalent second parse — see the corrected "Garbage collection" section); and — **[Corrected — Codex round 3]** — design, implement, and adversarially verify an actual publish-vs-GC concurrency protocol that closes the TOCTOU race the "Garbage collection" section now describes as unresolved (a simple grace-period timestamp is not sufficient, per that section's round-3 correction), including standalone concurrency stress tests for the specific interleavings flagged there, before this stage is considered done. No `db.enableRemoteSaving` default change yet, no account-sync eligibility change yet — this stage, once the concurrency protocol is actually closed (not just described), fixes the exact bug Codex found, for the backends where the mechanism is live today, without touching anything about who's allowed to use it. **This is now the largest, highest-risk piece of this whole design** — larger than the original "small addition" framing implied after round 1's correction, and larger still after round 3's finding that the round-1/round-2 fixes didn't actually close the race. Do not treat this stage as done on the basis of this report's description alone; it needs the same iterative-adversarial-review treatment Tier B Stage 1 got.
2. **Stage 3b (account-sync reclamation — [Corrected — Codex round 2]: currently blocked, not a scoped implementation step) :** the original framing of this stage — "narrow `cleanChunks()`'s early return so a remotes-only sweep can run for account-sync" — assumed a sweep-and-delete capability this client does not have: `AccountStorage` exposes no key-enumeration and no deletion capability at all (see the corrected "Garbage collection" section above). This stage cannot be scoped as a normal implementation task until one of three things happens: the hub is confirmed (through means not available to this investigation) to already expose a usable listing/delete capability; hub cooperation is obtained to add one (not currently achievable, per the confirmed upstream-only constraint); or the project owner makes an explicit, informed product decision to proceed without reclamation, accepting unbounded per-character remote-block accumulation on the hub as a known tradeoff. Do not treat this as a small carve-out to implement — it is presently an open blocker.
3. **Stage 3c (eligibility extension to account-sync) — gated on Stage 3b actually being resolved, not just Stage 3a shipping:** extend `encodeBlock()`'s gate (`risuSave.ts:379-384`) to include account-sync — this is the actual Stage-3-as-originally-attempted change. **[Corrected — Codex round 2]** The round-1 correction described this as "made safe by 3a existing underneath it," which is true only for the write-path corruption bug Codex's round-1 review on the original Tier B Stage 2-4 work found — it does not address the separate, newly-identified reclamation gap. Do not ship 3c until 3b is genuinely resolved (or the unbounded-growth tradeoff is explicitly and knowingly accepted), even though 3a alone is sufficient to fix the original corruption bug for Tauri/Node-server.
4. **Stage 3d (default flip, `db.enableRemoteSaving` opt-in → opt-out):** the second half of what was originally attempted and reverted together with 3c. Deliberately kept as its own last step, gated behind 3a-3c actually shipping and being observed as correct — this is a blast-radius decision (how many users' saves start touching this path) layered on top of a now-safe mechanism, not a prerequisite for the mechanism being safe.

This mirrors Report 06's own incremental-staging pattern (Stage 1 → Stage 2 → Stage 3 → Stage 4, each independently shippable and validated before the next), and keeps the highest-risk step (extending an already-once-reverted mechanism to account-sync) last, after the two lower-risk foundational pieces (naming fix, GC fix) are independently proven.

## Effort sizing

Smaller than the original Stage 3 attempt's actual cost turned out to be in one specific respect established by this investigation: the "atomic root-referencing" piece — which reads, in the abstract, like it could need a new transactional primitive layered under `saveDb()` — turns out to already exist as a side effect of how `encoder.set()`/`saveDb()` are already sequenced, so no new commit protocol is needed there. **[Corrected — Codex rounds 1 and 3]** The GC side is not small, and — as of round 3 — not even fully designed yet: it needs real decoder-to-GC plumbing (`risuSave.ts` exposing version/hash metadata the decoder currently discards, or an equivalent second parse) in `bootstrap.ts`'s two GC branches, **plus a genuine, adversarially-verified concurrency protocol for publish-vs-GC interleaving that this report has not yet solved** (see the "Garbage collection" section's round-3 correction) — this is real, open design work, not cross-file plumbing that can be scoped and estimated with confidence yet. Separately, and in addition to all of that: account-sync eligibility needs enumeration/deletion capabilities this repo does not have and cannot currently obtain — **not** "one further, narrowly-scoped carve-out" as an earlier draft of this paragraph said, but its own currently-unresolved blocker. None of this requires new server endpoints on `server.cjs` or any change to Stage 1/2's already-9-and-3-round-reviewed revision-checking machinery — this fix and Stage 1/2 are complementary (different write paths, `remotes/*` vs `database/database.bin`) rather than overlapping, so there's no risk of re-litigating either's own hard-won correctness — but the GC concurrency problem here is a comparably serious new one of its own, sized honestly rather than assumed away.

**What's genuinely deferred, and why:** a monotonic-revision-counter naming scheme (Option B) should not be pursued — not merely deferred as lower-priority, but actively not worth building, since content-addressing gives every property it would provide (a stable, comparably-immutable version identity) without needing any new server infrastructure and without depending on assumptions about account-sync hub internals this repo cannot verify, for the backend this whole feature exists to reach. If a future need for genuinely human-orderable version identifiers emerges (e.g., a "revision history" UI feature, not sketched or requested anywhere in this investigation), that would be its own separate product decision layered on top of content-addressing (a sequence number could still be attached as *metadata* alongside a content hash, without making the hash itself the coordination point) — not a reason to choose Option B as the primary mechanism now.

## Where this is a product decision, not a technical one

- **Whether to ever flip `db.enableRemoteSaving`'s default to opt-out (Stage 3d above) is unchanged from Report 06's own framing** — this investigation doesn't add new information that should shift that call either direction; it only establishes that the mechanism *can* be made safe first for Tauri/Node-server (Stage 3a), which was the missing precondition there, not a reason to now also decide the default-flip question. **[Corrected — Codex round 2]** This does *not* extend to account-sync eligibility (3c), which remains blocked on the unresolved reclamation gap (3b) regardless of what the default-flip decision ends up being. That remains the project owner's call about how much storage-layout risk to accept for users who never explicitly opted in — for Tauri/Node-server specifically.
- **Whether extending remote-block splitting to account-sync (3c) is worth doing before Phase 2's per-character DB decomposition (Roadmap Phase 2 item 5) lands** is a sequencing judgment call for *when* to attempt 3c, not a substitute for resolving 3b first — this report finds no technical reason 3a must wait for Phase 2 (it doesn't touch account-sync at all), but 3c specifically cannot proceed regardless of Phase 2 timing until the reclamation gap is closed or explicitly accepted. Report 06's own Stage-4/CRDT discussion already flagged that "per-character granular sync" thinking is the same shape of idea Phase 2's decomposition would reuse, so there may be a real efficiency argument for the project owner to sequence 3c and Phase 2 together once 3b is resolved, rather than build this mechanism's account-sync eligibility twice.
- **[Corrected — Codex rounds 2 and 4]** The publish-time liveness/grace-period handling described in the "Garbage collection" section (refresh/create a GC timestamp as part of publishing, keep a multi-day grace window before deleting anything superseded) is a **correctness requirement, not a product choice** — skipping it entirely would reopen the exact race this report exists to close, so it is not something a project owner should be asked to trade off. **But grace/timestamp handling by itself is not yet a complete safety mechanism** — per the round-3 correction, it does not close the deeper TOCTOU between GC's deletion *decision* (from one stale read) and its later *execution* (with no re-validation), which remains a genuinely unresolved design problem this report does not claim to have solved. Reclaiming superseded versions cannot be described as safe "once the grace window has passed" until that concurrency protocol is actually designed and verified — this closing bullet is not the place that happens; see the "Garbage collection" section. What genuinely *is* a product/UX call, layered on top of whatever safe mechanism eventually gets built: **whether to retain superseded versions for longer than the minimum safe window**, in service of a possible future "undo my last save" or "view a character's recent history" feature. This report's GC sketch assumes no such feature is wanted, matching the status quo (there is no history feature today). Content-addressed naming happens to make a future "keep the last N versions" feature comparatively cheap to add later if the project owner ever wants one, since the versions already exist as distinct, addressable objects rather than being destroyed on write the way the current stable-filename scheme destroys them — but that's a possible future enhancement layered on top of a safety mechanism that still needs to be designed, not part of it.
